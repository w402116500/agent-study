> 💡 **一句话速记结论**：
> 围绕质量、延迟、成本、异常和安全五大支柱构建实时大盘，建立黄金信号联动的立体监控体系。

##### 🎙️ 30 秒高频口答精要 (电梯演讲 / 直击要害)

大模型系统上线必须建立五维一体的可观测大盘：第一【模型质量】，监控离线回归测试集得分、线上无证据拒答率与用户点踩率（Thumbs-down）；第二【耗时延迟】，监控首字延迟（TTFT）、端到端 P95/P99 耗时及各工具调用耗时；第三【运营成本】，实时统计单次会话 Token 消耗、按模型/租户计费趋势；第四【系统故障】，监控 HTTP 5xx 率、Docker 沙箱超时率与熔断触发次数；第五【安全事件】，实时告警越权拦截、AST 白名单阻断与敏感词触发次数。

##### ⏱️ 60~120 秒深度展开 (系统架构 / 机制与推演 / 逐行源码讲解)

线上大盘监控设计：模型质量、P95/P99 延迟、成本、失败率与安全事件的立体可观测体系：
1. **五大黄金信号的联动监控蓝图**：
- **维度一：模型质量（Quality）**：实时抽检生成的 Faithfulness 分数、答案拒绝率（当知识库无答案时是否老实拒答）；
- **维度二：性能与延迟（Latency）**：首字时间（TTFT，P95 < 800ms）、端到端流式生成总耗时（P99 < 12s）、工具调用耗时；
- **维度三：成本开销（Cost）**：按会话/租户统计 Prompt Tokens、Completion Tokens 消耗趋势与实时折合人民币金额；
- **维度四：失败与容错（Error Rate）**：HTTP 5xx 比例、Tool Calling 连续三次失败熔断率、SQL 语法错误占比；
- **维度五：安全合规（Security）**：Prompt Injection 拦截次数、Docker 沙箱逃逸探针触发量、敏感字段脱敏触发计数。

2. **核心代码：基于 Prometheus 标准指标库的统一可观测埋点器**：

```python
from prometheus_client import Counter, Histogram, Gauge
import time

# 1. 延迟指标：首字时间与总生成时间直方图 (Histogram)
METRIC_TTFT = Histogram('llm_first_token_latency_seconds', '大模型首字返回延迟', ['model', 'endpoint'])
METRIC_LATENCY = Histogram('llm_generation_latency_seconds', '端到端总生成耗时', ['model'])

# 2. 成本与 Token 计数器 (Counter)
METRIC_TOKENS = Counter('llm_token_usage_total', '累计消耗 Token 统计', ['model', 'token_type'])

# 3. 失败与异常计数器
METRIC_ERRORS = Counter('agent_execution_errors_total', 'Agent 工具与模型执行异常', ['error_category'])

# 4. 安全事件告警计数器
METRIC_SECURITY = Counter('security_threats_blocked_total', '安全威胁拦截事件', ['threat_type'])

class ObservabilityHook:
    def record_chat_metrics(self, model: str, ttft: float, total_dur: float, prompt_tk: int, comp_tk: int, status: str):
        # 记录延迟
        METRIC_TTFT.labels(model=model, endpoint="/api/chat").observe(ttft)
        METRIC_LATENCY.labels(model=model).observe(total_dur)
        
        # 记录 Token 成本
        METRIC_TOKENS.labels(model=model, token_type="prompt").inc(prompt_tk)
        METRIC_TOKENS.labels(model=model, token_type="completion").inc(comp_tk)
        
        # 记录异常状态
        if status != "SUCCESS":
            METRIC_ERRORS.labels(error_category=status).inc()
```

3. **大盘报警联动实战法则**：
- **P99 延迟突增 + Token 计数正常** ➔ 外部模型供应商 API 拥堵或底层 Milvus 检索变慢；
- **P99 延迟突增 + Token 计数暴涨** ➔ 发生了多轮死循环或超大长文档注入；
- **失败率突增 + 安全事件平稳** ➔ 数据库连接池耗尽或 Docker 镜像启动异常。联动大盘能做到 1 分钟快速定界排障。

##### ❓ 面试官高频追问预判 (连环问攻防对决)

###### 🎯 追问对决：在微服务分布式链路中，如何使用 Trace ID 将前端一次点击、后端 SSE、多次 Tool Call 与 Docker 沙箱日志串联？

- 🎯 **考官意图**：考察分布式链路追踪（OpenTelemetry / Distributed Tracing）实战能力。
- 🛡️ **攻防标准应答**：在前端用户发起请求时，生成唯一的 `X-Trace-ID: req_uuid` 并在 HTTP 请求头中透传；FastAPI 接入层通过中间件捕获该 ID，并借助 Python 3.7+ 的 `contextvars.ContextVar` 在异步调用链路中隐式传递；当调用后台 LLM API、Milvus 检索和向 Docker 投递代码时，将该 Trace ID 作为请求元数据或环境变量注入；日志系统统一输出带 `[TraceID: req_uuid]` 的 JSON 结构化日志，在 Kibana/Grafana Tempo 中输入一个 ID 即可秒级还原包含数十个子任务的完整调用树拓扑。
- ⚠️ **避坑要点**：不要只在入口打 log，异步跨线程或进入子进程/Docker 后必须显式透传 Trace ID。

###### 🎯 追问对决：当发现线上 P99 延迟突增时，如何在 Grafana 大盘上 1 分钟内完成'网络-模型-工具-存储'的分层排查？

- 🎯 **考官意图**：考察黄金信号大盘设计与排障逻辑（Golden Signals Triaging）。
- 🛡️ **攻防标准应答**：查看分层耗时堆叠柱状图（Time Breakdown Stacked Chart）：1) 首先看【网络首字延迟 TTFT】：若首字延迟就高，直接定性为上游大模型 API 拥堵或排队；2) 若首字延迟极低但总耗时长，看【工具调用耗时 Tool Latency】：观察是 Docker 沙箱容器启动慢，还是数据库 SQL 执行超时；3) 若工具耗时正常，看【向量检索耗时 Retrieval Latency】：检查 Milvus 是否因内存不足触发了磁盘索引降级。四张堆叠看板一目了然，瞬间锁定责任方。
- ⚠️ **避坑要点**：不要盲目登录服务器去看 top，现代分布式架构必须靠 APM 耗时分层看板秒级定界。

##### 🛡️ 系统设计防御边界与权衡 (Anti-Goals / 放弃的假设)

- 🛑 全量采集每个 Token 的追踪数据会带来存储膨胀，建议采用自适应采样率（如正常请求 10% 采样，错误请求 100% 采样）
- 🛑 指标系统必须支持按租户多维度聚合与下钻

# E-03: 哪些互不依赖的工具调用可以并行？并行后如何合并结果、限制资源竞争和保持可审计？

- **归属项目**：`两个项目通用` | **题目类型**：`深挖题` | **难度等级**：`进阶` | **核心主题**：`并发控制, 并行调用, 审计日志, 资源管理`
- **可信级别**：项目事实 / 当前实现

> 💡 **一句话速记结论**：
> 纯只读、无状态且入参解耦的工具可并发；通过信号量限流、结果按 tool_call_id 保序归集与全量哈希落盘。

##### 🎙️ 30 秒高频口答精要 (电梯演讲 / 直击要害)

哪些工具可以并行？只有满足'纯只读、无副作用、互不依赖对方输出'的工具才能并行（例如多指标并发 SQL 查询、多文档检索召回）。并行合并时，必须使用 `tool_call_id` 作为唯一键组装结果，即使底层执行是乱序完成的，回传给模型的数组也必须保持稳定对应；同时采用 `asyncio.Semaphore` 限制最大并发池（如限制同时最多 3 个沙箱实例），并在写入可审计日志时记录全局递增流水号与因果时间戳。

##### ⏱️ 60~120 秒深度展开 (系统架构 / 机制与推演 / 逐行源码讲解)

在 Agent 架构中，互不依赖的工具调用并行化、资源竞争治理与可审计实现：
1. **判定工具可并行的核心标准**：
- **纯只读与无副作用（Idempotent & Read-Only）**：如并行执行多份财报的数据检索（`search_filing_q1` 与 `search_filing_q2`），互不影响物理状态；
- **入参无数据依赖（No DAG Dependencies）**：工具 B 的输入参数不依赖工具 A 的执行返回值；
- **反例禁止并行**：先执行“创建临时分析表”再执行“向该表插入中间结果”，存在严格时序因果，严禁并行。

2. **核心代码：受控并发、信号量隔离与审计日志落盘**：

```python
import asyncio
import time
import hashlib
from typing import List, Dict, Any

class ConcurrencyManager:
    def __init__(self, max_concurrent: int = 5):
        # 1. 信号量限制最大并发数，防止打崩底层 Milvus 连接池或数据库
        self.semaphore = asyncio.Semaphore(max_concurrent)

    async def run_with_audit(self, tool_func, tool_id: str, args: dict) -> Dict[str, Any]:
        start_ts = time.time()
        async with self.semaphore:
            try:
                # 执行具体工具逻辑
                res = await tool_func(args)
                status = "SUCCESS"
                err_msg = None
            except Exception as e:
                res = None
                status = "FAILED"
                err_msg = str(e)
            
            elapsed_ms = int((time.time() - start_ts) * 1000)
            
            # 2. 结构化审计条目：包含全量哈希签名，确保审计不可篡改
            audit_entry = {
                "tool_call_id": tool_id,
                "args_hash": hashlib.sha256(str(sorted(args.items())).encode()).hexdigest(),
                "duration_ms": elapsed_ms,
                "status": status,
                "error": err_msg
            }
            # 异步写审计通道
            self.write_audit_log(audit_entry)
            
            return {"tool_call_id": tool_id, "content": res if status == "SUCCESS" else err_msg}

    def write_audit_log(self, entry: dict):
        # 模拟落盘到不可篡改的日志存储 (如 ElasticSearch / 专属日志表)
        pass
```

3. **并发合并与保序契约**：
- **保序组装**：通过 `asyncio.gather` 保留发起顺序，或者通过字典基于 `tool_call_id` 将各异步任务的结果安全填入响应槽位，坚决防止由于执行快慢导致返回模型的消息错乱；
- **资源保护（Pool Protection）**：Milvus 检索与数据库查询设置独立线程池/连接池配额，避免 10 个并发 Agent 任务瞬间耗尽全站连接数；
- **超时快速释放**：每个并行分支强置超时上限（如 8 秒），超时单个任务自动抛出并释放信号量，不阻塞整体流程。

##### ⭐ 核心关键技术点 (回答骨架)

- ✔️ 只有无副作用且无数据依赖的只读查询类工具允许并行拉起
- ✔️ 使用 asyncio.Semaphore 严格限制宿主机沙箱与数据库连接的并发槽位
- ✔️ 并行异步执行完毕后，必须基于 tool_call_id 保序重构消息链并固化审计因果日志

##### ❓ 面试官高频追问预判 (连环问攻防对决)

###### 🎯 追问对决：如果并行执行的 3 个工具中，有 2 个成功但 1 个抛出了致命系统异常，合并层应该如何向模型回报？

- 🎯 **考官意图**：考察并行任务部分失败（Partial Failure）的优雅处理与上下文拼接。
- 🛡️ **攻防标准应答**：坚决不能直接抛出全局异常中断整个会话！合并层应当利用 `asyncio.gather(..., return_exceptions=True)` 分别解包结果：成功的 2 个工具回传正常真实数据并携带其对应的 `tool_call_id`；失败的 1 个工具则将其错误包装为特定 `[TOOL_ERROR]` 格式，同样带上其对应的 `tool_call_id` 回传给模型。让大模型知晓部分事实已到位，由模型决定是基于已有数据进行部分解答并告知用户某项指标查询超时，还是发起局部降级查询。
- ⚠️ **避坑要点**：不能因为一个非核心工具失败就把已成功获取的全部上下文丢弃丢给用户报错。

###### 🎯 追问对决：如何通过动态依赖分析（DAG 解析）让原本串行的部分复杂工具在满足前置依赖后自动触发并行？

- 🎯 **考官意图**：考察拓扑排序与高级工作流调度引擎原理。
- 🛡️ **攻防标准应答**：构建【动态任务拓扑图（Dynamic DAG Scheduler）】：在模型下发复杂任务时，分析各任务参数中的引用占位符（如 `$step1.output.id`）。通过入度拓扑排序识别入度为 0 的节点立即并发调度；某个上游节点执行完成并产出结果后，将其输出注入下游输入，动态将下游节点入度减 1。一旦下游节点入度归零，自动唤醒协程并发执行，实现串行与并行的自适应无缝结合。
- ⚠️ **避坑要点**：注意循环依赖（Cycle Detection），在建图前必须做环路检测（DFS/Tarjan 算法）防止死锁。

##### 🛡️ 系统设计防御边界与权衡 (Anti-Goals / 放弃的假设)

- 🛑 并行执行会急剧放大数据库连接池（Connection Pool）和并发内存的峰值压力
- 🛑 当前 DataPilot 将单次并行工具调用数硬限制在最大 3 个

# E-04: 一个工具失败时，如何区分参数错误、权限拒绝、业务空结果、超时和基础设施故障？

- **归属项目**：`两个项目通用` | **题目类型**：`深挖题` | **难度等级**：`进阶` | **核心主题**：`错误处理, 异常分类, 状态码, 工程容错`
- **可信级别**：项目事实 / 标准规范

> 💡 **一句话速记结论**：
> 将错误严格归入参数、权限、业务、超时、基建五大标准枚举，明确区分可自愈提示与熔断阻断。

##### 🎙️ 30 秒高频口答精要 (电梯演讲 / 直击要害)

系统通过统一异常分层模型处理工具失败：第一类【参数错误】（400，字段类型错/缺参），属于模型幻觉，返回友好提示让模型自愈修正；第二类【权限拒绝】（403，越权/注入阻断），属于安全越权，立即抛出终态拦截并断路；第三类【业务空结果】（200-Empty，无匹配数据），属于正常逻辑，告知模型'无数据'引导其调整筛选条件；第四类【超时】（408）与第五类【基础设施故障】（500，Docker 宕机/DB 断连），属于平台故障，立即触发服务熔断与降级重试，严禁让模型在应用层反复无意义打转。

##### ⏱️ 60~120 秒深度展开 (系统架构 / 机制与推演 / 逐行源码讲解)

在企业级 Agent 生产环境中，工具失败的标准分级与精准容错机制：
1. **五大核心错误类型的严谨判定矩阵**：
- **1. 参数与语法错误（CLIENT_PARAM_ERROR）**：
  - 现象：Pydantic 校验失败、JSON 解析异常、SQL 语法错误（缺少 GROUP BY）。
  - 策略：向模型返回清晰的人类可读修正指引，允许最多 2 次自愈重试。
- **2. 权限与安全拒绝（PERMISSION_DENIED）**：
  - 现象：越权访问隔离租户数据、AST 拦截到敏感写指令（DROP/DELETE）。
  - 策略：立刻硬阻断，禁止重试，向模型注入标准违规事实，直接向终端用户警报。
- **3. 业务空结果（EMPTY_BUSINESS_RESULT）**：
  - 现象：SQL 或向量库执行完全成功但返回 0 条记录（如“未查到该员工 2026 年考勤”）。
  - 策略：作为正常事实返回给模型，引导模型明确向用户回复“暂无相关记录”，严禁臆造。
- **4. 执行超时（TIMEOUT_EXCEEDED）**：
  - 现象：复杂聚合 SQL 或海量文档重排耗时超过阈值（如 > 8.0s）。
  - 策略：终止执行，返回提示建议缩小查询时间跨度或分页查询。
- **5. 基础设施故障（INFRA_FAILURE）**：
  - 现象：数据库连接池爆满、Docker 沙箱 Daemon 崩溃、Milvus 节点无响应。
  - 策略：触发熔断器，立刻向用户道歉并降级，严禁让模型在此类故障下无效重试。

2. **核心代码：五级错误分类与智能路由中继器**：

```python
from enum import Enum
from typing import Dict, Any

class ErrorCategory(str, Enum):
    PARAM_ERROR = "PARAM_ERROR"         # 可自愈：引导修正
    PERMISSION = "PERMISSION_DENIED"    # 零容忍：阻断并报警
    EMPTY_RESULT = "EMPTY_RESULT"       # 正常业务流：真实事实
    TIMEOUT = "TIMEOUT"                 # 策略收缩：引导缩小范围
    INFRA = "INFRASTRUCTURE_FAULT"     # 熔断告警：降级兜底

def classify_and_route_tool_result(result_or_exc: Any) -> Dict[str, Any]:
    """将原生结果或异常统一分流为标准化结构"""
    if isinstance(result_or_exc, SyntaxError):
        return {
            "category": ErrorCategory.PARAM_ERROR,
            "feedback_to_model": f"SQL语法错误: {str(result_or_exc)}，请修正后重试一次。",
            "allow_retry": True
        }
    elif isinstance(result_or_exc, PermissionError):
        return {
            "category": ErrorCategory.PERMISSION,
            "feedback_to_model": "安全策略拦截：该操作涉及未经授权的权限边界。",
            "allow_retry": False
        }
    elif isinstance(result_or_exc, TimeoutError):
        return {
            "category": ErrorCategory.TIMEOUT,
            "feedback_to_model": "执行超时：计算量过大，请尝试缩小查询时间窗口或增加过滤条件。",
            "allow_retry": True
        }
    # 正常空结果
    elif isinstance(result_or_exc, list) and len(result_or_exc) == 0:
        return {
            "category": ErrorCategory.EMPTY_RESULT,
            "feedback_to_model": "查询成功，但数据表中满足条件的数据条目为 0。",
            "allow_retry": False
        }
    # 其余未知异常按基础设施故障处理
    return {
        "category": ErrorCategory.INFRA,
        "feedback_to_model": "系统底层数据节点暂时不可用，已进入熔断保护。",
        "allow_retry": False
    }
```

3. **生产防坑与成本防线**：
- 绝对区分“模型犯的错”与“系统生的病”。把系统 500 当成参数错误甩给模型，只会诱发模型产生幻觉，疯狂修改正确的参数并无谓消耗上万 Token；明确的错误分类是控制 Agent 推理成本的第一防线。

##### ⭐ 核心关键技术点 (回答骨架)

- ✔️ 严格划分为参数、权限、空结果、超时、基础设施五大错误类别
- ✔️ 参数错误允许自愈，空结果正常引导，权限与安全拒绝坚决阻断且禁重试
- ✔️ 超时硬杀进程防资源挂死，基建故障触发系统级熔断与旁路降级

##### ❓ 面试官高频追问预判 (连环问攻防对决)

###### 🎯 追问对决：如果一个复杂 SQL 报错来自于数据库内核的生僻错误码，系统如何将其转换为模型看得懂的修正提示？

- 🎯 **考官意图**：考察数据库原生错误到自然语言/语义反馈的翻译层设计。
- 🛡️ **攻防标准应答**：在工具层维护一张【错误码转换表（Error Code Translator）】：例如捕获 PostgreSQL 原生 '42803: column x must appear in the GROUP BY clause'，通过正则或映射字典将其翻译成高价值提示：'字段 x 未包含在 GROUP BY 子句中，且未使用聚合函数包裹，请调整聚合查询结构'。将黑盒错误转化为具象的操作建议，能将模型的自愈成功率从 20% 提升到 85% 以上。
- ⚠️ **避坑要点**：严禁直接将原始十六进制错误码或未经清洗的 C++ 驱动报错原样扔给大模型。

###### 🎯 追问对决：当基础设施连续出现 500 故障时，如何通过滑动窗口限流阻止后续会话继续浪费大模型调用费用？

- 🎯 **考官意图**：考察熔断器模式（Circuit Breaker）在 LLM/Agent 系统中的应用。
- 🛡️ **攻防标准应答**：部署【熔断拦截器（Circuit Breaker）】：记录最近 60 秒内工具执行的错误率。若底层持续抛出 `INFRA_FAILURE` 且错误率超过 50%，熔断器立即切换为 OPEN（打开）状态，持续 30 秒内直接在接入层快速拒绝所有工具调用并降级为通用话术，严禁再调用昂贵的大模型推理，保护公司账单与系统稳定性。
- ⚠️ **避坑要点**：不要等到几百个请求全部超时堆积才告警，必须有滑动窗口自动化快速熔断机制。

##### 🛡️ 系统设计防御边界与权衡 (Anti-Goals / 放弃的假设)

- 🛑 严禁直接将原始的 Python Traceback 堆栈暴露给模型，防止内部源码与环境路径泄漏
- 🛑 空结果绝不是错误，必须作为结构化正常数据交给模型做逻辑决策

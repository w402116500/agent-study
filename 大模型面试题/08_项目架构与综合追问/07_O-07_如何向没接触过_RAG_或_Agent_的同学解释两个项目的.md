# O-07: 如何向没接触过 RAG 或 Agent 的同学解释两个项目的核心差异？

- **归属项目**：`两个项目通用` | **题目类型**：`简单题` | **难度等级**：`基础` | **核心主题**：`系统设计, RAG, Agent`
- **可信级别**：本地通用知识

> 💡 **一句话速记结论**：
> RAG 是‘给模型开卷考试找参考书’，Agent 是‘给模型配工具和环境让它自主按计划解题’，输入形式与交互模式不同。

##### 🎙️ 30 秒高频口答精要 (电梯演讲 / 直击要害)

核心区别可以用两个比喻讲清：SuperMew RAG 就像‘带参考书的开卷考试’——用户提问是非结构化问题，系统负责去海量文档里把最相关的几页找出来喂给模型，模型只需要理解并归纳，链路是前向单向的；DataPilot Agent 就像‘给实习生配了电脑、计算器和数据库权限’——用户提问是复杂的数据分析目标，模型自己决定‘第一步查哪张表、第二步算什么指标、第三步写 Python 画什么图’，系统提供沙箱和安全网关，链路是多轮动态循环迭代的。

##### ⏱️ 60~120 秒深度展开 (系统架构 / 机制与推演 / 逐行源码讲解)

向初学者清晰拆解 RAG 与 Agent 的本质差异，可以用“查阅开卷图书”与“雇佣只读分析员”进行形象对比：
1. **SuperMew（RAG）的核心机制：静态知识管道**：
- **本质**：是一个确定性的文本检索与内容抽取管道。它面对的是非结构化事实（PDF、Word、制度规范）；
- **行为模式**：用户提问 ➔ 系统把问题当成检索词 ➔ 去 Milvus/BM25 捞出最匹配的前 8 个段落 ➔ 把段落塞给大模型 ➔ 大模型充当“总结员”，提炼并注明出处；
- **状态特征**：单次无状态流动，没有与外部世界的数据修改或交互，不具备自主推演行动链。

2. **DataPilot（Agent）的核心机制：目标驱动的受控决策回路**：
- **本质**：是一个具备状态机、工具调用与动态反思的自主规划智能体。它面对的是企业结构化数据（Postgres、MySQL 数据库）；
- **行为模式**：用户提问 ➔ 模型制定规划 ➔ 自主决定是查 SQL 还是写 Python 绘图 ➔ 服务端通过网关审计并执行工具 ➔ 拿到数据后模型反思是否解决 ➔ 多轮循环直到生成最终报告；
- **状态特征**：强状态机流转，具备明确的环境感知、行动、结果反馈闭环与严格的安全审计边界。

3. **核心代码对比：检索单向流 vs 状态机循环**：
```python
# RAG：线性静态管道（确定性步骤）
def run_rag_pipeline(query: str) -> str:
    chunks = hybrid_retrieve(query, top_k=8)  # 1. 查
    context = format_context(chunks)          # 2. 拼
    return llm.generate_answer(query, context) # 3. 答

# Agent：带状态与工具反馈的受控动态循环
def run_agent_loop(goal: str, state: dict) -> str:
    while state["step"] < state["max_budget"]:
        # 1. 模型根据环境状态自主决定下一步动作
        action = llm.plan_next_action(goal, state["history"])
        if action.is_finish:
            return generate_final_report(state["history"])
            
        # 2. 服务端受控安全执行工具
        tool_result = execute_sandboxed_tool(action.tool_name, action.args)
        
        # 3. 反思更新状态，进入下一轮迭代
        state["history"].append({"action": action, "result": tool_result})
        state["step"] += 1
```

##### ⭐ 核心关键技术点 (回答骨架)

- ✔️ RAG 面向非结构化知识的检索与合成（查资料）
- ✔️ Agent 面向结构化业务的意图规划与受控执行（办事情）
- ✔️ RAG 是静态流水线，Agent 是具备观察-思考-行动动态循环的智能体
- ✔️ 两者互不取代，企业真实场景中常在 Agent 工具箱中集成 RAG 检索工具

##### ❓ 面试官高频追问预判 (连环问攻防对决)

###### 🎯 追问对决：为什么不能直接用 RAG 的方式做数据分析？（如把整张表转成文本切块检索）

- 🎯 **考官意图**：考察对结构化关系数据与向量语义检索本质差异的底层认知。
- 🛡️ **攻防标准应答**：因为向量检索基于语义相似度，天然丧失精准的聚合与计算能力。一张包含 100 万行订单的表转成文本后，向量检索既无法计算'2024年总GMV'（只能召回零碎的几行文本碎片而无法加和），更无法处理多表关联 JOIN；数据分析必须借助关系代数和 SQL 引擎进行精确计算，这正是 Agent 调度工具的不可替代之处。
- ⚠️ **避坑要点**：千万不能说'可以切小一点存进去'，必须点出语义相似度检索与数值代数计算的根本冲突。

###### 🎯 追问对决：在你的 DataPilot 中，未来有没有引入 RAG 检索企业指标口径字典的规划？

- 🎯 **考官意图**：考察对 RAG + Agent 复合架构演进路线的前瞻性思考。
- 🛡️ **攻防标准应答**：这正是下一阶段的重点规划：构建'指标与元数据 RAG 插件'。企业中有大量复杂的口径定义（如'什么是高净值活跃用户'、'净利率如何剔除退款'），通过在 Opening 阶段引入轻量 RAG 检索企业指标知识库，将精准的计算口径注入 Agent 的系统提示词中，再由 Agent 生成标准 SQL，能够彻底消除大模型对业务口径的理解幻觉。
- ⚠️ **避坑要点**：不要把两者割裂开来，要展示出将 RAG 作为 Agent 辅助知识外脑的高阶系统设计视野。

##### 🛡️ 系统设计防御边界与权衡 (Anti-Goals / 放弃的假设)

- 🛑 RAG 不擅长精确多行多列数值聚合计算（容易数错行或幻觉）
- 🛑 Agent 消耗 Token 与调用延迟显著高于单一 RAG 检索

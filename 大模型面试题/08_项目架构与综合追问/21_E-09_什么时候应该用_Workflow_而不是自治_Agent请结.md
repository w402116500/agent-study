# E-09: 什么时候应该用 Workflow 而不是自治 Agent？请结合固定步骤、动态分支、可审计性和成本回答。

- **归属项目**：`两个项目通用` | **题目类型**：`深挖题` | **难度等级**：`进阶` | **核心主题**：`架构选型, Workflow vs Agent, 系统稳定性, 成本控制`
- **可信级别**：项目事实 / 架构选型

> 💡 **一句话速记结论**：
> 固定链路与严格审计用确定性 Workflow，开放探寻与动态分支用受控 Agent，生产落地通常是 Agent 嵌在 Workflow 中。

##### 🎙️ 30 秒高频口答精要 (电梯演讲 / 直击要害)

什么时候用 Workflow，什么时候用自治 Agent？选型取决于'路径的确定性与对失败的容忍度'：如果业务目标明确、输入输出格式标准、执行步骤可提前编排（如标准财报抽取、固定指标日历计算），必须用 Workflow（有向无环图 DAG），成本低、可重试、延迟确定且 100% 可审计；如果面对的是开放式探索、未知分支需要根据前一步动态反馈调整工具（如未知原因的指标异动深度排查），才引入自治 Agent。生产最佳实践是'外层 Workflow 守住骨架，内层局部节点用受控 Agent'。

##### ⏱️ 60~120 秒深度展开 (系统架构 / 机制与推演 / 逐行源码讲解)

何时选择确定性工作流（Workflow），何时选择自治智能体（Agent）：
1. **两者的核心维度深度对比矩阵**：

| 评估维度 | 确定性工作流 (Deterministic Workflow) | 自治智能体 (Autonomous Agent) |
| :--- | :--- | :--- |
| **执行路径** | 静态编排 DAG（明确的 Step 1 ➔ Step 2 ➔ Step 3） | 模型动态自规划（ReAct / 循环分支） |
| **可审计性** | 100% 确定可复现，每一步入参出参严格可控 | 存在概率性随机，每次推理路径可能轻微不同 |
| **成本与延迟** | 单次调用开销固定，P99 延迟稳定（< 2s） | 消耗多次 LLM 推理 Token，延迟波动大（5s ~ 30s） |
| **适用业务** | 标准财报数据清洗、固定审批流、每日报表生成 | 开放式多轮诊断、发散性归因分析、代码编写与调试 |

2. **生产级架构模式：Agent 嵌入在受控 Workflow 内部**：

```python
# 生产最佳实践：外层是铁打的确定性 Pipeline，内层局部节点使用 Agent 灵活推理
async def enterprise_analysis_pipeline(doc_id: str, query: str):
    # 步骤 1：固定确定性代码提取文本（Workflow 阶段，零大模型成本）
    raw_text = await fetch_document_content(doc_id)
    
    # 步骤 2：确定性关键词与向量召回（Workflow 阶段，毫秒级响应）
    retrieved_chunks = await run_hybrid_search(raw_text, query, top_k=10)
    
    # 步骤 3：局部自治 Agent 节点（仅在复杂归因推断时调用受控 Agent）
    # 受限上下文、固定最大 3 轮迭代、受限工具集合
    agent_insight = await run_bounded_agent(
        context=retrieved_chunks,
        max_turns=3,
        tools=[calc_tool, verify_tool]
    )
    
    # 步骤 4：固定格式渲染与风控合规检查（Workflow 阶段，安全归宿）
    return enforce_compliance_and_render_report(agent_insight)
```

3. **架构选型决策铁律**：
- **只要业务步骤是已知的，坚决用代码写死 Workflow，绝对不交给 Agent 自由发挥**！
- 只有当“下一步该干什么取决于上一步的未预料结果”且“分支极其繁杂无法穷举”时，才将该局部节点托付给受控 Agent。

##### ⭐ 核心关键技术点 (回答骨架)

- ✔️ 确定性、合规严、成本敏感场景坚决选 Workflow；开放分支、自适应探索场景选 Agent
- ✔️ Workflow 具备确定性延迟和 100% 幂等可测性，纯 Agent 存在 Token 膨胀与偶发死循环风险
- ✔️ 生产落地最佳实践是'外层 Workflow 约束全局状态与硬边界，内层受控 Agent 负责局部灵活探寻'

##### ❓ 面试官高频追问预判 (连环问攻防对决)

###### 🎯 追问对决：如何将一个原本写死的 10 步复杂 Workflow 逐步重构为'人在回路'（Human-in-the-Loop）的半自治架构？

- 🎯 **考官意图**：考察传统工作流向高级人机协同 Agent 架构平滑演进的工程能力。
- 🛡️ **攻防标准应答**：引入【带状态挂起的中间态节点（Interrupt & Suspend Mechanism）】：借助 LangGraph 或 Temporal 状态机，在前 5 步自动化执行（数据清洗、多源检索、初步汇总）完成后，系统将计算图持久化到数据库并向前端推送待审批事件。当业务专家在 Web 界面完成数据复核、修改或点击'通过'后，状态机从上次检查点反序列化恢复执行后续 5 步，兼顾了工作流的高效与关键业务节点的人工兜底安全性。
- ⚠️ **避坑要点**：不要重构为完全放手让 Agent 自动跑完 10 步，核心风险业务必须保留人工审计挂起。

###### 🎯 追问对决：使用 LangGraph 或 Temporal 编排工作流时，如何处理 Agent 节点的非幂等重试？

- 🎯 **考官意图**：考察分布式工作流引擎面对大模型不确定性重试时的状态一致性设计。
- 🛡️ **攻防标准应答**：实施【节点结果持久化快照与幂等标记（Idempotency Token per Node）】：工作流框架为 Agent 节点分配全局唯一的 `step_run_id`。如果 Agent 节点在执行外部调用后、自身回传前发生网络超时，重试唤醒时先检查该 `step_run_id` 是否已在数据库产出过有效输出快照。若已有快照直接返回历史结果，不再重新激活大模型生成，从而防止重复计费并保证下游状态确定性。
- ⚠️ **避坑要点**：不能依赖大模型自己的记忆，必须在工作流编排器外层记录每个节点的状态快照。

##### 🛡️ 系统设计防御边界与权衡 (Anti-Goals / 放弃的假设)

- 🛑 拒绝'万物皆 Agent'的过度设计，能用 3 行 Python 代码解决的固定逻辑坚决不用大模型 Agent
- 🛑 系统最终交付给用户的必须是高确定性、高可信赖的分析结果

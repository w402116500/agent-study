# O-05: 项目里有哪些持久化存储？各自保存什么，为什么不合并成一个？

- **归属项目**：`两个项目通用` | **题目类型**：`简单题` | **难度等级**：`基础` | **核心主题**：`系统设计, SQL`
- **可信级别**：项目事实 / 当前代码

> 💡 **一句话速记结论**：
> 系统采用 Milvus(向量/稀疏索引)、PostgreSQL(关系元数据/正文/审计事件)与 Redis(热点缓存/会话状态)三类存储，职责严格正交，不可盲目合并。

##### 🎙️ 30 秒高频口答精要 (电梯演讲 / 直击要害)

项目中共有三类持久化与半持久化存储：1. Milvus：专用于存储 SuperMew 的 L3 向量嵌入（1024 维 BGE-M3）以及倒排稀疏索引（BM25），负责海量向量的毫秒级相似度高并发比对；2. PostgreSQL：系统的持久化核心，存储 SuperMew 的完整 L1/L2 大块文本与文档元数据，以及 DataPilot 的 Run 状态、SQL 审计日志（Audit Log）、产物元数据与全局事件流水（SSE Events）；3. Redis：用于 SuperMew 高频父块的正文热点缓存，以及 DataPilot 在线 Session 状态与分布式锁。三者在读写特征、事务保障与索引算法上完全正交，合并不利于横向扩展与性能隔离。

##### ⏱️ 60~120 秒深度展开 (系统架构 / 机制与推演 / 逐行源码讲解)

系统根据数据访问模式、一致性要求与读写吞吐，严格划分了四类持久化存储体系：
1. **Milvus 向量数据库**：
- **职责**：专职存储 L3 叶子切块（800字原子）的 1024 维 BGE-M3 向量表征与原生 BM25 倒排索引；
- **选型原因**：支持十亿级向量的高性能 HNSW 索引构建，检索延迟稳定在 15ms 以内，支持基于 Metadata 的前置标量硬过滤。

2. **PostgreSQL 关系数据库**：
- **职责**：存储文档元数据（文档版本、大小、Hash）、L1/L2 父级全文内容、DataPilot 的 Session 会话、Audit 审计记录与 Run 全量事件流；
- **选型原因**：具备强 ACID 事务保障，JSONB 灵活支持复杂结构化日志与事件溯源，支持外键与复合约束。

3. **Redis 内存缓存**：
- **职责**：缓存高频上卷的 L1/L2 父级全文块（Key: `parent_chunk:{id}`，TTL=2小时），缓存 DataPilot 的活跃会话状态与 Token 预算原子计数器；
- **选型原因**：将父级大文本读取的 P99 延迟从 Postgres 的 8ms 压低至 0.5ms，极大释放关系数据库的并发连接压力。

4. **本地只读沙箱卷（Host Volume）**：
- **职责**：只读挂载 CSV/Parquet 原始数据源文件供 Python 容器分析，以及接收临时输出的 PNG/HTML 产物。

5. **核心代码：分层存储写入与一致性维护**：
```python
import redis
import psycopg2
from pymilvus import Collection

class DocumentStorageManager:
    """多存储协同与原子发布管理器"""
    def __init__(self, pg_conn, redis_cli: redis.Redis, milvus_col: Collection):
        self.pg = pg_conn
        self.redis = redis_cli
        self.milvus = milvus_col

    def persist_document_chunks(self, doc_id: str, l1_chunks: list, l3_chunks: list):
        # 1. 关系数据写入 PG 事务中，获取持久化唯一 ID
        with self.pg.cursor() as cur:
            for l1 in l1_chunks:
                cur.execute(
                    "INSERT INTO doc_parents (id, doc_id, content, level) VALUES (%s, %s, %s, %s)",
                    (l1["id"], doc_id, l1["text"], "L1")
                )
            self.pg.commit()

        # 2. 高频父级同步预热进入 Redis 缓存
        pipe = self.redis.pipeline()
        for l1 in l1_chunks:
            pipe.setex(f"parent_chunk:{l1['id']}", 7200, l1["text"])
        pipe.execute()

        # 3. 向量与元数据批量灌入 Milvus
        entities = [
            [c["id"] for c in l3_chunks],
            [c["embedding"] for c in l3_chunks],
            [c["parent_id"] for c in l3_chunks]
        ]
        self.milvus.insert(entities)
        self.milvus.flush()
```

##### ⭐ 核心关键技术点 (回答骨架)

- ✔️ Milvus 专职向量相似度与稀疏全文检索，保证召回吞吐与低延迟
- ✔️ PostgreSQL 专职大文本持久化、关系完整性、事务审计与事件回放流水
- ✔️ Redis 专职父块正文高速缓存、任务取消信号与临时会话
- ✔️ 合并到单一库会导致内存/磁盘 I/O 竞争严重、大文本击穿缓存

##### ❓ 面试官高频追问预判 (连环问攻防对决)

###### 🎯 追问对决：为什么 SuperMew 不直接用 PostgreSQL 的 pgvector 插件搞定全部？

- 🎯 **考官意图**：考察对专有向量库与关系型插件性能上限、资源争抢及生态差异的认知。
- 🛡️ **攻防标准应答**：pgvector 适合百万级以内的小型轻量场景，但当数据规模达到千万级以上且并发检索要求高时，pgvector 的 HNSW 索引极其消耗共享内存，会导致 PG 缓存命中率雪崩并严重干扰核心事务处理；此外，Milvus 具备原生的 BM25 稀疏混合索引支持、分布式水平扩展能力与分段压缩机制，能为复杂混合检索提供毫秒级的极速吞吐。
- ⚠️ **避坑要点**：不要贬低 pgvector 毫无用处，而要从规模边界（百万 vs 千万）与事务/检索混合负载的资源争抢角度理性作答。

###### 🎯 追问对决：当文档被管理员删除时，如何保证 PostgreSQL、Redis 缓存和 Milvus 向量索引的一致性？

- 🎯 **考官意图**：考察分布式存储的删除一致性、两阶段提交或补偿机制设计。
- 🛡️ **攻防标准应答**：采用'软删标记 → 异步物理清洗'的两阶段策略：管理员删除时，首先在 PostgreSQL 事务中将文档状态标记为 `DELETED`，此后在线查询立即从 PG 元数据过滤该文档；随后发送异步清理任务，按 doc_id 批量向 Milvus 发送 delete 表达式物理擦除向量实体，最后精准拉取父块 ID 列表执行 Redis DEL 清理，并记录审计日志。
- ⚠️ **避坑要点**：切忌回答'直接在一个同步请求里依次 delete 三个系统'，中间任何一个网络抖动都会导致系统遗留永久脏数据。

###### 🎯 追问对决：DataPilot 的 Event 事件表在长期高频写入下如何做分表或归档？

- 🎯 **考官意图**：考察高并发日志写入、PostgreSQL 分区表设计与冷热数据归档方案。
- 🛡️ **攻防标准应答**：系统对 `run_events` 表采用基于 PostgreSQL Declarative Partitioning 按月份或周进行 Range 分区；对超过 90 天的历史已完成会话，启动后台归档 Worker 将冷数据批量导出至 Parquet 格式转存对象存储（S3），并在主库中 DROP 分区释放物理存储，保持活动事务索引树的高效精简。
- ⚠️ **避坑要点**：不要说'直接在应用层手动拼表名写 SQL'，要提及 PostgreSQL 官方的原生分区表机制与 Parquet 冷归档方案。

##### 🛡️ 系统设计防御边界与权衡 (Anti-Goals / 放弃的假设)

- 🛑 Redis 仅作为易失性缓存，缓存穿透时必须安全回源 PostgreSQL
- 🛑 Milvus 不直接持久化长篇大段原始正文，只保存叶子块索引与标量外键

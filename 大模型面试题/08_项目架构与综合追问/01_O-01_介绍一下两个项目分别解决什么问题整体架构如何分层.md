# O-01: 介绍一下两个项目分别解决什么问题，整体架构如何分层？

- **归属项目**：`两个项目通用` | **题目类型**：`简单题` | **难度等级**：`基础` | **核心主题**：`系统设计, RAG, Agent`
- **可信级别**：项目事实 / 当前代码

> 💡 **一句话速记结论**：
> SuperMew 专注复杂长文档高保真结构化混合检索 RAG，DataPilot 专注异构数据源受控只读分析与代码沙箱出图 Agent。

##### 🎙️ 30 秒高频口答精要 (电梯演讲 / 直击要害)

SuperMew 解决企业复杂非结构化长文档（如跨章节技术规范与带合并单元格的财报附注）在传统固定切分下“上下文截断、表格破碎、多跳证据漏召”的痛点，采用“版面分析解析 → markdown_header_recursive_v1 结构化分块 → BGE-M3 Dense + Milvus BM25 混合检索 → RRF (k=60) 融合 → Qwen3-Reranker-4B 精排 (Top 30 ➔ Top 8) → 溯源引用”全链路；DataPilot 解决企业结构化多源数据（CSV/SQLite/MySQL）在自然语言分析时的“Schema 宽泛、幻觉注入与非受控操作”痛点，基于 FastMCP DataLink 协议，通过“基于 sqlglot AST 的 SQLGuard 语法守卫（只读 SELECT、拦截危险函数、强制 LIMIT 1000）→ 隔离 Docker 安全沙箱（--network none、只读根系统、512MB/15s、非 root 用户）→ FinalMarkdownPayload 结构化交付”构筑端到端安全闭环。两者的核心共性是：绝不信任模型自由发挥，必须由服务端系统契约锁定安全与状态边界。

##### ⏱️ 60~120 秒深度展开 (系统架构 / 机制与推演 / 逐行源码讲解)

SuperMew 与 DataPilot 分别面向非结构化长文档与结构化多数据源，架构分层与契约设计如下：

1. **SuperMew（复杂长文档高保真 RAG）架构分层**：
- **摄取与解析层**：面向 43 份涵盖企业复杂技术白皮书、工业参数规程与财报附注的长文档，先进行版面分析提取高保真 Markdown 与规范表格；
- **结构化分块与索引层**：在 `backend/indexing/document_loader.py` 中实现 `markdown_header_recursive_v1` 策略，按照 H1~H3 标题树递归切分，为每个分块注入标题面包屑元数据（如 `H1 > H2 > H3`），完整保留 Markdown 表格的原子性，避免跨行截断；Dense 向量写入 Milvus（BGE-M3 1024 维），同时构建 Milvus 原生 BM25 稀疏索引；
- **检索与重排层**（`backend/rag/pipeline.py`）：Dense 向量与 BM25 稀疏检索各召回 Top 30，通过倒数排名融合（RRF, $k=60$）合并候选集，再经 `Qwen/Qwen3-Reranker-4B` 交叉注意力精排输出 Top 8 上下文；
- **生成与评估层**：生成模型输入冻结 Prompt，附带精准文档段落角标；在 24 例严格单变量受控靶向分析集上实现证据链完整覆盖率提升 45.83%（8.33% ➔ 54.17%）、回答通过率提升 29.17%（4.17% ➔ 33.33%，净解决 7 题）；在 300 例分析集上稳步提升至 69.33%（净解决 22 题）。

2. **DataPilot（受控只读数据分析 Agent）架构分层**：
- **接入与语义发现层**：FastAPI 提供统一入口，基于 FastMCP DataLink 协议按需拉取数据源（CSV、SQLite、MySQL）的 Schema 快照与字段拓扑，避免宽表全量 prompt 导致上下文溢出；
- **受控调度层**：维护全局单调递增 `seq` 状态机生命周期（`QUEUED ➔ RUNNING ➔ SUCCEEDED / FAILED / TIMED_OUT`），每个执行步骤持久化至 PostgreSQL，驱动前端 SSE 可靠流式推送与断线回放；
- **SQL 执行安全层**（`packages/data_gateway/sql_guard.py`）：调用 `guard_sql`，使用 `sqlglot` 针对 SQLite 与 MySQL 对应方言解析 AST，严格限定只读 SELECT，遍历所有函数节点硬阻断 `_DANGEROUS_FUNCTION_NAMES`（如 `load_file`, `sleep`, `benchmark`, `load_extension`, `read_csv`），并自动注入或收敛 `LIMIT 1000`；
- **代码沙箱隔离层**（`apps/api/application/docker_sandbox.py`）：执行 Python 数据清洗与可视化时，动态拉起严格加固容器（`--network none`, `--memory 512m --memory-swap 512m`, `--cpus 1.0`, 15s CPU / 30s 挂钟超时, `--read-only` 根文件系统, tmpfs `/tmp:rw,noexec,nosuid,size=64m`, `--user 10001:10001`, `--cap-drop ALL`），产物进行 SHA-256 登记回传；
- **交付与呈现层**：终态调用严格遵循 `FinalMarkdownPayload` 契约，输出经安全脱敏的图表与数据结论。

3. **核心代码：DataPilot SQLGuard AST 语法守卫真实实现模式**：
```python
from typing import Literal
import sqlglot
from sqlglot import exp

_DANGEROUS_FUNCTION_NAMES = {
    "load_file", "sleep", "benchmark", "load_extension", "read_csv"
}

def guard_sql(
    sql: str,
    dialect: Literal["sqlite", "mysql"],
    default_limit: int = 1000,
    max_limit: int = 1000
) -> str:
    """通过 sqlglot AST 语法树拦截写操作与危险函数，并强制收敛 LIMIT"""
    try:
        statements = sqlglot.parse(sql, read=dialect)
    except Exception as e:
        raise ValueError(f"SQL 语法解析失败: {e}")
    if len(statements) != 1 or statements[0] is None:
        raise ValueError("安全违规：仅支持单条 SQL 语句执行")
    
    parsed = statements[0]
    # 严格限定只读查询语句 (Select 或 Union)
    if not isinstance(parsed, (exp.Select, exp.Union)):
        raise PermissionError(f"安全拦截：仅允许只读 SELECT 查询，检测到: {type(parsed).__name__}")
    
    # 遍历 AST 检查所有函数调用，杜绝注入
    for func in parsed.find_all(exp.Func):
        func_name = func.sql_name().lower()
        if func_name in _DANGEROUS_FUNCTION_NAMES:
            raise PermissionError(f"安全拦截：禁止调用高危函数 {func_name}")
            
    # 强制注入或修正 LIMIT
    limit_node = parsed.args.get("limit")
    if not limit_node:
        parsed = parsed.limit(default_limit)
    else:
        current_limit = int(limit_node.expression.this)
        if current_limit > max_limit or current_limit <= 0:
            limit_node.expression.set("this", max_limit)
            
    return parsed.sql(dialect=dialect)
```

##### ⭐ 核心关键技术点 (回答骨架)

- ✔️ SuperMew 核心：Markdown 标题树结构分块、保留表格原子性、BGE-M3 + Milvus BM25 混合检索与 Qwen3-Reranker-4B 精排
- ✔️ DataPilot 核心：FastMCP DataLink 语义发现、sqlglot AST 只读与危险函数拦截、Docker 无网加固沙箱、单调 seq 事件落盘
- ✔️ 两者共性原则：模型只做推理与参数建议，执行边界、网络隔离与数据流向全由服务端系统契约硬性锁定

##### ❓ 面试官高频追问预判 (连环问攻防对决)

###### 🎯 追问 1：两个系统的并发策略有何不同？
- 🎯 **考官意图**：考察对无状态检索与有状态 Agent 工具调度并发特性的理解。
- 🛡️ **攻防标准应答**：SuperMew 面向纯只读检索，检索流程无状态副作用，若拆分子查询可安全采用 `asyncio.gather` 并行向 Milvus 与 BM25 发起检索以降低延迟；而 DataPilot 涉及环境交互与工具调用审计，多工具调用间存在前后数据依赖（如先查 Schema 再查 SQL，再将结果喂给 Python 沙箱），必须在调度器中严格串行执行并对齐 `tool_call_id` 与单调递增 `seq`，杜绝竞态破坏审计日志与上下文时序。
- ⚠️ **避坑要点**：切忌回答“都可以随便并发”，Agent 工具调用若无序并发，中间变量传递和状态机回放必然混乱。

###### 🎯 追问 2：两个系统如何对外部模型或微服务不可用做优雅降级？
- 🎯 **考官意图**：考察高可用设计与故障降级兜底方案。
- 🛡️ **攻防标准应答**：SuperMew 中，若 Qwen3-Reranker-4B 微服务超时或不可用，系统自动 Fallback 熔断直接采用 RRF 融合分数截断 Top 8，并在元数据中打上 `rerank_fallback: true` 标记；DataPilot 中，若 DataLink 外部图谱服务超时，降级为直连数据库读取核心 Schema 信息，若 LLM 连续报错，立即将当前步骤标记为 FAILED 并落盘已产生的事件与 Trace，返回前端明确的错误码与重试建议，避免前端无限等待。
- ⚠️ **避坑要点**：必须说明系统自动兜底（如熔断回退、元数据标记）而不是让异常裸抛给用户。

###### 🎯 追问 3：如果给系统做多租户扩展，两个系统分别最先重构哪个模块？
- 🎯 **考官意图**：考察多租户数据隔离与系统扩展演进设计。
- 🛡️ **攻防标准应答**：SuperMew 最先重构 Milvus Collection 分区与标量过滤，为每个租户建立专属 Partition 或在向量 metadata 中强制注入 `tenant_id` 过滤表达式，杜绝知识库越权；DataPilot 最先重构数据源连接池与 Docker 沙箱资源池，确保租户的数据库凭证在独立 KMS 隔离解密，沙箱容器挂载完全隔离的只读卷并销毁临时文件，防止跨租户数据残留。
- ⚠️ **避坑要点**：切忌回答“只在前端加租户 ID”，后端存储与容器隔离必须有物理级的鉴权与隔离边界。

##### 🛡️ 系统设计防御边界与权衡 (Anti-Goals / 放弃的假设)

- 🛑 SuperMew 面向低频更新的静态技术与财务规范，未实现跨存储分布式两阶段事务
- 🛑 DataPilot 定位于受控只读分析系统，坚决不支持写操作（DML/DDL）与多表跨库变更

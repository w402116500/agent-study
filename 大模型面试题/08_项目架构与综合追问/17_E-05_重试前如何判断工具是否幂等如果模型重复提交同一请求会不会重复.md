# E-05: 重试前如何判断工具是否幂等？如果模型重复提交同一请求，会不会重复写入或重复计费？

- **归属项目**：`两个项目通用` | **题目类型**：`深挖题` | **难度等级**：`进阶` | **核心主题**：`幂等性, 并发控制, 防重机制, 计费安全`
- **可信级别**：项目事实 / 架构设计

> 💡 **一句话速记结论**：
> 只读工具天然幂等；写与计费工具通过业务唯一幂等键加 Redis 分布式锁，配合只读快照从源头消灭重复副作用。

##### 🎙️ 30 秒高频口答精要 (电梯演讲 / 直击要害)

判断工具幂等的关键是看'该操作是否具有状态变更或外部副作用'。只读查询天然幂等，可安全重试；任何涉及写库、外部 API 调用或按次计费的操作都是非幂等的。为了防止模型因网络抖动或自身幻觉重复发起同一请求，系统必须实施两道防线：第一，针对每个敏感操作由前端或会话层生成唯一幂等键（Idempotency Key），在 Redis 中通过 `SETNX` 加锁并缓存执行结果，重复请求直接返回历史缓存；第二，在 DataPilot 项目中，所有分析工具均设计为在只读副本或本地 DuckDB 快照上执行，物理上没有写操作，天然消除了重复写入脏数据的风险！

##### ⏱️ 60~120 秒深度展开 (系统架构 / 机制与推演 / 逐行源码讲解)

工具调用幂等性设计与防重复写入、重复计费机制：
1. **幂等判定与真实业务场景**：
- **只读查询工具天然幂等**：如检索财报 `search_docs` 或只读 SQL `run_sql_query`，多次执行只产生只读开销，不会篡改业务物理状态。
- **有副作用的工具绝非天然幂等**：如 DataPilot 中的“导出分析报表并落盘持久化”、“调用计费推理 API”或“执行临时视图创建”。如果模型在重试时重复下发相同请求，极易引发文件覆写冲突或重复扣除账户额度。

2. **核心代码：基于业务参数哈希与 Redis 分布式锁的幂等守卫**：

```python
import hashlib
import json
import redis
from typing import Dict, Any

class IdempotentToolGuard:
    def __init__(self, redis_client: redis.Redis):
        self.r = redis_client

    def generate_idempotency_key(self, session_id: str, tool_name: str, args: dict) -> str:
        # 1. 规范化参数序列化，对字典键排序后计算 SHA256 指纹
        sorted_args = json.dumps(args, sort_keys=True, ensure_ascii=False)
        args_hash = hashlib.sha256(sorted_args.encode('utf-8')).hexdigest()
        return f"idempotent:{session_id}:{tool_name}:{args_hash}"

    def execute_with_guard(self, session_id: str, tool_name: str, args: dict, tool_func):
        key = self.generate_idempotency_key(session_id, tool_name, args)
        
        # 2. Redis 原子 setnx 分布式防重锁 (锁定 60 秒)
        acquired = self.r.set(key, "PROCESSING", nx=True, ex=60)
        if not acquired:
            cached_val = self.r.get(key)
            if cached_val == b"PROCESSING":
                raise RuntimeError("相同请求正在并发执行中，请勿重复提交！")
            # 若已有计算完成的结果，直接幂等返回历史缓存，杜绝二次物理执行
            return json.loads(cached_val.decode('utf-8'))

        try:
            # 3. 首次执行真实工具
            result = tool_func(args)
            # 执行成功后缓存结果，保留 10 分钟以供重试直接命中
            self.r.set(key, json.dumps(result, ensure_ascii=False), ex=600)
            return result
        except Exception as e:
            # 失败时及时删除正在处理的锁标记，允许重试
            self.r.delete(key)
            raise e
```

3. **两阶段提交与防计费漏洞**：
- **扣费前置预占与后置核销（Two-Phase Reservation）**：调用外部昂贵商业 API（如大模型生成深度图表）时，先扣除预占冻结额度并记录 `tx_id`，工具成功后核销，失败则自动释放；
- **只读连接池强制隔离**：在数据库层面，为 Agent 分配具备 `default_transaction_read_only = on` 的专用只读账户，哪怕模型生成了 `INSERT` 或 `UPDATE`，在数据库引擎内核级直接拒绝执行，从源头消灭重复写入风险。

##### ⭐ 核心关键技术点 (回答骨架)

- ✔️ 只读查询天然幂等可重试；写操作与扣费操作必须通过 SHA-256 复合幂等键防重
- ✔️ 使用 Redis 分布式锁与状态缓存（EXECUTING / COMPLETED）实现重复调用的透明拦截与结果重放
- ✔️ DataPilot 通过只读数据库连接与只读快照挂载，从架构根源切断重复写脏数据的可能

##### ❓ 面试官高频追问预判 (连环问攻防对决)

###### 🎯 追问对决：如果一个外部第三方工具本身不支持幂等键机制，Agent 这一侧该如何做两阶段状态确认？

- 🎯 **考官意图**：考察对第三方无状态/非幂等服务的外部包装与补偿事务机制。
- 🛡️ **攻防标准应答**：实施【本端查询预检 + 补偿确认机制（Pre-Check & Compensating Workflow）】：在真正发起写调用前，先通过具备唯一标识（如订单号或批次号）的只读接口向第三方查询是否存在已处理记录；若不存在，才发起写操作；若发生网络超时，严禁盲目重试，必须进入异步探针轮询其只读状态，确认未成功再重试，确认已成功则直接提取已有结果，避免重复创建。
- ⚠️ **避坑要点**：不要回答‘直接用 try-except 重试 3 次’，对非幂等第三方无脑重试会导致严重的重复扣费或数据重复。

###### 🎯 追问对决：当大模型在多步推理中把原本单次调用的任务自行拆解成 5 个微调任务时，幂等锁如何感知语义层面的重复？

- 🎯 **考官意图**：考察高级 Agent 的语义层幂等与冗余调用合并。
- 🛡️ **攻防标准应答**：引入【语义向量/规范化 AST 缓存层】：不仅对参数做字面哈希，对于 SQL 类的工具，先经过 sqlglot 解析为规范化 AST，消除无意义的空格、注释与别名差异；对于自然语言检索，通过 Embedding 计算 Query 语义相似度。若与 60 秒内刚执行过的查询余弦相似度 > 0.98 且数据源未变更，直接复用前序结果，拦截多步拆解带来的语义级冗余调用。
- ⚠️ **避坑要点**：字面哈希只能防一模一样的字符串，SQL 稍加空格或大小写就会绕过字面哈希，必须上 AST 规范化。

##### 🛡️ 系统设计防御边界与权衡 (Anti-Goals / 放弃的假设)

- 🛑 幂等键依赖于参数哈希，如果模型每次生成的参数存在微小的空字符或字段排序差异，需先做参数正规化（Canonicalization）
- 🛑 Redis 幂等记录必须设置合理的 TTL 过期时间，避免占用无限制内存

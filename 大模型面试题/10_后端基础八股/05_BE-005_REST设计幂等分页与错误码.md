# BE-005: REST API 怎样设计创建任务、幂等、分页与错误码？

#### 简要回答

接口应该围绕明确资源与状态设计。耗时分析可以返回 RunID，让查询、订阅和取消分别操作该资源；重复提交需要定义幂等行为，列表分页需要稳定顺序。类型校验、业务冲突、权限拒绝与内部失败应保留不同错误语义，不能都返回 200 加一句报错。


#### 详细解析


##### 1. 1. 资源与运行生命周期

同步创建请求不必等待分析全完成，可先创建持久 Run，再由执行器运行，客户端通过 RunID 读取状态与事件。取消本身是状态转换请求，需定义对已完成 Run 的行为。这里能看到 DataPilot 存在 Run 资源，不代表已有完整幂等键方案；是否重复点击创建两次需看创建入口。


##### 2. 2. 幂等如何落到存储

HTTP 方法的语义不能代替后端幂等实现。对于 POST 创建，可定义请求幂等键与参数摘要，在唯一约束下复用同一结果；同键不同参数应冲突，而不是误复用。客户端超时后先查询状态也能减少盲目重发。幂等记录的作用域、有效期与最终结果保存都必须明确。


##### 3. 3. 分页与错误契约

事件历史和文档列表需要确定排序，例如时间加唯一 ID，避免同时间记录分页遗漏。游标适合持续追加流，offset 简单但数据变化会造成重复或遗漏。错误返回保留稳定代码与可理解说明，内部 Trace 和密钥不应原样外泄。前端才可区分可修正输入、需要重试和应停止的错误。


#### 面试总结

- 资源 ID 连接请求与后台任务
- 幂等必须有存储约束
- 分页顺序需稳定
- 错误契约服务前端决策


#### 递进追问与参考答案


**追问 1：唯一约束冲突直接重试就好吗？**

应先确定冲突含义。若是同一个幂等键，可读取已创建资源；若同键参数不同，应明确拒绝。无差别换 ID 重试会绕过幂等意图并创建重复任务。事务失败后还需先回滚。


**追问 2：取消接口可以重复调用吗？**

应该定义重复调用语义：已经取消可返回当前终态，已完成则说明不能再取消。底层清理也应可重复，不因容器已不存在再次失败。具体项目是否完全做到要沿取消与 Finalizer 验证，不能只从方法名推导。

# BE-001: FastAPI 如何处理 async def 与同步 def？同步 SDK 怎么避免阻塞？

- **归属模块**：`后端与部署` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：PY-11：FastAPI 如何处理 async def 与同步 def 路由？Docker 沙箱/同步 SDK 任务怎样避免阻塞事件循环？

对应简历：熟悉 FastAPI；Python 异步编程


#### 简要回答

FastAPI 的 async 路由直接在事件循环中运行，同步 def 路由和依赖由线程池执行。async 路由里手动调用普通同步函数不会被自动卸载，因此应检查真实 SDK，优先异步客户端，必要时受限线程或进程执行。RAG 当前关系库与 Redis 封装是同步的，不能把服务描述成所有 I/O 全异步。


#### 详细解析


##### 1. 1. 框架边界与普通函数边界

路由和 Depends 是框架掌握的调用位置，FastAPI 可以根据函数类型安排执行；普通 helper 是用户直接调用的函数，框架不会自动识别里面有阻塞 I/O。把同步数据库函数放进 async 路由，只改变外层声明，不改变驱动等待方式。需要看调用链最底层是 await、同步网络还是 CPU 计算。


##### 2. 2. 三种处理方式的取舍

如果客户端支持异步，可使用原生 await；如果只有同步 API，可将完整同步工作单元卸载到有限线程；纯 Python 重计算可独立进程。线程会引入排队与上下文传播问题，会话也不能随意跨线程共享。不能只把最后一条 db.query 移到线程，却让 Session 在不同线程之间交替使用。


##### 3. 3. 如何证明修改有效

同时发一个慢依赖请求和一个轻量请求，记录轻量请求延迟、SSE 心跳与线程池排队，而非只看慢请求的总时间。DataPilot 沙箱使用异步子进程读取与有限超时，可作为另一种等待外部程序的例子。部署 Worker 数与数据库连接总量也需一起预算；更多 Worker 不会自动消除外部服务瓶颈。


#### 面试总结

- 同步 helper 不自动进线程池
- 完整工作单元明确执行环境
- 异步子进程适合程序等待
- 用事件循环延迟验证


#### 递进追问与参考答案


**追问 1：改成 def 路由就全解决了吗？**

只解决该路由占用事件循环的部分问题。线程池容量仍有限，同步调用需要超时，CPU 工作仍可能受 GIL 限制。也不能把需要异步流式等待的逻辑机械改为同步；应根据调用链选择执行模型并限制负载。


**追问 2：提高 Worker 数要注意什么？**

每个进程会有独立内存、连接池和模型客户端，数据库连接总量可能成倍增长。进程内 Task、锁、队列也不会自动共享。应确认业务状态可跨进程持久访问，再按内存、连接容量和实际吞吐设 Worker 数。

# BE-002: SSE 如何实现流式响应？断线补发与用户取消分别在哪一层处理？

- **归属模块**：`后端与部署` | **优先级**：`P0` | **性质**：`当前实现` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：PY-06：FastAPI 如何通过 StreamingResponse 暴露 SSE？事件先落库、断线补发和客户端取消分别在哪一层处理？

对应简历：SSE；断线补发；历史回放


#### 简要回答

SSE 是长连接上的事件流，响应生成器持续编码事件。DataPilot 把 Run 生命周期与订阅分开，提供事件流和历史查询；断线补发需要持久事件、顺序游标和客户端去重，用户取消则是独立业务动作。RAG 的流式队列不能直接被说成拥有同样的持久回放。


#### 详细解析


##### 1. 1. 流式协议需要哪些契约

一次响应可以发送多条事件，事件类型、数据结构、序号与终止条件应稳定。心跳维持链路可见性，但不代表任务还在正常推进。浏览器断开、代理缓冲与中间层空闲超时会影响体验，服务端 yield 也不意味着客户端立即显示，应记录首包和实际到达间隔。


##### 2. 2. 订阅与任务状态分离

前端订阅只负责接收，Run 执行负责产生事件；断线后任务是否继续属于产品与运行时策略。补发应从客户端已处理的游标之后读取，并处理实时事件与历史交接时的竞争。网络只提供重复或丢失的可能，客户端用稳定事件 ID 去重，不能承诺发送一次就消费一次。


##### 3. 3. 对照当前项目

DataPilot routes/runs.py 有流式订阅、取消和事件列表接口，对应简历的流式、历史回放与取消能力。RAG service.py 使用请求 worker 与队列，把模型输出转成流；它的请求取消规则需独立解释。两套实现不能混用，尤其不能把 DataPilot 的持久事件机制归到 RAG。


#### 面试总结

- SSE 编码与业务任务分离
- 游标与去重支持补发
- 断连不等同取消
- 两项目回放能力分别核验


#### 递进追问与参考答案


**追问 1：代理缓冲导致整段一起到达怎么查？**

比较后端生成时间、代理到达时间和前端接收时间；若后端逐步生成而客户端成批收到，检查代理缓冲、压缩、超时与转发配置。对 SSE 路径采用相应配置后再验证，不能只凭前端表现归因模型慢。


**追问 2：事件发送后进程崩溃会怎样？**

取决于事件是否持久提交与任务状态是否收敛。若先落库再发布，客户端可从持久记录补发；仍需处理已落库但未发布与重复发布。运行中的内存 Task 不会因存在事件表就自动重启恢复，恢复执行需要另一个机制。

# BE-003: 如何设计外部服务超时、重试与熔断，避免一次请求无限等待？

- **归属模块**：`后端与部署` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：原题库超时、工具异常与服务稳定性相关题；新增统一预算展开

对应简历：调用次数、超时与同类失败断路器


#### 简要回答

应把排队、连接、读取、单步与整体请求预算分别定义，再由整体截止时间约束各阶段。只有可恢复且满足幂等条件的操作才有限重试，并加退避与抖动。参数、安全和版本错误不靠重试掩盖；连续同类故障要断路或降级，保持错误可追踪。


#### 详细解析


##### 1. 1. 超时并不是单个数字

模型 API 可能连接快但首 token 慢，SQL 可能连接等待长但执行快，沙箱还涉及启动与清理。只设读取超时会遗漏排队；每阶段重新给全额时间又会使总请求超预算。使用单调时钟管理整体截止时间，进入下一阶段时只分配剩余预算，清理另有有限时间。


##### 2. 2. 重试为何需要幂等和分类

网络失败可能发生在服务已完成写入、响应未到达之后，盲目重发可能重复创建任务或重复写数据。查询可以相对容易重试，入库与创建 Run 需要幂等标识或状态查询。指数退避加抖动减少同时恢复的冲击，但不是放大故障的无限循环。每次失败记录原因、尝试次数与最终收尾状态。


##### 3. 3. 项目对应与回答边界

DataPilot 简历明确提到工具调用次数、超时与同类失败断路器；DataLink 暂时不可用允许精确版本缓存再 Schema-only，而参数、安全、版本不匹配不能静默降级。这里统一预算与重试设计是方法，不应自动说全部 SDK 具备完备熔断实现。具体需检查实际调用和异常映射。


#### 面试总结

- 整体预算覆盖排队与执行
- 可恢复错误才有限重试
- 有副作用操作先看幂等
- 降级不能掩盖安全与版本错误


#### 递进追问与参考答案


**追问 1：模型 429 是否立刻重试？**

不宜立刻循环。遵守服务返回的重试提示，减少并发，有限退避并观察剩余预算。如果仍持续限流，应排队、切换经允许的配置或明确失败，避免重试风暴和额外成本。还应统计初次请求与重试次数。


**追问 2：查询只读就一定可以安全重试吗？**

也需要考虑读一致性和成本。底层数据在两次读取之间可能变化，查询可能耗费大量资源，锁定读取也并非普通无副作用查询。应固定必要版本、说明数据时点，并限制次数；只读权限不代表无限重试没有风险。

- 沙箱剩余预算：`E:/mystudy/Data-Agent/DataPilot/apps/api/application/docker_sandbox.py`（第 208 行）

# BE-004: SQLAlchemy Engine、连接池和 Session 有什么区别？连接池耗尽如何排查？

- **归属模块**：`后端与部署` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：PY-08：数据库会话生命周期；新增连接池耗尽专题

对应简历：SQLAlchemy


#### 简要回答

Engine 管理驱动与连接池，Session 管理业务事务和对象状态，Session 工厂只是创建入口。连接池复用连接降低建连开销，但长事务和未关闭会话会占住连接。排查应分清借连接等待、SQL 执行和事务空闲，核对所有进程的连接预算，而不是只增大 pool_size。


#### 详细解析


##### 1. 1. 连接是怎样被占用的

Session 并不一定创建时就借出连接，执行数据库操作后通常会在事务范围内占用。commit、rollback 或 close 的时机会影响归还。若持有事务期间去等待几十秒模型 API，连接虽未执行 SQL 仍可能不能给其他请求使用。应尽量先读取必要数据、结束数据库事务，再进入长外部调用。


##### 2. 2. 容量与故障不是一个问题

总连接需求近似与每进程池上限、进程数和其他服务有关，还要给运维留空间。增大池可能缓解正常突发，也可能使数据库承受更多同时查询。pool_pre_ping 能借出前检查失效连接，但不解决慢 SQL、业务锁和会话泄漏，也不能保证正在执行时连接永不掉线。


##### 3. 3. 当前实现与排查路径

RAG Engine 设置 pool_pre_ping，并用 SessionLocal 创建同步会话；DataPilot Run 有自己的异步会话工厂。先测连接获取耗时、执行时间和事务长度，再看数据库活动会话、等待锁与异常路径关闭。未做真实容量测量时不能给出“项目支持某 QPS”或把默认池大小说成优化结果。


#### 面试总结

- Engine 与 Session 职责不同
- 等待外部模型时避免占事务
- 总连接预算跨进程计算
- pre_ping 不解决连接泄漏


#### 递进追问与参考答案


**追问 1：为什么不能全局一个 Session？**

它是有状态对象，事务、待提交修改和对象缓存会被不同请求混用。一个请求回滚可能影响另一个请求，且并发访问不安全。Engine 可以复用，Session 应按明确业务工作单元创建并结束。


**追问 2：连接池超时都说明泄漏吗？**

不一定，可能是正常峰值超容量、慢 SQL、长事务、锁等待或数据库故障。先看连接使用和归还曲线及查询时间；若任务结束后占用不降再查泄漏，若都在执行慢查询应优化查询或限流。

- Run 独立会话：`E:/mystudy/Data-Agent/DataPilot/apps/api/runtime/run_executor.py`（第 30 行）

# BE-005: REST API 怎样设计创建任务、幂等、分页与错误码？

- **归属模块**：`后端与部署` | **优先级**：`P0` | **性质**：`方案讨论` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：新增：简历 REST API 能力专项

对应简历：REST API


#### 简要回答

接口应该围绕明确资源与状态设计。耗时分析可以返回 RunID，让查询、订阅和取消分别操作该资源；重复提交需要定义幂等行为，列表分页需要稳定顺序。类型校验、业务冲突、权限拒绝与内部失败应保留不同错误语义，不能都返回 200 加一句报错。


#### 详细解析


##### 1. 1. 资源与运行生命周期

同步创建请求不必等待分析全完成，可先创建持久 Run，再由执行器运行，客户端通过 RunID 读取状态与事件。取消本身是状态转换请求，需定义对已完成 Run 的行为。这里能看到 DataPilot 存在 Run 资源，不代表已有完整幂等键方案；是否重复点击创建两次需看创建入口。


##### 2. 2. 幂等如何落到存储

HTTP 方法的语义不能代替后端幂等实现。对于 POST 创建，可定义请求幂等键与参数摘要，在唯一约束下复用同一结果；同键不同参数应冲突，而不是误复用。客户端超时后先查询状态也能减少盲目重发。幂等记录的作用域、有效期与最终结果保存都必须明确。


##### 3. 3. 分页与错误契约

事件历史和文档列表需要确定排序，例如时间加唯一 ID，避免同时间记录分页遗漏。游标适合持续追加流，offset 简单但数据变化会造成重复或遗漏。错误返回保留稳定代码与可理解说明，内部 Trace 和密钥不应原样外泄。前端才可区分可修正输入、需要重试和应停止的错误。


#### 面试总结

- 资源 ID 连接请求与后台任务
- 幂等必须有存储约束
- 分页顺序需稳定
- 错误契约服务前端决策


#### 递进追问与参考答案


**追问 1：唯一约束冲突直接重试就好吗？**

应先确定冲突含义。若是同一个幂等键，可读取已创建资源；若同键参数不同，应明确拒绝。无差别换 ID 重试会绕过幂等意图并创建重复任务。事务失败后还需先回滚。


**追问 2：取消接口可以重复调用吗？**

应该定义重复调用语义：已经取消可返回当前终态，已完成则说明不能再取消。底层清理也应可重复，不因容器已不存在再次失败。具体项目是否完全做到要沿取消与 Finalizer 验证，不能只从方法名推导。

# BE-006: 日志、健康检查和部署故障排查如何贯穿一个 Agent 请求？

- **归属模块**：`后端与部署` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：原题库：如何将前端一次点击、后端 SSE、多次 Tool Call 与 Docker 沙箱日志串联？

对应简历：Docker 部署；历史回放


#### 简要回答

用请求、Run 与工具调用 ID 关联关键阶段，记录耗时、错误类别、版本和终态，避免只堆一长串模型文本。部署排查从进程、网络、依赖、业务链路逐层定位；健康检查要区分进程活着与依赖可用。公网演示能证明可体验，不能自动证明生产高并发或多租户能力。


#### 详细解析


##### 1. 1. 关联信息为何比全文日志重要

一次分析会跨 HTTP、后台 Task、SQL、模型和容器，只有时间接近的日志很难准确关联。每阶段保留 RunID、tool_call_id、数据源与版本，加上开始、结束和耗时，才能解释“慢在等待还是执行”。原始 SQL、模型输入和路径还可能含敏感信息，应控制日志可见范围与保留期。


##### 2. 2. 可用性的分层检查

端口能连只说明网络到进程，healthcheck 通过可能只说明 Redis ping 或数据库连接。服务就绪还要看配置、集合、模型与业务链路，但不能每几秒跑昂贵完整 Agent。可将轻量存活检查、依赖就绪检查与低频代表性业务探针分开，并为失败给出稳定状态。


##### 3. 3. 当前项目可以怎么讲

RAG Compose 有 Redis 等依赖健康检查；DataPilot 有 Run 历史、工具调用和 SQL 审计接口，便于围绕 Run 回溯。故障处理可以从浏览器请求是否到达、反向代理、应用日志、数据库/模型依赖与沙箱逐层查。没有具体事故记录时只描述排查方法，不编造企业线上故障、SLA 或压测结论。


#### 面试总结

- 关联 ID 串起多阶段
- 日志需控制敏感内容
- 存活与就绪检查区分
- 部署文件不证明容量


#### 递进追问与参考答案


**追问 1：接口正常但回答很慢，先加机器吗？**

先拆耗时：入口排队、规划、模型、检索、重排、数据库和输出分别测。若模型远端慢，加本机资源帮助有限；若连接等待或 CPU 满才考虑容量与卸载。没有阶段数据时扩容容易增加成本却不改变瓶颈。


**追问 2：记录完整 Prompt 是否最方便排查？**

方便但有泄漏与存储成本。优先记录摘要、长度、版本、错误码和证据 ID，必要时在受控诊断模式保存内容并设置访问与期限。不能把所有用户数据默认公开到日志或直接返回前端异常堆栈。

# DB-001: B+ 树索引为什么能加速查询？为什么索引越多并不一定越好？

- **归属模块**：`数据库与 SQL` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：新增：数据库基础与项目 SQL 能力展开

对应简历：数据库开发与 SQLAlchemy


#### 简要回答

索引维护按键组织的数据结构，让数据库减少需要访问的记录；常见 B+ 树适合等值、范围与有序扫描。但是否更快取决于选择性、回表、排序和数据分布，索引还增加写入和存储成本。应围绕实际查询设计并看执行计划，不把每列都建索引当优化。


#### 详细解析


##### 1. 1. 从全表扫描到缩小访问范围

全表扫描要检查大量记录，索引可先定位符合键条件的范围。树高较小和节点容纳多键帮助减少层级访问，叶子有序也便于范围遍历。索引找到的记录可能还要访问表中其余字段，选择大量行时这些回表成本会抵消收益，所以优化器选择全表扫描并不一定错误。


##### 2. 2. 索引不是免费副本

插入、更新和删除都要维护相应索引，宽键会占更多空间，缓存能容纳的索引页变少。低选择性状态列单独建索引未必划算，但结合租户、时间或排序可能有效。数据库引擎的物理组织不同，例如 InnoDB 主键聚簇索引与 PostgreSQL 堆表不能完全套用同一个“回表”解释。


##### 3. 3. 在项目里怎样回答

RAG 父块按 ID 查询、聊天记录按会话和顺序读取，可从访问模式推导候选索引；是否已建哪些索引要核对模型与迁移。DataPilot 查询远程用户库不能随意替用户建索引，应输出诊断与建议并保留只读权限。没有实测数据不写“加索引性能提升几十倍”。


#### 面试总结

- 索引通过减少访问量提速
- 选择性与回表决定收益
- 写入维护有成本
- 建议索引不冒称已经优化


#### 递进追问与参考答案


**追问 1：为什么查询很多行时全表扫描可能更快？**

大部分数据都需要读时，连续扫描可能比通过索引逐行随机访问更便宜。应看实际行数、缓存和输出字段，而不是见到 Seq Scan 或 ALL 就断言索引失效。最终比较实际执行与 I/O 成本。


**追问 2：覆盖索引一定不读表吗？**

不应跨数据库绝对化。InnoDB 的覆盖查询与 PostgreSQL index-only scan 的可见性检查机制不同，后者可能仍需要访问堆。还要考虑索引是否包含全部输出、过滤与可见性条件，用计划核验。

# DB-002: 联合索引如何设计？最左前缀、范围条件与排序如何一起考虑？

- **归属模块**：`数据库与 SQL` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：新增：数据库基础与项目 SQL 能力展开

对应简历：SQL 查询与数据库开发


#### 简要回答

联合索引按多个键的顺序组织，常见 B 树利用左侧前缀缩小范围。设计应结合等值过滤、范围、排序与输出，而不是死记某一种排序公式。范围后面的列可能仍参与过滤、覆盖或其他优化，不能一概说完全失效；MySQL 与 PostgreSQL 应分别看计划与版本。


#### 详细解析


##### 1. 1. 为什么列顺序影响访问

假设查询按 session_id 过滤再按序号读取消息，索引(session_id,seq)能先找到会话区间并保持序号顺序。倒过来以 seq 为首键，通常不能同样有效地缩小某会话的区间。联合索引类似先按第一列分组再按下一列排序，不是把多列单列索引简单叠加。


##### 2. 2. 范围和排序的细节

索引(user_id,created_at,id)面对 user_id 等值与时间范围，可以利用相应有序区间；ORDER BY 是否免排序要看方向、过滤与键顺序。遇到范围并不意味着后续键不再有任何价值，它可能减少索引内过滤成本或支持覆盖。优化器也可能使用其他路径，应避免把教材规则说成所有版本永恒限制。


##### 3. 3. 如何把方案变成证据

选代表性高频查询与真实分布，比较候选索引的估算和实际行数、排序、缓存访问及写入代价。模型中一个字段标了 index=True 不等于全部组合访问已覆盖。对远程 MySQL，只读 Agent 可以分析执行信息或给建议，但实际修改索引必须是独立授权的管理操作。


#### 面试总结

- 联合键顺序影响范围定位
- 排序需要与过滤共同分析
- 范围后列不等于无任何价值
- 计划与真实分布验证


#### 递进追问与参考答案


**追问 1：where 条件书写顺序决定联合索引吗？**

通常由优化器根据谓词与索引结构分析，不是 SQL 文本把哪个条件写前面就决定用哪列。真正影响的是索引列顺序、谓词形式和数据分布。不要把改变 AND 顺序当主要优化。


**追问 2：索引(a,b)能否查 b？**

不能简单用“绝对不能”。它可能被完整扫描、用于覆盖，某些版本还存在特定优化；但通常不能获得与以 b 开头索引相同的精准范围收益。回答应区分是否使用索引与是否有效缩小扫描。

# DB-003: 为什么建了索引查询仍然慢？哪些谓词和数据分布会影响计划？

- **归属模块**：`数据库与 SQL` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：新增：数据库基础与项目 SQL 能力展开

对应简历：SQL 只读校验；取数分析


#### 简要回答

建索引不保证访问路径有效。函数计算、隐式转换、前导通配符、低选择性和统计信息偏差都可能影响范围定位；查询返回大量行、排序、JOIN 放大或锁等待也会慢。需要检查计划和实际耗时阶段，而不是把所有慢查询归为“索引失效”。


#### 详细解析


##### 1. 1. 谓词能否映射到索引范围

对时间列直接使用日期函数，可能让普通索引难以形成范围，可考虑改写为开始与结束边界；但表达式索引等机制需按具体数据库分析。字符串与数字比较还可能引入隐式转换，参数类型应与字段一致。前导百分号模糊匹配通常不适合普通 B 树前缀定位，全文检索又是另一种工具。


##### 2. 2. 计划正确也可能仍很慢

如果过滤后要输出几百万行，索引只能帮助定位，不能消除网络传输和序列化。重复 JOIN、宽 SELECT *、排序落盘与大 OFFSET 也会增加成本。统计信息不准确会使估算偏差，选择错误 JOIN 顺序；索引本身存在不等于优化器有正确的分布认知。


##### 3. 3. Agent 的 SQL 应怎样诊断

DataPilot SQL 安全通过，只说明符合当前限制，不证明查询高效。应分别看执行时间、返回规模、输出限制与关联基数。生成 LIMIT 能限制最终行数，却可能不能减少聚合前扫描；必要时提示用户收窄时间与字段。回答中的优化建议应能解释改变了哪个成本，避免堆一组无关索引口诀。


#### 面试总结

- 谓词形式影响范围定位
- 统计偏差影响计划
- LIMIT 不保证扫描少
- 安全通过与性能分开


#### 递进追问与参考答案


**追问 1：查询加 LIMIT 100 就不会拖垮库了吗？**

不一定。SUM、GROUP BY、排序或复杂 JOIN 可能先处理大量数据再返回100行。还需要执行预算、扫描范围、数据库超时与连接容量，必要时禁止或提示高成本路径。只读也会消耗资源。


**追问 2：要不要直接强制使用某索引？**

先查统计、谓词与数据分布。强制提示可能改善一个样本却在另一分布恶化，并增加维护成本。应比较代表性输入和实际计划后再决定，不能把 Hint 当通用第一步。

# DB-004: EXPLAIN 和 EXPLAIN ANALYZE 有什么区别？怎样从执行计划定位慢 SQL？

- **归属模块**：`数据库与 SQL` | **优先级**：`P0` | **性质**：`方案讨论` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：新增：数据库基础与项目 SQL 能力展开

对应简历：数据库与 SQL 能力


#### 简要回答

EXPLAIN 主要展示优化器估算的计划，ANALYZE 会真实执行并展示实际耗时、行数与循环次数。排查时沿节点找估算与实际偏差、重复循环、过滤量和排序/缓存成本。ANALYZE 有真实负载甚至副作用，应该对允许的语句和环境使用，不能作为无成本安全检查。


#### 详细解析


##### 1. 1. 估算与真实执行的区别

估算 cost 是优化器模型值，不应直接当作毫秒；rows 表示估计输出规模。实际计划包含真实行数与次数，一处实际行数远超估算，可能导致 JOIN 策略与内存预算不合适。节点时间可能包含子节点工作，不可将所有时间简单相加形成总耗时。不同数据库的输出字段和节点名称也不同。


##### 2. 2. 怎么阅读而非只背字段

先看整体返回规模，再从输入节点看是否大量扫描与过滤；观察 JOIN 内侧 loops 是否巨大、排序是否发生额外 I/O。PostgreSQL 可以用 BUFFERS 辅助理解缓存命中与访问。MySQL8 的实际计划也能展示扫描、哈希 JOIN 等行为。定位后提出有因果的改写、索引或统计建议，再用相同数据对照。


##### 3. 3. 在受控分析项目中的边界

DataPilot 当前只读网关不意味着自动允许所有诊断命令，具体 AST 白名单要另查。拿生产库执行 ANALYZE 也可能产生长查询负载；应由受控诊断入口、限时与明确权限承担。此题训练的是数据库诊断能力，没有材料时不说项目已经自动分析全部执行计划。


#### 面试总结

- cost 不是耗时毫秒
- ANALYZE 真实执行
- actual rows 与 loops 联看
- 诊断也需权限与预算


#### 递进追问与参考答案


**追问 1：估算行数不准有什么后果？**

可能错误选择 JOIN 次序、扫描方式和内存策略，导致循环或排序量放大。检查统计更新、关联分布与谓词复杂度，再考虑相应统计或查询改写，不能仅补一条索引。


**追问 2：EXPLAIN ANALYZE 能随意用于 UPDATE 吗？**

不能，支持时它会执行语句并可能改变数据、触发函数或造成锁等待。需要合适测试环境和事务控制，且不能忽视外部副作用。只读 Agent 更不应绕过安全策略去执行写语句诊断。

- PostgreSQL 16 官方：执行计划：`https://www.postgresql.org/docs/16/using-explain.html`
- MySQL8 官方 EXPLAIN：`https://dev.mysql.com/doc/refman/8.0/en/explain.html`

# DB-005: 事务 ACID 和隔离级别分别解决什么问题？什么时候需要重试整个事务？

- **归属模块**：`数据库与 SQL` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：新增：数据库基础与项目 SQL 能力展开

对应简历：SQLAlchemy；文档替换保护


#### 简要回答

事务把相关数据库操作组成一个提交单元，ACID 分别讨论原子性、一致性约束、隔离与持久性。隔离级别影响并发读写允许的现象，不是越高就绝对越好。发生死锁或序列化失败时，一般在回滚后有限重试完整业务事务；数据库事务不自动覆盖 Redis、Milvus 或模型 API。


#### 详细解析


##### 1. 1. 原子性必须有明确范围

例如写入父块记录与同库文档状态，可放同一数据库事务，使成功一起提交、异常一起回滚。数据库的“一致性”依赖约束和应用逻辑共同维护，不能自动识别金额是否按正确业务口径计算。Durability 还要对应数据库与存储配置，不能泛化成任何故障下绝不丢失。


##### 2. 2. 隔离不是固定背诵顺序

Read Committed、Repeatable Read 与 Serializable 等名称需要结合数据库实现。读到哪个版本、范围锁、序列化检测可能不同。更强隔离通常增加冲突与重试；普通读取和更新业务也应分别考虑。请求里等待模型时维持长事务会增加连接与版本保留成本。


##### 3. 3. 项目里最容易被追问的边界

RAG 文档涉及关系库、向量库与缓存，SQL commit 不会让另外两种存储自动一起回滚。DataPilot 固定 Schema/graph 版本也不冻结远端表数据。需要明确事务覆盖范围，说明跨库一致性是通过版本、状态机、补偿或重试管理的另一个问题，不以“用了 SQLAlchemy”推导完全一致。


#### 面试总结

- 事务范围限于参与资源
- 隔离实现按数据库区分
- 失败先回滚再有限重试
- 模型等待避免长事务


#### 递进追问与参考答案


**追问 1：事务重试只重发失败 SQL 可以吗？**

不够安全。前面的读结果可能已经过时，数据库也可能要求整个事务重启。应重新获取业务条件并执行完整单元，给重试上限和退避；外部副作用要有幂等保障，防止重复发送。


**追问 2：Serializable 是不是没有并发了？**

不是，它允许并发，但要求成功提交效果满足相应序列化语义，可能通过锁或冲突检测阻止异常，失败事务需要重试。具体机制依数据库；不能把它理解为所有请求排成一条队列。

# DB-006: MVCC 如何实现并发读取？固定图谱版本为什么不等于固定数据快照？

- **归属模块**：`数据库与 SQL` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：新增：数据库基础与项目 SQL 能力展开

对应简历：分析时固定图谱版本


#### 简要回答

MVCC 通过多版本与可见性规则让查询读取合适版本，减少读写直接互相阻塞。可见范围取决于事务隔离、数据库和语句方式。固定 DataLink 图谱只固定字段语义与候选关系，MySQL 行数据仍会变化；要可复现取数，还需要一致性读或数据快照及其时点记录。


#### 详细解析


##### 1. 1. 版本与可见性

并发事务可能同时读取同一记录的不同时期版本，数据库判断哪些版本对当前读可见。MVCC 不意味着完全没有锁，写写冲突仍要处理；长事务还可能延迟旧版本回收，增加维护与存储成本。PostgreSQL 的版本回收和 InnoDB undo 机制有各自细节，不能混称同一实现。


##### 2. 2. 语句与事务快照的差异

PostgreSQL Read Committed 通常以语句快照读取，因此同事务两条 SELECT 可能看到不同提交结果；Repeatable Read 提供更稳定的事务视图但仍有冲突和失败条件。MySQL InnoDB 默认 Repeatable Read 下普通一致性读与锁定读又不同。业务想保证同一报表口径，不能只假设“放在一个事务就一定同一个时间点”。


##### 3. 3. 项目复现有多个版本维度

DataLink graph_version、Schema_version、SQL、评分 gold 版本和行数据时点都影响结果。固定 graph 便于解释使用哪份语义映射，不保证同一句 SQL 一周后结果相同。评测记录应保存数据集/快照标识、时间范围与结果材料；若连接的是实时业务库，应说明复现限制。


#### 面试总结

- MVCC 与锁共同工作
- 语句与事务快照区分
- graph 版本不冻结行数据
- 复现需记录多个版本


#### 递进追问与参考答案


**追问 1：为什么长事务影响性能？**

它可能长期占用连接、持有锁或要求保留旧版本，导致清理延迟和存储增长。尤其应避免数据库事务里等待用户或模型长响应。先取必要数据并结束事务，确需一致快照时控制持续时间。


**追问 2：同一 Run 的两条 SQL 一定一致吗？**

不一定，取决于是否同一数据库事务、隔离级别、数据来源与查询类型。固定图谱只能保证语义配置稳定。若需要统一数据视图，应设计一致性读取或离线快照，并明确现有实现是否做到。

# DB-007: 数据库锁、死锁与乐观并发控制有什么区别？怎样避免更新丢失？

- **归属模块**：`数据库与 SQL` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：新增：数据库基础与项目 SQL 能力展开

对应简历：数据库并发与终态管理


#### 简要回答

锁通过限制并发访问维护不变量，乐观控制通过版本或条件更新检测冲突。死锁是事务互相等待，需要数据库或应用中断并重试；可以通过固定加锁顺序、短事务和合适索引减少发生。读完再无条件写回会丢失并发更新，不能靠 Python GIL 或进程内锁解决多实例数据库竞争。


#### 详细解析


##### 1. 1. 两种更新思路

悲观方式可以先锁定记录再更新；乐观方式把旧版本条件放入 UPDATE，检查受影响行数。版本不匹配时重新读取或提示冲突。唯一约束负责禁止重复键，但不自动完成业务重试。比如 Run 终态转换，需要“仍在运行才更新”的条件，而非先 SELECT 判断后无条件 UPDATE。


##### 2. 2. 死锁来自资源顺序

两个事务分别先锁 A 再锁 B、先锁 B 再锁 A，就可能形成循环。减小事务、统一顺序、避免等待外部服务有助减少风险。缺少索引的范围更新也可能扩大锁影响，但实际锁范围依数据库、隔离与访问路径而定。InnoDB next-key 涉及记录与间隙，不能将任何 SELECT 都描述成加同样的锁。


##### 3. 3. 项目关联与未证明部分

DataPilot 有进程内任务管理与事件机制，单进程锁不能协调多个服务进程；RAG 文档并发替换也需要考虑数据库版本与存储状态。本文给出并发控制方法，不宣称源码已经使用分布式锁或完整乐观版本。应进一步核对数据库约束与条件更新再回答已实现能力。


#### 面试总结

- 条件更新防止检查后竞态
- 死锁需要识别与事务重试
- 锁范围依数据库与路径
- 进程锁不覆盖多实例


#### 递进追问与参考答案


**追问 1：检测到死锁是否说明设计彻底失败？**

不是，数据库并发环境允许偶发死锁并选择牺牲事务。应用需要有限重试并监测频率；频繁出现时再查锁顺序、索引和事务长度。吞掉错误返回成功才会破坏正确性。


**追问 2：乐观控制什么时候不合适？**

冲突非常频繁或业务无法承受反复重算时，重试成本会高；可用短事务锁定或按业务键串行化。选择取决于争用与延迟需求，不是乐观方式永远更快。

- MySQL8 官方 InnoDB 锁：`https://dev.mysql.com/doc/refman/8.0/en/innodb-locking.html`

# DB-008: JOIN 为什么会把 GMV 算大？怎样检查关联粒度与 NULL 语义？

- **归属模块**：`数据库与 SQL` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：新增：数据库基础与项目 SQL 能力展开

对应简历：含 Join、时序、陷阱题；相关字段和候选 Join 路径


#### 简要回答

JOIN 只遵守匹配条件，不知道业务粒度。订单金额与订单明细一对多关联会重复订单金额，再 SUM 就可能放大。应明确订单、明细、用户等粒度，检查键唯一性、匹配数量与空值，必要时先按目标粒度聚合。DataLink 给候选 Join，不等于已经证明关联满足业务统计。


#### 详细解析


##### 1. 1. 一个具体错误例子

订单 o1 金额100有3条明细，按 order_id 联接后形成3行，SUM(order_amount)变300。SUM(DISTINCT amount)也不能通用修复，因为两笔不同订单同金额会被错误合并。正确方案取决于目标：订单金额在订单表汇总，或先让明细按订单聚合成一行，再与订单关联。


##### 2. 2. JOIN 类型与过滤位置

LEFT JOIN 保留左表无匹配记录，但把右表条件写入 WHERE 可能排除这些行，使结果不再具有原预期。COUNT(*)、COUNT(column) 与 COUNT(DISTINCT user_id) 统计对象不同，NULL 也影响聚合。复购率还需要定义有效订单、时间窗口、退款规则与分母人群，不能只写“联接后 count”。


##### 3. 3. 如何校验候选关联

先看外键/唯一约束与业务含义，再比较关联前后行数、主键去重数、匹配覆盖与最大重复倍数。值重合可能来自巧合或跨系统相同编号，DataLink 候选应辅助探索而非替代语义确认。对应项目答案可以解释验证方法，但不捏造已经为所有候选关系建立完整约束证明。


#### 面试总结

- 先明确统计粒度
- SUM DISTINCT 不是万能修复
- 过滤位置影响外联接语义
- 候选 Join 必须核验


#### 递进追问与参考答案


**追问 1：如何检测 Join 放大？**

比较联接前目标主键数量、联接后行数与每个主键匹配数，再在少量样例上追到重复来源。检查右侧键是否唯一，必要时先聚合。仅比较最终金额是否“看着合理”不足以验证。


**追问 2：值重合率高为什么仍不能确定外键？**

同类型编号可能偶然重合、不同环境复用或使用了别的业务命名空间。还要看方向、唯一性、缺失比例、时间条件和实体定义。统计提示是候选证据，不是业务关系的逻辑证明。

# DB-009: MySQL 与 PostgreSQL 的隔离、SQL 方言和优化行为有哪些区别？

- **归属模块**：`数据库与 SQL` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：新增：数据库基础与项目 SQL 能力展开

对应简历：CSV/SQLite/MySQL；PostgreSQL


#### 简要回答

两个数据库都支持关系查询和事务，但默认隔离、版本可见性、函数、日期语法、标识符和执行计划不同。MySQL 要说明 InnoDB 与版本，PostgreSQL 也要对应部署版本。DataPilot 多数据源生成 SQL 时必须显式区分 dialect，不能把通过一种数据库验证的 SQL 和安全规则直接套到另一种。


#### 详细解析


##### 1. 1. 事务名相同不代表完全同义

MySQL InnoDB 默认隔离通常是 Repeatable Read，PostgreSQL 默认 Read Committed；配置可以改变。InnoDB 普通一致性读和锁定读、范围锁，与 PostgreSQL 的快照和序列化失败语义不完全一致。回答先交代引擎与配置，再讨论业务读写，避免一句“RR 都没有幻读”覆盖所有情况。


##### 2. 2. SQL 与存储差异

日期截断、字符串函数、参数语法、大小写与标识符引用、JSON 与 upsert 形式都有差异。InnoDB 聚簇主键和 PostgreSQL 堆表也影响覆盖与回表解释。优化器选择依赖实际版本与统计，不能把某个索引规则绝对化推广。NULL、时区和数值精度则要按查询语义重点验证。


##### 3. 3. 项目角色不要混用

RAG 用 PostgreSQL 保存父块等关系信息，Redis 缓存，Milvus 检索；DataPilot 访问 SQLite、CSV 与 MySQL，元数据与业务取数也有不同角色。SQLGlot 解析和生成应知道目标 dialect，但解析成功不代表远程驱动支持全部语句。应以代表性跨源案例验证，并保留数据库专属安全限制。


#### 面试总结

- 明确引擎版本与配置
- 默认隔离与实际配置区分
- dialect 需要显式处理
- 项目各存储职责分别讲


#### 递进追问与参考答案


**追问 1：可以只换连接串就迁移数据库吗？**

通常不足。模型类型、迁移、方言函数、索引、隔离、事务和驱动都需核对；数据与约束也要迁移验证。ORM 缩小差异但不能消除全部数据库特性。


**追问 2：同一题两个数据库金额不同怎么查？**

先检查数据与时间范围，再查 NULL、时区、整数除法、DECIMAL/浮点、JOIN 粒度与排序限制。不要一开始就归因模型随机性；保留实际 SQL、参数和结果，才能定位语义差异。

原题关联：新增：数据库基础与项目 SQL 能力展开

对应简历：资料入库；同名文档替换保护；PostgreSQL、Milvus、Redis

普通 PostgreSQL 事务不自动覆盖 Milvus 和 Redis。文档更新应围绕版本、状态与幂等步骤设计：准备新数据，验证后切换可见版本，失败可重试或补偿，缓存按版本失效。RAG 当前有同名文档暂存保护，但不能把它说成三种存储原子回滚。


#### 详细解析

##### 2. 2. 可讨论的改进设计

##### 3. 3. 对现有简历的准确解释

简历资料入库与同名替换可对应暂存准备和旧数据保护，父块数据库与缓存代码可看到单库 commit 与缓存更新。但准备通过后的删除、文件提升、父块和向量写入仍可能部分成功。面试应说明已覆盖的失败阶段与残余风险，而不是把“有 try/except”解释为跨库全部回滚。


#### 面试总结

- 单库事务不覆盖多存储
- 读写都要携带一致版本
- 幂等与补偿处理部分成功
- 暂存保护不等于原子回滚

# RED-001: Redis 的 TTL 过期和 maxmemory 淘汰有什么区别？

- **归属模块**：`Redis 缓存` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：新增：Redis 缓存与项目应用

对应简历：Redis；父级补全与缓存


#### 简要回答

TTL 是应用给某个键设定的时间语义，到期后键不再作为有效缓存；maxmemory 淘汰是实例内存达到上限后按策略选择键清除。两者可以同时存在，TTL 不是内存上限，淘汰也不代表业务版本已更新。RAG 的 300 秒默认 TTL 只能限制陈旧窗口，不能替代版本化 Key 和失效策略。


#### 详细解析


##### 1. 1. 两种机制处理不同问题

TTL 关注单个键的有效期，适合父块或会话缓存的时间边界；淘汰关注整个 Redis 实例的容量，allkeys-lru、volatile-ttl 等策略决定在压力下删除谁。设置 TTL 的键也可能提前被淘汰，没有 TTL 的键在某些 volatile 策略下可能成为无法淘汰对象。容量策略不应被误说成按业务重要性自动选择。


##### 2. 2. 如何选配置

缓存实例可设置 maxmemory 与适合访问分布的策略，并监测命中率、evicted_keys、内存碎片与错误。TTL 应由数据变更频率、允许陈旧时间和回源成本决定，不要一律设很长以追求命中。缓存不能写入时，业务应回源或明确降级；noeviction 下新增写入可能报错，而读仍可工作。


##### 3. 3. 当前项目对应

RAG cache.py 从环境读取 REDIS_CACHE_TTL_SECONDS，set_json 使用 setex；get_json 失败按未命中返回，业务回源 PostgreSQL。这里能证明固定 TTL 与容错降级，不能证明已经配置 maxmemory、淘汰策略或监控告警。面试应清楚区分代码默认值、部署配置和运维验证。


#### 面试总结

- TTL 是键有效期
- 淘汰是实例容量策略
- TTL 不保证不提前淘汰
- 当前代码默认 300 秒并按失败回源


#### 递进追问与参考答案


**追问 1：TTL 到期会立刻删除键吗？**

不应依赖某一瞬间立刻物理删除。Redis 会按机制清理过期键，读取过期键不会作为有效值返回；业务观察到的可用性是重点。若需要统计准确过期时刻，设计事件或版本状态，而不是把过期扫描时间当业务时间。


**追问 2：缓存满了就把 TTL 最短的删掉吗？**

只有选择 volatile-ttl 等相应策略时才是候选行为；allkeys-lru 等策略依据访问性。部署策略应显式配置和验证，不能由设置 TTL 推导实例必然按剩余时间淘汰。

# RED-002: Cache Aside 模式如何读写？数据库更新与缓存删除存在什么竞态？

---

原题关联：新增：Redis 缓存与项目应用

对应简历：Redis；父级补全与缓存


#### 简要回答

Cache Aside 通常先读缓存，未命中查数据库再回填；写入先更新数据库，再删除缓存。它简单、适合缓存派生数据，但删除失败或并发读回填可能留下旧值，因此需要 TTL、版本化 Key、重试和可观测性。当前 RedisCache 对缓存异常降级为未命中，并不等于强一致缓存。


#### 详细解析


##### 1. 1. 读路径的契约

缓存命中直接返回，未命中回源并回填。回填前应确认结果属于当前数据版本，避免慢查询拿到旧快照在更新后覆盖新缓存。缓存序列化失败也应分类记录。缓存只能存可重建数据，不能把 Redis 作为唯一事实来源，除非另有持久化设计。


##### 2. 2. 写路径为何常用删而非直接更新

更新数据库后删除缓存，可以让下一次读取到新值，且避免在应用中重建复杂派生结果。但并发读可能在数据库更新前读旧值，之后慢回填覆盖删除后的键；常见缓解是延迟双删、版本 Key 或写入版本比较。方案要根据可接受陈旧窗口与写读并发选择。


##### 3. 3. 项目事实与边界

RAG chat storage 和 parent_chunk_store 在数据库操作后 set/delete 相应缓存，get 失败回源。代码还捕获 Redis 异常返回 None，使 Redis 暂时不可用不阻断主流程。这是可用性降级，不是强一致保证；文档替换跨 PostgreSQL/Milvus/Redis 的部分成功仍需版本和补偿策略。


#### 面试总结

- 缓存是派生数据
- 回填要考虑旧快照竞态
- 删缓存不提供强一致
- 异常按未命中会保护主流程


#### 递进追问与参考答案


**追问 1：为什么不先删缓存再写库？**

先删后写期间读请求会回源旧数据库并可能回填旧值；写库失败还造成无必要失效。数据库先成功再删除通常更容易保证之后读取新值，但仍需处理并发回填与删除失败。没有一个简单顺序能替代版本或一致性需求分析。


**追问 2：缓存回填和删除谁最后谁赢怎么办？**

可以把版本号写入缓存，回填时只允许不低于当前版本，或用带版本的 Key 让新版本读路径完全避开旧键。也可缩短 TTL、延迟删除并监控。是否采用要以实际代码为准，不能把方案说成已实现。

# RED-003: 缓存穿透、击穿、雪崩分别是什么？怎样按问题处理？

- **归属模块**：`Redis 缓存` | **优先级**：`P0` | **性质**：`方案讨论` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：新增：Redis 缓存与项目应用

对应简历：Redis；父级补全


#### 简要回答

穿透是大量请求查询根本不存在的数据；击穿是热点键刚失效时并发回源；雪崩是大量键同时失效或 Redis 故障造成回源洪峰。解决分别考虑空值/布隆过滤器、单飞或热点续期、TTL 抖动与限流降级。实现措施需符合当前缓存数据和部署规模，不能因为会背名词就声称已做高并发治理。


#### 详细解析


##### 1. 1. 先区分触发条件

不存在 key 的攻击会持续绕过普通缓存，空值短 TTL 可以减少重复；热点 key 失效只影响少数高频项，需要并发合并；很多 key 同时到期可能把数据库压垮，需要错峰。Redis 自身不可用又是依赖故障，单飞锁不能代替回源保护。


##### 2. 2. 组合防护

给 TTL 加小范围随机抖动，避免同批写入同一时刻过期；对热点回源设置有限等待或 stale-while-revalidate；对不存在结果设置短空值；入口用信号量和超时限制回源。布隆过滤器需要维护更新，误判只能阻止不存在请求，不能把真实存在误判为不存在。


##### 3. 3. 与 RAG 的适配

父块缓存缺失时可以按 chunk IDs 批量回源，降低每碎片一次查询的放大；大规模父块缓存应有容量和版本策略。当前代码对 Redis 异常回源 PostgreSQL，未证明采用分布式 singleflight、布隆过滤器或多租户限流，因此回答这些是设计建议。


#### 面试总结

- 穿透是不存在数据
- 击穿是热点失效
- 雪崩是批量失效或依赖故障
- 具体措施要与实际实现区分


#### 递进追问与参考答案


**追问 1：空值缓存会不会污染新数据？**

如果不存在结果后来变成存在，空值 TTL 过长会延迟发现；应设置较短 TTL并在写入时删除对应空键。Key 还需包含正确作用域，避免把一个用户/版本的不存在误用于另一范围。


**追问 2：热点键加锁一定更好？**

锁会减少回源，但会产生等待、超时、故障持有和跨进程语义；可采用有限等待、已有旧值先返回或请求合并。单机进程锁不能覆盖多实例，不能声称它自动解决分布式击穿。

原题关联：新增：Redis 缓存与项目应用

对应简历：Redis；父级补全；资料入库


#### 简要回答

Key 是缓存正确性的一部分，应编码资源类型、业务作用域、版本和必要参数，保持可预测且不过度冗长。父块缓存至少要避免不同文档版本共用同一键；会话缓存还要区分用户与会话。删除策略、批量失效和迁移应在命名规则确定时一起设计。

- Key 作用域避免串读
- 版本 Key 避免旧内容混入
- 版本与清理是容量权衡
- 统一前缀便于运维

**追问 1：为什么只用文件名当 Key 不够？**

同名文件会被替换、不同知识库可能有同名文件，文件名没有稳定版本与租户作用域。应使用文档 ID、版本和集合作用域，并在元数据中保留映射。


**追问 2：版本键会造成内存翻倍吗？**

- 缓存可用性降级不等于数据安全降级

缓存也属于数据副本，需按数据分类、Key 权限、序列化大小和 TTL 管控。敏感字段应最小化或脱敏，避免把完整 Prompt、凭证和用户私密内容长期写入；大父块应评估压缩、批量和容量。当前项目代码缓存会话/父块 JSON，面试时要明确这是实现事实，不推导已经完成隐私审计。

##### 1. 1. 缓存复制风险

数据库权限收紧后，Redis 副本可能仍保留旧内容；备份、AOF 和日志也扩展泄漏面。应只缓存需要重复读取的字段，设置合理过期，隔离 Redis 网络与认证，必要时加密或脱敏。Key 本身也可能暴露用户或文件名，不要把用户输入直接当路径或管理命令。


##### 2. 2. 大对象对延迟的影响

JSON 序列化和网络传输会随对象变大，单个父块缓存过大可能阻塞 Redis 单线程处理其他请求并增加内存碎片。可以拆分可独立读取的字段、限制最大正文、按 ID 批量回源，但拆分也增加请求数。选择要用命中率、P95、内存与回源成本验证。


##### 3. 3. 项目边界

RAG cache.py 使用 json.dumps 并 setex，没有材料证明加密、字段级脱敏或容量审计。DataPilot 的敏感字段遮蔽是结果输出链路约束，不能自动覆盖 RAG 缓存副本。回答可以指出这一差异，并将生产级密钥、访问控制和审计列为部署要求而非已完成事实。


#### 面试总结

- 缓存是敏感数据副本
- 大 JSON 会拖慢与占内存
- TTL 不等于隐私删除
- DataPilot 输出遮蔽不覆盖 RAG 缓存


#### 递进追问与参考答案


**追问 1：缓存加密后就安全了吗？**

加密只解决部分存储或传输风险，访问控制、密钥保管、备份与应用日志仍可能泄漏。还要减少不必要字段和缩短保留期，不能以一个配置声称完整合规。


**追问 2：要不要缓存完整父块？**

看回源成本和上下文需求。可缓存规范化后的必要正文与元数据，限制长度并按版本隔离；若父块很大，分块或数据库读取可能更合适。应通过命中率、延迟与内存实测选择。

# DOCK-001: 镜像与容器有什么区别？容器为何不能被当作完整虚拟机？

- **归属模块**：`Docker 部署与沙箱` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：新增：Docker 部署与代码沙箱

对应简历：Docker 部署；无网络 Docker 沙箱


#### 简要回答

镜像是用于创建运行实例的分层文件与配置，容器是带进程、网络和文件系统视图的运行实例。通常容器共享宿主机内核，通过隔离和资源控制限制访问，启动成本较低；虚拟机有独立客户机内核。容器不是天然绝对安全，沙箱还需明确网络、挂载、权限与资源边界。


#### 详细解析


##### 1. 1. 从镜像到实例

同一镜像可创建多个容器，每个实例有自己的可写层和进程状态；删除容器通常会删除该实例可写层，持久数据需放卷或外部存储。镜像既包含文件，也包含默认启动命令等元数据。应用是否运行成功取决于启动环境、依赖和配置，镜像构建成功不等于服务就绪。


##### 2. 2. 隔离的边界

Namespace 提供进程、挂载、网络等视图隔离，cgroup 管理 CPU、内存等资源，权限能力和安全策略进一步缩小攻击面。共享内核意味着内核与运行时漏洞仍值得关注，宿主目录挂载还可能直接引入数据访问。不能把 Docker 的进程隔离描述为硬件级隔离或保证无逃逸。


##### 3. 3. 两个项目的不同用途

RAG 通过 Compose 部署依赖与应用；DataPilot 将模型生成 Python 放入每次受控容器执行。前者关注依赖、持久数据和服务可用性，后者关注最小权限、无网络、资源上限和清理。答题必须明确讨论部署容器还是不可信代码沙箱，不能把默认部署配置当安全沙箱配置。


#### 面试总结

- 镜像与运行实例区分
- 容器通常共享宿主内核
- 持久数据放卷或外部库
- 部署与沙箱目标不同


#### 递进追问与参考答案


**追问 1：容器删除后 PostgreSQL 数据会丢吗？**

看数据目录是否使用持久卷。若只写容器可写层，删除重建可能丢失；挂载卷能跨实例保留，但仍需要备份、权限和恢复验证。保留卷不等于备份。


**追问 2：镜像固定版本就完全可复现了吗？**

还需固定依赖、构建输入、环境配置、数据库与外部模型版本。镜像 tag 可能移动，严格复现应记录 digest；远端数据库行与模型服务变化仍影响结果。

# DOCK-002: Dockerfile 分层、构建缓存和多阶段构建怎样影响交付？

- **归属模块**：`Docker 部署与沙箱` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：新增：Docker 部署与代码沙箱

对应简历：Docker 部署


#### 简要回答

镜像按构建步骤形成层，前面步骤变化会使后续缓存失效。通常先复制依赖清单并安装，再复制频繁变化的源码，提高缓存利用；多阶段构建可把构建工具与运行产物分开。小镜像不是唯一目标，还需版本锁定、非 root、必要运行依赖和构建输入可追踪。


#### 详细解析


##### 1. 1. 构建缓存的因果关系

若一开始 COPY 整个仓库再安装依赖，每次改业务代码都可能重新安装。先复制锁文件、安装依赖、再复制源码，可让依赖稳定时复用相应层。缓存是否生效还受构建参数、基础镜像与远端获取影响。不要把依赖版本未固定的热缓存构建当完全可复现。


##### 2. 2. 运行镜像保留什么

多阶段可以在构建阶段装编译器，再只复制必要程序和运行依赖到最终阶段，减少体积与攻击面。但 Python 原生包可能依赖共享库，盲目复制虚拟环境会导致运行缺库。应在干净容器验证实际启动和关键路径，而不只看构建退出码。


##### 3. 3. 项目与密钥边界

RAG 有 Dockerfile 与 Compose，可以核对运行命令和依赖；源码中的 .env、缓存、评测输出和用户文档应按需求排除构建上下文。把密钥写入 RUN 或 COPY 可能留在历史层中，即使后面删除也不保证消失。此处多阶段和安全构建是基础，不宣称项目已有完整供应链审计。


#### 面试总结

- 依赖层与源码层分开
- 多阶段保留运行必要文件
- 锁文件与 digest 提高复现性
- 密钥不能写入镜像层


#### 递进追问与参考答案


**追问 1：为什么删除镜像中的密钥仍可能泄漏？**

层保存了之前的文件变化，后续删除只是新层隐藏，旧层仍可能包含内容。应从源头避免复制，用运行时配置或构建 secret 机制，并轮换已暴露密钥。


**追问 2：镜像越小启动越快吗？**

小镜像常降低拉取成本，但实际启动还受模型加载、数据库连接和应用初始化影响。应分别测下载、创建和就绪耗时，不把所有延迟归为体积。

# DOCK-003: 容器网络、服务名和端口映射如何工作？为什么容器里 localhost 连不上数据库？

- **归属模块**：`Docker 部署与沙箱` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：新增：Docker 部署与代码沙箱

对应简历：无网络 Docker 沙箱；Docker 部署


#### 简要回答

localhost 指当前容器自身，不是宿主机或另一个容器。Compose 服务间通常用服务名和容器端口访问，宿主访问再使用端口映射。排查要从监听地址、网络、服务名解析、连接端口与防火墙逐层确认；DataPilot 沙箱 network none 则刻意禁止网络，不能要求它直连数据库。


#### 详细解析


##### 1. 1. 三种地址分别是谁

浏览器访问宿主或公网暴露端口，应用容器访问数据库服务名，容器自身 localhost 只指自己。把宿主映射的15432用于容器内部可能错误，内部 PostgreSQL 常用5432，具体以配置为准。监听127.0.0.1只允许实例内部访问，应用服务往往需要在合适接口监听。


##### 2. 2. 排查路径

先确认目标容器活着和服务监听，再检查两个服务是否在同一网络、名称能否解析、端口是否一致，之后检查身份认证和 TLS。连接拒绝、连接超时与认证失败含义不同。不能看到数据库连接失败就无限重试或直接把数据库暴露到公网。


##### 3. 3. 当前项目事实

RAG 生产 Compose 配置 Redis URL 为 redis://redis:6379/0，对应服务名访问；DataPilot 沙箱命令传 --network none，SQL 取数由主服务完成，再给沙箱所需数据。这个设计减少生成代码网络访问面，但输入中若已有敏感内容，stdout 和文件仍可能泄漏，因此还需输出验证。


#### 面试总结

- localhost 只指本容器
- 服务间用内部端口
- 端口映射服务宿主访问
- 无网络不等于无数据泄漏


#### 递进追问与参考答案


**追问 1：Docker port 映射了但浏览器访问不了怎么查？**

检查容器进程是否监听正确地址、映射是否正确，再查宿主防火墙、代理和公网规则。若内部访问也失败，先定位应用启动错误；若内部正常外部失败，才集中网络暴露。


**追问 2：沙箱能否直接调用远程模型？**

当前无网络配置下不应允许。需要模型调用由受控主服务执行，再把必要结果作为输入。如果确有联网工具需求，应设计单独受限代理和权限，而不是取消沙箱全部网络约束。

# DOCK-004: bind mount、volume 与只读挂载如何选择？挂载目录为何是沙箱风险点？

- **归属模块**：`Docker 部署与沙箱` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：新增：Docker 部署与代码沙箱

对应简历：产物逐个校验声明路径；无网络 Docker 沙箱


#### 简要回答

bind mount 直接映射指定宿主路径，volume 由 Docker 管理，适合持久数据。只读挂载限制容器修改输入，但不会阻止读取或通过输出泄漏。沙箱只应暴露最少输入与独立输出目录，验证路径解析、符号链接和声明产物，不能挂载整个仓库或 Docker socket。


#### 详细解析


##### 1. 1. 持久化与宿主耦合

数据库数据卷可跨容器重建保留，bind mount 更易定位宿主文件但依赖路径、权限和操作系统。卷需要备份和容量管理，不能因为容器可重建就忽略数据。跨 Windows 与 Linux 部署时路径和 UID/GID 可能不同，应验证实际读写而非只看到目录存在。


##### 2. 2. 最小挂载

只给沙箱输入需要的数据，输入只读，输出限定独立目录；根文件系统只读也不能覆盖显式可写挂载。代码能读取的数据可能通过 stdout、图片或输出文件带出，所以挂载只读解决完整性，不自动解决保密性。挂载 Docker socket 会赋予很强宿主操作能力，不应让不可信执行层获得。


##### 3. 3. 产物校验的完整流程

脚本声明了 output.csv 不代表真实文件就在允许目录。应解析绝对路径、检查父目录与符号链接，核对文件类型、大小和格式，再登记产物。DataPilot 简历的逐个声明路径校验能说明输出准入，但不能自动涵盖所有衍生敏感内容或全部内核漏洞。


#### 面试总结

- 持久卷不等于备份
- 只读主要限制修改
- 挂载遵循最小暴露
- 产物路径解析后再准入


#### 递进追问与参考答案


**追问 1：--read-only 能否保证输出目录不可写？**

不能，显式 volume 或 tmpfs 可以有自己的写入权限。应逐项检查根文件系统与挂载，确认输入只读、输出可写且独立。配置名不能代替实际写入测试。


**追问 2：为什么要防符号链接？**

符号链接可能让看似允许目录下的路径实际指向外部。验证需解析真实目标并检查范围，创建与使用之间还可能有竞态。可通过安全文件操作和受控目录进一步减少风险。

- Docker 官方 bind mounts：`https://docs.docker.com/engine/storage/bind-mounts/`

# DOCK-005: Compose 的 depends_on、健康检查与重启策略分别保证什么？

- **归属模块**：`Docker 部署与沙箱` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：新增：Docker 部署与代码沙箱

对应简历：Docker 部署


#### 简要回答

depends_on 组织依赖启动，健康条件可以等待依赖具备相应就绪信号，但不能证明业务请求一定成功；restart 处理进程退出，不解决错误配置或无响应但进程还活着。应用仍需连接重试、超时与状态检查。RAG Compose 中的 Redis ping 是轻量健康检查，不能当完整问答成功率。


#### 详细解析


##### 1. 1. 启动顺序不等于可用性

数据库容器启动后仍可能初始化，应用过早连接会失败；通过 service_healthy 依赖可降低这类竞争。健康检查内容决定含义，ping 只证明 Redis 可响应，未证明缓存数据版本正确。即使启动时就绪，依赖运行中仍可能失效，应用必须处理断连。


##### 2. 2. 重启与持久状态

自动重启能恢复退出进程，但如果错误来自缺少密钥、集合不匹配或数据库迁移，反复重启只形成循环。后台内存 Task 随进程消失，容器重启不自动恢复 Run 执行。需要持久任务状态和启动后的恢复策略；未实现时准确说明边界。


##### 3. 3. 部署核验方式

查看容器状态、health、退出码与日志；验证依赖就绪后应用是否可完成代表性请求，并测试依赖短暂故障的错误反馈。RAG production Compose 可证明存在健康检查和依赖配置，不证明已经实现滚动发布、Kubernetes 或高可用集群。


#### 面试总结

- 启动与就绪不同
- 健康信号有明确范围
- 重启不自动恢复内存任务
- 部署配置不证明高可用


#### 递进追问与参考答案


**追问 1：进程活着但一直无响应会自动重启吗？**

restart 主要依据退出情况，单靠它不能处理所有挂起。需要健康检查、外部监督与业务超时，并注意误杀导致重复副作用。观察健康失败和服务状态，再定义可恢复策略。


**追问 2：健康检查该直接跑一次 Agent 吗？**

频繁完整 Agent 成本高且受外部模型影响。更适合轻量存活、依赖就绪与低频代表性业务探针分层；避免探针自身耗尽资源或产生用户数据。

- RAG Redis healthcheck：`E:/mystudy/agent_study/SuperMew/docker-compose.prod.yml`（第 19 行）

# DOCK-006: 无网络 Python 沙箱还要配置哪些资源与权限限制？

- **归属模块**：`Docker 部署与沙箱` | **优先级**：`P0` | **性质**：`当前实现` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

原题关联：新增：Docker 部署与代码沙箱

对应简历：Python 在无网络 Docker 沙箱执行


#### 简要回答

无网络只减少联网访问面，还需要 CPU、内存、进程数、执行时间、非 root、去 capabilities、no-new-privileges、只读根文件系统和受控挂载。DataPilot 当前命令包含这些限制项，但实际数值来自配置且需验证；不能声称配置完成后绝对无逃逸或无泄漏。

##### 2. 2. 权限与文件系统

##### 3. 3. 当前源码准确表述

docker_sandbox.py 命令构造处包含 network、cpus、memory、pids-limit、cap-drop、security-opt、user、read-only。可以逐项解释保护对象，并说明有单独执行超时和清理。应避免把源码配置等同已做真实攻击验证，本轮未运行沙箱，17条 MySQL 用例也不验证容器逃逸。

- 网络资源权限三层约束
- 超时与 CPU 配额不同

- SQL 用例不证明沙箱逃逸安全

# DOCK-007: 沙箱超时或用户取消后，为什么既要停进程又要删命名容器？

原题关联：新增：Docker 部署与代码沙箱

对应简历：超时取消；无网络 Docker 沙箱


#### 简要回答

Docker CLI 进程与实际容器是两个生命周期。只杀宿主 CLI 不能保证容器中脚本已停止；应按命名容器执行清理，正常退出也可配合 --rm。DataPilot 有有限等待、停止子进程和 remove_container 收尾；清理失败还需记录并提供后续回收机制，不能直接假定没有残留。


#### 详细解析


##### 1. 1. 两个对象可能脱离

API 启动 docker run 后，CLI 等待容器输出，容器由 Docker daemon 管理。取消等待或 CLI 被杀可能让容器继续占资源。给每次执行独立安全名称，可在错误路径找到并移除对应容器，但名称要避免注入和冲突；不要模糊匹配删其他任务。


##### 2. 2. 清理需要幂等与预算

正常、超时、取消、启动失败都可能进入清理，应允许目标已经不存在。停止先给有限时间，再必要时强制；清理不能无限等待，否则取消也不能收敛。进程崩溃可能跳过 finally，因此可以有启动/周期残留扫描，但需明确所有权与保留策略。


##### 3. 3. 当前实现与不足

DataPilot runner 用异步 subprocess、communicate 与 deadline，remove_container 尽力删除命名容器，正常路径有 --rm。此处可以讲已有清理机制，但不宣称已有定时巡检或跨实例恢复。排查残留时记录 RunID、容器名、时间和状态，而不是暴露完整 stderr 给用户。


#### 面试总结

- CLI 与容器分别管理
- 命名资源支持精确清理
- 清理幂等且有限时
- finally 不覆盖进程崩溃

**追问 2：清理失败如何向用户展示？**

主任务仍应给明确超时/取消终态，内部记录清理失败与资源标识，触发后续回收。不能把清理失败吞掉并当完全成功，也不应把宿主路径和原始命令秘密直接返回用户。

# NET-001: TCP 三次握手为什么不能是两次？四次挥手为什么需要 TIME_WAIT？

- **归属模块**：`网络基础` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：本模块新撰（2026-10-06，绑定 DataPilot / Enterprise RAG 场景）

---

#### 简要回答

三次握手让双方都确认「自己和对方的收发能力都正常」，两次握手无法防止历史失效连接占用资源；四次挥手是因为 TCP 全双工，两端要分别关闭；TIME_WAIT 是主动关闭方停留 2MSL 的状态，保证最后的 ACK 丢失时能重传，并让本连接的旧报文在网络中自然消亡。

#### 详细解析

##### 1. 三次握手的本质是同步双方初始序列号

握手交换的是各自的初始序列号（ISN），之后的数据按序列号确认与重排。两次握手的问题：一个在网络中徘徊的历史 SYN 先于新连接到达服务端，服务端回 ACK 后即认为连接建立并分配资源，而客户端根本不认这笔账，服务端就会白白挂着。第三次 ACK 给了客户端确认「这正是我现在要的连接」的机会。

##### 2. 四次挥手因为全双工，TIME_WAIT 承担两个收尾职责

收到 FIN 只说明对方不再发送，我方可能还有数据要发，所以 ACK 与我方 FIN 分开发送，共四次。主动关闭方进入 TIME_WAIT（2MSL）：一是若最后的 ACK 丢失，对方重传 FIN 时我方仍能应答；二是让本连接的旧报文在网络里自然消亡，避免污染四元组相同的下一个连接。

##### 3. 在项目里怎样回答

DataPilot 的 SSE 是长时间 HTTP 连接，前端刷新、断网重连会产生大量短生命周期连接，服务端出现 TIME_WAIT 堆积是正常现象。回答时先说观测手段（`netstat` 统计 TIME_WAIT 数量、确认是否集中在监听端口），再说缓解（HTTP keep-alive 长连接复用减少建拆连接次数），不要脱口而出「调内核参数回收 TIME_WAIT」——缩短 2MSL 是有报文污染风险的取舍，先解释机制再谈调优才是加分顺序。

#### 面试总结

- 三次握手同步双方初始序列号，并防止历史失效连接占用服务端资源
- 四次挥手因全双工分两次关闭，ACK 与 FIN 分离
- TIME_WAIT：保最后的 ACK 可重传 + 旧报文自然消亡
- 线上先观测 TIME_WAIT 分布，再谈是否调优

# NET-002: TCP 与 UDP 的区别是什么？SSE、WebSocket、WebRTC 各自选了哪条路？

- **归属模块**：`网络基础` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：本模块新撰（2026-10-06，绑定 DataPilot / Enterprise RAG 场景）

---

#### 简要回答

TCP 面向连接、可靠有序、带拥塞控制，代价是握手延迟与重传等待；UDP 无连接、无可靠性承诺、开销小、延迟低。可靠性不是「更好」而是「更合适」：SSE 和 WebSocket 都建在 TCP 之上，因为事件流丢不得；WebRTC 走 UDP，因为音视频帧宁可丢弃也不能等重传。

#### 详细解析

##### 1. 先问「丢一帧会怎样」再选传输方式

文字答案、工具调用事件、审计记录丢了会导致状态不一致，必须可靠有序 → TCP；实时音频/视频帧迟到了就失去价值，重传反而不划算 → UDP + 应用层容错（FEC、抖动缓冲）。这是所有传输选型题的第一判断。

##### 2. 三条路对应三类需求

SSE：普通 HTTP 长响应，服务器单向推送，代理与认证体系全复用，断线补发靠应用层 seq；WebSocket：协议升级后的独立双向长连接，适合双向低延迟交互，中间代理要配置 Upgrade 透传；WebRTC：UDP（SRTP）+ ICE 打洞 + DTLS 加密，端到端媒体流。三者不是新旧替代关系，是需求不同。

##### 3. 在项目里怎样回答

DataPilot 只需要「服务端单向事件 + 断线补发」，所以选 SSE 而不是 WebSocket：不需要客户端向服务器推流，SSE 却能沿用 HTTP 认证、代理与负载均衡体系，重连后按事件序号补发即可（题库 08/E-11 与 PY-06 有完整展开）。传输层为什么撑得住：TCP 保证字节流有序不丢，应用层再保证「事件先落库、按 seq 补发」，两层各管一段。

#### 面试总结

- 区别四件套：连接、可靠性、拥塞控制、报文开销
- SSE / WebSocket 是 TCP 的不同用法，WebRTC 才真正走 UDP
- 选型第一问：丢一份数据的后果是什么
- SSE 单向 + seq 补发够用的场景，不必上 WebSocket

# NET-003: HTTPS/TLS 是怎么保证安全的？为什么对称和非对称加密要一起用？

- **归属模块**：`网络基础` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：本模块新撰（2026-10-06，绑定 DataPilot / Enterprise RAG 场景）

---

#### 简要回答

TLS 握手完成三件事：协商协议版本与密码套件、验证服务端证书链、通过非对称算法（如 ECDHE）协商出双方一致的对称会话密钥；之后所有数据用对称加密传输。非对称慢但能在不安全信道安全地交换密钥，对称快适合大流量，所以「握手用非对称、传输用对称」。

#### 详细解析

##### 1. 握手在防什么

防窃听（密文传输）、防篡改（AEAD 如 AES-GCM 自带完整性校验）、防冒充（证书链验证：签发链、域名、有效期、吊销状态）。用 ECDHE 这类临时密钥交换还提供前向保密——即使服务端私钥日后泄露，历史会话也无法解密。

##### 2. 为什么不全程非对称

非对称运算比对称慢几个数量级，用它保护每一个报文在性能上不可行；它只承担「把对称密钥安全送到对端」这一次性工作。这是典型的用一次贵操作换长期便宜路径的工程取舍。

##### 3. 在项目里怎样回答

DataPilot 后端调用外部 LLM、Rerank、Embedding API 全部走 HTTPS，API Key 不进 URL、不进日志；容器内网（Docker 网络内 db / datalink 之间的 HTTP 明文）是部署边界内的有意选择——内网明文要「说得出为什么可以」：网络边界受控、流量不出主机。面试里能主动讲清这个边界判断，比背握手流程更能体现工程素养。

#### 面试总结

- TLS = 证书认证 + 密钥交换 + 对称加密传输
- 非对称换密钥（贵、一次性），对称扛流量（快、持续性）
- ECDHE 提供前向保密；AEAD 同时保机密性与完整性
- 内网明文是边界判断，要能说清为什么可以

# NET-004: HTTP/1.1、HTTP/2、HTTP/3 的核心区别？SSE 为什么用 HTTP/1.1 也能工作？

- **归属模块**：`网络基础` | **优先级**：`P1` | **性质**：`通用原理` | **来源**：本模块新撰（2026-10-06，绑定 DataPilot / Enterprise RAG 场景）

---

#### 简要回答

HTTP/1.1 是文本协议，一个连接同一时刻只处理一个请求，靠 keep-alive 复用 TCP 连接；HTTP/2 引入二进制分帧与多路复用，一个连接并发多个流，外加 HPACK 头部压缩，但 TCP 层队头阻塞仍在；HTTP/3 改用 QUIC（UDP），流之间独立丢包重传，彻底解决队头阻塞并内置 TLS 1.3。SSE 本质是「一个不结束的 HTTP 响应」，单流场景 HTTP/1.1 完全够用。

#### 详细解析

##### 1. 队头阻塞有两层，各代协议只解决自己那层

应用层队头阻塞：HTTP/1.1 前一个响应没结束，后一个请求就得排队——HTTP/2 用分帧多路复用解决；传输层队头阻塞：TCP 字节流里任何一个包丢失，其后的所有流数据都要等重传——HTTP/2 无能为力，HTTP/3 用 QUIC 让每个流独立重传才解决。能把这两层分开说的面试者很少，值得记住。

##### 2. SSE 对协议版本没有特殊要求，怕的是中间层

SSE 就是 `Content-Type: text/event-stream` 的流式响应，浏览器 EventSource 自动重连。实践中比版本选择更常出问题的是反代/网关缓冲：Nginx 等默认可能攒响应，事件会被「攒成一坨」延迟到达，必须显式关闭代理缓冲（如 `X-Accel-Buffering: no`）并设置合理的读超时。

##### 3. 在项目里怎样回答

DataPilot 用 SSE 时，部署链路上要确认网关禁用缓冲；被问「为什么不上 HTTP/2/3」，答案是：SSE 单流场景协议收益有限，系统延迟瓶颈在外部 LLM API 的生成时间，不在协议分帧——把延迟归因讲清楚（衔接 NET-008 与 T-F-06 的分段测量）比堆技术名词更有说服力。

#### 面试总结

- 1.1 文本 + keep-alive；2 二进制分帧 + 多路复用；3 QUIC 解决 TCP 队头阻塞
- 队头阻塞分应用层与传输层两层，h2 只解了前者
- SSE 不挑版本，怕代理缓冲；单流场景协议升级收益有限

# NET-005: 从浏览器输入 URL 到页面展示，中间发生了什么？

- **归属模块**：`网络基础` | **优先级**：`P0` | **性质**：`通用原理` | **来源**：本模块新撰（2026-10-06，绑定 DataPilot / Enterprise RAG 场景）

---

#### 简要回答

主干链路：URL 解析 → DNS 解析拿到 IP → TCP 三次握手 → TLS 握手（https）→ 发送 HTTP 请求 → 服务端处理并返回响应 → 浏览器解析渲染（HTML 建 DOM、CSS 建 CSSOM、合成渲染树、布局、绘制，JS 按加载策略执行）。

#### 详细解析

##### 1. 每一步都有可展开的第二层

DNS：浏览器缓存 → 系统缓存与 hosts → 递归解析器 → 根/顶级域/权威服务器，逐级 TTL 缓存；TCP：握手同步初始序列号；TLS：证书验证 + 密钥协商；HTTP：方法、头、体与状态码语义。这题考的不是背主干，而是每一层能不能再被往下追问两层。

##### 2. 渲染管线是常见的第一追问

解析 HTML 构建 DOM，遇 CSS 构建 CSSOM，两者合成渲染树；Layout 计算几何位置，Paint 绘制像素。JS 默认阻塞解析（async 下载完即执行、defer 文档解析完按序执行）——「为什么脚本放底部 / 加 defer」就是从这里来的。

##### 3. 在项目里怎样回答

这题适合主动接回自己的系统制造差异点：DataPilot 前端断线刷新后，走完这条链只是「连接恢复」，业务状态还没恢复——前端按 Run 查询本地已收到的最大事件 seq，SSE 服务端从断点补发持久化事件，这才是页面恢复到中断前样子的原因。URL 链路是通用底座，应用层在其上补状态恢复逻辑，衔接 07/T-E-06 与 08 的断线恢复题。

#### 面试总结

- 主干六步是及格线，每层能再答两层才算掌握
- DNS 多级缓存、TCP 同步序列号、TLS 证书+密钥，三处最常被追问
- 渲染管线索引出 async/defer 的区别
- 结尾落到自己系统的行为差异（断线补发），是拉开差距的地方

# NET-006: DNS 是怎么工作的？递归查询与迭代查询有什么区别？

- **归属模块**：`网络基础` | **优先级**：`P1` | **性质**：`通用原理` | **来源**：本模块新撰（2026-10-06，绑定 DataPilot / Enterprise RAG 场景）

---

#### 简要回答

DNS 把域名翻译成 IP。客户端到本地递归解析器是递归查询——「你必须给我最终答案」；解析器到根域名服务器、顶级域服务器、权威服务器是迭代查询——「你不用给答案，告诉我该问谁」。分层授权 + 逐级 TTL 缓存让全球解析体系可扩展。

#### 详细解析

##### 1. 完整链路与缓存层次

浏览器缓存 → 系统缓存/hosts → 本地递归解析器（运营商或公共 DNS）→ 根服务器（告诉谁管 `.com`）→ 顶级域服务器（告诉谁管 `example.com`）→ 权威服务器（给出 A/AAAA 记录）。每一级结果都按 TTL 缓存，所以改 DNS 记录后「全球生效要等 TTL 过期」。

##### 2. 常见追问点

主用 UDP 53（报文小、一次往返），响应过大或区域传送用 TCP；DNS 明文可被劫持/污染，DoH/DoT 用加密解决隐私与篡改问题。能主动提这两个「为什么」即可，不必展开协议细节。

##### 3. 在项目里怎样回答

容器环境的服务发现就是一次 DNS 查询：Docker/Compose 内置 DNS 把容器名、服务名解析成容器 IP，DataPilot 的 Compose 网络里 `db`、`datalink`、`sandbox` 之间的互访都靠它（衔接 DOCK-003「容器里为什么 localhost 连不上数据库」——因为容器 DNS 解析到的是各自独立的 NET namespace）。排障时 `dig`/`nslookup` 区分「解析失败」与「连不上」是定位网络问题的第一刀，衔接 NET-008 的分段定位。

#### 面试总结

- 递归查「结果」，迭代问「路径」，授权自根向下逐级委托
- 多级缓存 + TTL 决定变更生效速度
- UDP 为主、TCP 兜底；DoH/DoT 解决明文问题
- 容器服务名解析就是 DNS，排障先用 dig 分层

# NET-007: TCP 长连接为什么会断？keepalive 心跳与应用层心跳有什么区别？

- **归属模块**：`网络基础` | **优先级**：`P0` | **性质**：`通用原理 + 项目实践` | **来源**：本模块新撰（2026-10-06，绑定 DataPilot / Enterprise RAG 场景）

---

#### 简要回答

两类原因：中间设备（NAT、防火墙、负载均衡）会回收「空闲」连接；对端崩溃或网络分区时 TCP 本身感知不到对方死活。所以需要心跳。TCP keepalive 是内核探测，默认约 2 小时才发第一针，基本必须调参数；应用层心跳由业务自定义间隔、超时语义，还能捎带状态，是绝大多数服务的实际选择。

#### 详细解析

##### 1. 半开连接问题

对端进程崩溃或网线拔掉后，本端发的数据会一直等 ACK 直到超时，期间连接仍挂在内核里占用资源。心跳的作用是把「对端还活着吗」的探测从小时级压到秒级，并让中间设备一直把这条连接视为「活跃」，不被提前回收。

##### 2. 应用层心跳的优势

间隔与超时可配置；超时即可主动断开重连，语义清晰；可携带业务状态（如负载、版本）；能穿过只放行 HTTP 的代理。SSE 场景的标准做法是服务端周期发注释行或心跳事件，防止代理把空闲连接当死链掐掉。

##### 3. 在项目里怎样回答

这里有一个能直接背下来的项目细节：DataPilot 的 SSE 心跳事件**不落库**——心跳只是传输层保活信号，不是业务事件，若写入事件存储反而会污染断线补发所依赖的 seq 序列。心跳负责「连接别断」，持久化事件 + seq 负责「断了之后补齐」，两个机制各管一段，面试里别混成一件事（衔接 07/T-E-06、08/E-11）。

#### 面试总结

- 连接会断：中间设备回收空闲连接 + 对端死活感知缺失
- TCP keepalive 默认极慢（约 2h），实际服务多用应用层心跳
- SSE 心跳保活不落库；断线恢复靠持久化 seq，两者职责分离

# NET-008: 一次 HTTP 请求很慢，怎么分层定位是 DNS、连接、TLS 还是服务端的问题？

- **归属模块**：`网络基础` | **优先级**：`P0` | **性质**：`通用方法 + 项目实践` | **来源**：本模块新撰（2026-10-06，绑定 DataPilot / Enterprise RAG 场景）

---

#### 简要回答

先分段再归因。用 `curl -w` 输出五个时间点：`time_namelookup`（DNS 完成）、`time_connect`（TCP 完成）、`time_appconnect`（TLS 完成）、`time_starttransfer`（收到首字节）、`time_total`（完成）。相邻时间点做减法，每一段对应一层，哪段异常就深挖哪层。

#### 详细解析

##### 1. 减法公式（可直接白板写）

DNS 耗时 = namelookup；TCP 耗时 = connect − namelookup；TLS 耗时 = appconnect − connect；首字节耗时 = starttransfer − appconnect（含服务端处理时间）；内容下载耗时 = total − starttransfer。connect 慢看路由与丢包；starttransfer 慢是服务端真的慢（查后端与依赖）；total 远大于 starttransfer 是传输量大或带宽问题。

##### 2. 分段之外的两个常用手段

对比重试（偶发慢 vs 稳定慢）；对比来源（同机房直连 vs 经代理）。慢如果是「每请求都慢」，优先怀疑连接未复用——每次都付 TCP+TLS 握手成本；如果「偶发毛刺」，看 GC、连接池等待、下游超时抖动。

##### 3. 在项目里怎样回答

DataPilot 观测 P99 时把延迟拆成模型调用、Gateway、Sandbox、DataLink、SSE 各阶段（07/T-F-06），方法与 curl 分段完全同构：先拆段归因，再谈优化。典型例子：调用外部 LLM API 慢，先区分是 TLS 反复握手（连接未复用 → 上连接池/keep-alive）还是生成时间本身长（token 量与模型侧问题 → 优化 prompt 或用流式改善体感）。把「慢」拆成可测量的小段，比任何单一优化技巧都重要。

#### 面试总结

- 分段测量是通用方法论：DNS / TCP / TLS / 首字节 / 下载各管一段
- `curl -w` 五个时间点是可白板复现的面试工具
- 每请求都慢先查连接复用，偶发毛刺查 GC/连接池/下游抖动

# OS-001: 进程、线程、协程有什么区别？各自的切换成本和适用场景？

- **归属模块**：`操作系统` | **优先级**：`P0` | **性质**：`通用原理 + 项目实践` | **来源**：本模块新撰（2026-10-06，绑定 DataPilot / Enterprise RAG 场景）

---

#### 简要回答

进程是资源分配单位，拥有独立地址空间；线程是 CPU 调度单位，共享所属进程的地址空间；协程是运行时在用户态调度的执行单元，切换不进内核。切换成本：进程 > 线程 > 协程。选型口诀：IO 密集用协程/线程提高并发，CPU 密集用多进程绕开 GIL；要隔离就用进程边界。

#### 详细解析

##### 1. 三者的本质差异在「共享了什么、谁来调度」

进程间地址空间隔离，通信靠 IPC，一个进程崩溃不拖垮别人；线程共享内存，通信快但要处理竞态与锁；协程在单线程内交替执行，切换只是保存寄存器与栈指针，没有内核介入——但也因此是协作式调度：一个协程执行阻塞调用会卡住整个线程（衔接 PY-02「异步函数为何仍会阻塞」）。

##### 2. 切换成本的来源

进程切换要换页表、刷 TLB、切内核上下文，最贵；线程切换共享地址空间、只切寄存器与栈，便宜一个量级；协程切换是函数调用级别的开销，可以支撑百万级并发单元。

##### 3. 在项目里怎样回答

DataPilot 一套系统把三种都用上了，这是现成的回答框架：FastAPI 事件循环里的协程承载并发请求与 SSE 长连接；同步阻塞的 SDK 与数据库驱动丢进线程池，不占事件循环（BE-001）；模型生成的 Python 代码放独立容器进程执行——隔离靠进程 + namespace 边界，而不是线程（线程共享地址空间，恶意代码可以越界伤及宿主，衔接 OS-005）。CPU 密集任务（如本地嵌入计算）走多进程池，绕 GIL（衔接 PY-01）。

#### 面试总结

- 分配单位 vs 调度单位 vs 用户态调度单元
- 切换成本与隔离性成反比，选型按 IO/CPU 与安全边界定
- 协作式调度既是协程高并发的来源，也是「一阻塞全卡」的原因
- DataPilot：协程扛请求、线程池接阻塞、容器进程做隔离

# OS-002: IO 多路复用是什么？select/poll/epoll 有什么区别？

- **归属模块**：`操作系统` | **优先级**：`P0` | **性质**：`通用原理 + 项目实践` | **来源**：本模块新撰（2026-10-06，绑定 DataPilot / Enterprise RAG 场景）

---

#### 简要回答

IO 多路复用让单个线程同时等待大量 fd，谁就绪就处理谁，避免「一个连接一个线程」。select 用固定大小位图，每次调用全量拷贝进内核并 O(n) 扫描；poll 改成数组去掉数量上限但仍是 O(n)；epoll 用内核事件表 + 回调 + 就绪链表，注册一次、只返回就绪的 fd，连接多而活跃少时接近 O(1)，是 Linux 高并发服务的基石。

#### 详细解析

##### 1. 核心差异在「谁来扫就绪状态」

select/poll 每次都要把整个 fd 集合拷进内核，再由调用方线性扫一遍找出就绪者；epoll 用 `epoll_ctl` 注册一次，内核维护红黑树，事件发生时回调把它挂进就绪链表，`epoll_wait` 只拿就绪集合。连接数大、活跃占比小（典型的长连接服务形态）时，epoll 免掉了两笔全量开销。

##### 2. 边缘触发（ET）与水平触发（LT）

LT：只要条件满足就持续通知，没读完下次还会提醒，编程简单；ET：仅在状态变化时通知一次，必须循环读到 EAGAIN。Python 标准库 selectors 与 asyncio 默认以 LT 语义为主，牺牲一点性能换正确性容易。

##### 3. 在项目里怎样回答

FastAPI/uvicorn 的事件循环底层就是 Linux 上的 epoll：一个进程用一条线程扛几百条 SSE 长连接，靠的是「注册后等事件」而不是「每连接配一线程」。回答时注意两个边界：一，epoll 解决 IO 等待问题，与 GIL 限制 CPU 并行是两件事，别混在一起说（衔接 PY-01）；二，Windows 用 IOCP/降级实现，行为有差异，这是部署选 Linux 的原因之一。能讲「事件循环 = 多路复用 + 就绪事件分发」这层封装关系，就超过了背 API 的层次。

#### 面试总结

- select 固定上限 + 全量扫描；poll 去掉上限但仍 O(n)；epoll 注册一次、回调收就绪
- ET 通知一次必须读到底，LT 持续通知更易写对
- 事件循环是「多路复用 + 事件分发」的应用层封装
- epoll 管 IO 等待，GIL 管 CPU 并行，两个问题别混谈

# OS-003: 零拷贝是什么？解决什么问题？与 mmap、sendfile 什么关系？

- **归属模块**：`操作系统` | **优先级**：`P1` | **性质**：`通用原理 + 项目实践` | **来源**：本模块新撰（2026-10-06，绑定 DataPilot / Enterprise RAG 场景）

---

#### 简要回答

传统「读文件再发网络」要经历磁盘 → 内核页缓存 → 用户缓冲区 → socket 缓冲区 → 网卡的多次拷贝和内核/用户态来回切换。零拷贝的目标是数据不回用户态：`sendfile` 让数据从页缓存直接送到 socket；`mmap` 把文件映射进用户地址空间，省掉 read 的那次拷贝。它优化的是「搬运」，不是「处理」。

#### 详细解析

##### 1. 先分清两笔开销：CPU 拷贝与上下文切换

磁盘到页缓存由 DMA 完成，不占 CPU；`sendfile`（配合 DMA gather）让 CPU 完全不参与数据搬运；但若需要在用户态修改内容（加密、压缩、转换），sendfile 不适用，改用 mmap + write。零拷贝不是无拷贝，是把「不必要的拷贝」消掉。

##### 2. 适用边界：原样转发才有效

静态文件服务、日志采集、消息队列的刷盘与发送是典型受益场景；只要数据需要计算，那份进用户态的拷贝就省不掉。判断顺序是「要不要处理 → 怎么省拷贝」，反着背优化清单没意义。

##### 3. 在项目里怎样回答

DataPilot 的文件快照、CSV/SQLite 输入进沙箱，走的是 bind mount——容器与宿主共享同一份文件，连一次拷贝都不发生，比任何用户态拷贝优化都彻底（衔接 DOCK-004）。真正需要用户态处理的环节（上传 PDF → 解析成 Markdown）就老实读进来处理；同类系统的教训是：大文件上传用流式转发（生成器逐块搬运，衔接 PY-05），不要整包读进内存——「流式」与零拷贝同属一个思想：别把不需要驻留内存的数据搬进内存。

#### 面试总结

- 零拷贝消的是内核/用户态往返拷贝，不是所有拷贝
- sendfile 适合原样转发，mmap 适合需用户态访问；要处理的数据省不了
- 同机共享数据的终极方案是挂载共享，不是更快的拷贝
- 与流式处理同源：数据不必驻留内存就不进内存

# OS-004: 虚拟内存是怎么工作的？缺页中断是什么？

- **归属模块**：`操作系统` | **优先级**：`P1` | **性质**：`通用原理 + 项目实践` | **来源**：本模块新撰（2026-10-06，绑定 DataPilot / Enterprise RAG 场景）

---

#### 简要回答

每个进程拥有独立的虚拟地址空间，MMU 通过页表把虚拟页翻译成物理页帧——进程只见虚拟地址，隔离与重定位由此实现。访问的页不在物理内存时触发缺页中断，内核从磁盘换入或按需建立映射；物理内存不足时按策略回收换出，极端情况下 OOM。

#### 详细解析

##### 1. 虚拟内存的三个收益

隔离：进程地址空间互不可见，配合权限位实现只读/可执行保护；重定位：程序链接地址与物理存放位置解耦；超额分配：虚拟空间可以远大于物理内存 + swap，按需加载兜底。代价是每次访存都要查页表，靠 TLB 缓存翻译结果。

##### 2. 缺页分两类，性能含义完全不同

次要缺页：页还在页缓存里，建立映射即可，开销小；主要缺页：必须从磁盘读入，开销大。主要缺页频繁意味着内存吃紧或访问模式差（随机访问大文件、无局部性），性能会断崖式下跌——「服务突然变慢但 CPU 不高」时，查缺页与 swap 是一个方向。

##### 3. 在项目里怎样回答

两个落点：一，容器内存限制（cgroup）约束的是物理用量，DataPilot 沙箱限 512MB，模型脚本吃内存超限的结局不是报异常而是内核直接 OOM kill（退出码 137），这是排查沙箱任务「进程无声消失」的第一个怀疑点（衔接 DOCK-006/DOCK-007 与 OS-005）；二，mmap 方式读大 SQLite/CSV 时文件页按需加载，顺序访问友好、随机访问易缺页（衔接 OS-003），「数据库为什么自己做页缓存而不全依赖 OS」也由此展开。

#### 面试总结

- 虚拟内存 = 页表翻译 + 按需加载 + 换页兜底，隔离与重定位是核心收益
- 次要缺页便宜、主要缺页昂贵；主要缺页频发是性能告警
- 容器内存超限的结局是 OOM kill（137），不是异常可捕获

# OS-005: 容器的 CPU/内存限制底层是怎么实现的？OOM 是怎么发生的？

- **归属模块**：`操作系统` | **优先级**：`P0` | **性质**：`通用原理 + 项目实践` | **来源**：本模块新撰（2026-10-06，绑定 DataPilot / Enterprise RAG 场景）

---

#### 简要回答

容器不是虚拟机，而是「普通进程 + 内核隔离手段」：namespace 提供视图隔离（PID、网络、挂载等各看各的），cgroup 提供资源限额（CPU 配额、内存上限）。内存超过上限时内核先做页回收，回收不够就按 OOM score 选进程 SIGKILL，容器表现为被 OOM kill，退出码 137。

#### 详细解析

##### 1. namespace 管「看得见什么」

PID namespace 让容器内进程以为自己是一号进程；NET namespace 给独立网络栈与接口（沙箱「无网络」就是只建 NET namespace 而不接外部网卡）；MNT namespace 配合 mount 提供独立文件系统视图；另有 UTS/IPC/USER。「容器里 ps 只看到自己」就是 namespace 的直接体验。

##### 2. cgroup 管「能用多少」

cgroup v2 用 `cpu.max` 设配额（每周期可用微秒数）、`memory.max` 设硬上限。内存超限的顺序是：先回收页缓存/换页，回收不够 → 触发 OOM → 内核直接 SIGKILL。注意 CPU 超限与内存超限的症状不同：CPU 被限流是**变慢**（throttle），内存超限是**被杀**——排障时这是两类症状两条路。

##### 3. 在项目里怎样回答

DataPilot 沙箱 512MB/15s 的限制就是 cgroup 参数（衔接 DOCK-006），「无网络」就是 namespace 组合（衔接 DOCK-003/DOCK-004）。这题还能反向回答一个架构题：「为什么不用线程池跑模型生成的代码」——线程共享地址空间，恶意或错误代码可以越界伤及宿主进程；容器进程有独立 namespace + 硬限额，最坏情况是容器被杀、Run 标记失败，宿主无恙（衔接 OS-001）。OOM 后的观测特征要能说：容器退出码 137、内核日志有 oom-killer 记录、进程无声消失。

#### 面试总结

- namespace 管视图隔离，cgroup 管资源额度，两者合起来才是「容器」
- CPU 超限变慢（throttle），内存超限被杀（OOM SIGKILL，退出码 137）
- 进程级隔离是沙箱安全模型的地基，线程给不了

# OS-006: 死锁产生的四个必要条件是什么？怎么避免？

- **归属模块**：`操作系统` | **优先级**：`P0` | **性质**：`通用原理 + 项目实践` | **来源**：本模块新撰（2026-10-06，绑定 DataPilot / Enterprise RAG 场景）

---

#### 简要回答

互斥、持有并等待、不可剥夺、循环等待——四个条件同时成立才会死锁，破坏任意一个即可避免。工程上最常用：固定加锁顺序破坏循环等待、一次性申请全部资源破坏持有并等待、超时与死锁检测做兜底。

#### 详细解析

##### 1. 数据库层：检测 + 回滚重试

InnoDB 维护锁等待图，检测到死锁主动回滚代价小的事务并报错（Deadlock found）。应用要捕获这个错并**重试整个事务**，而不是重试单条语句——回滚后的状态已不可续用（衔接 DB-005「什么时候需要重试整个事务」）。

##### 2. 应用层：写法纪律

缩短临界区；多把锁按统一顺序获取；持锁时不做 IO、不回调外部代码；`asyncio.Lock`/线程锁都在 finally 或 async-with 里保证释放。连接池与锁交叉使用时，「先拿锁再等连接」与「先拿连接再等锁」混用是经典死锁配方——申请顺序也要固定。

##### 3. 在项目里怎样回答

DataPilot 里有现成的设计证据：工具串行节点按固定顺序执行、SQL Audit 记录先 `proposed` 再流转状态、SSE 事件先落库再推送——这类「单一写入口 + 固定顺序」本质上就是靠破坏循环等待来防死锁；取消与超时路径必须保证锁最终释放（finally + 取消安全），否则一次取消就可能让后续所有 Run 卡死（衔接 PY-004、BE-003）。被追问「你的系统哪里可能死锁」时，用这套证据回答，比背四条件高一档。

#### 面试总结

- 四条件：互斥、持有并等待、不可剥夺、循环等待，破坏其一即可
- 数据库死锁靠捕获后重试整个事务；应用死锁靠顺序一致 + 临界区短 + 持锁不做 IO
- 取消/超时路径必须保证锁释放，否则死锁以「全系统卡死」的形式出现

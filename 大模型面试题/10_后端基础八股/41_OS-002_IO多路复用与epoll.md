# OS-002: IO 多路复用是什么？select/poll/epoll 有什么区别？

- **归属模块**：`操作系统` | **优先级**：`P0` | **性质**：`通用原理 + 项目实践` | **来源**：本模块新撰（2026-10-06，绑定 DataPilot / Enterprise RAG 场景）

---

#### 简要回答

IO 多路复用让单个线程同时等待大量 fd，谁就绪就处理谁，避免「一个连接一个线程」。select 用固定大小位图，每次调用全量拷贝进内核并 O(n) 扫描；poll 改成数组去掉数量上限但仍是 O(n)；epoll 用内核事件表 + 回调 + 就绪链表，注册一次、只返回就绪的 fd，连接多而活跃少时接近 O(1)，是 Linux 高并发服务的基石。

#### 详细解析

##### 1. 核心差异在「谁来扫就绪状态」

select/poll 每次都要把整个 fd 集合拷进内核，再由调用方线性扫一遍找出就绪者；epoll 用 `epoll_ctl` 注册一次，内核维护红黑树，事件发生时回调把它挂进就绪链表，`epoll_wait` 只拿就绪集合。连接数大、活跃占比小（典型的长连接服务形态）时，epoll 免掉了两笔全量开销。

##### 2. 边缘触发（ET）与水平触发（LT）

LT：只要条件满足就持续通知，没读完下次还会提醒，编程简单；ET：仅在状态变化时通知一次，必须循环读到 EAGAIN。Python 标准库 selectors 与 asyncio 默认以 LT 语义为主，牺牲一点性能换正确性容易。

##### 3. 在项目里怎样回答

FastAPI/uvicorn 的事件循环底层就是 Linux 上的 epoll：一个进程用一条线程扛几百条 SSE 长连接，靠的是「注册后等事件」而不是「每连接配一线程」。回答时注意两个边界：一，epoll 解决 IO 等待问题，与 GIL 限制 CPU 并行是两件事，别混在一起说（衔接 PY-01）；二，Windows 用 IOCP/降级实现，行为有差异，这是部署选 Linux 的原因之一。能讲「事件循环 = 多路复用 + 就绪事件分发」这层封装关系，就超过了背 API 的层次。

#### 面试总结

- select 固定上限 + 全量扫描；poll 去掉上限但仍 O(n)；epoll 注册一次、回调收就绪
- ET 通知一次必须读到底，LT 持续通知更易写对
- 事件循环是「多路复用 + 事件分发」的应用层封装
- epoll 管 IO 等待，GIL 管 CPU 并行，两个问题别混谈

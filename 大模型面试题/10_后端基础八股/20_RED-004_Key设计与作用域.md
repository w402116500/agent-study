# RED-004: Redis Key 如何设计版本、用户和文档作用域？

#### 简要回答

Key 是缓存正确性的一部分，应编码资源类型、业务作用域、版本和必要参数，保持可预测且不过度冗长。父块缓存至少要避免不同文档版本共用同一键；会话缓存还要区分用户与会话。删除策略、批量失效和迁移应在命名规则确定时一起设计。


#### 详细解析


##### 1. 1. Key 防止什么串读

没有用户或知识库作用域，两个请求可能读到相同字符串下的错误对象；没有文档版本，旧父块可能在新索引请求中被补回。将 type:scope:version:id 作为逻辑结构有助排查和批量管理，但 scope 不能放入用户可控未清洗文本，长度也需受控。


##### 2. 2. 版本化和删除的取舍

版本 Key 可以让新读天然避开旧缓存，旧键再异步清理；代价是短期内多版本占空间。就地删除节省键数量，却依赖删除成功。可以同时存活版本指针，但更新指针也需原子或条件语义。版本号来自数据库/索引状态，不应每次请求随机生成。


##### 3. 3. 当前项目的证据

cache.py 使用统一前缀；聊天存储按 user_id/session_id 形成会话和消息 Key，父块 store 以 chunk_id 形成缓存键。源码能证明基础作用域与 TTL，但并不能证明缓存键已经编码所有索引版本；若版本要求是新增设计，应明确为改进方向。


#### 面试总结

- Key 作用域避免串读
- 版本 Key 避免旧内容混入
- 版本与清理是容量权衡
- 统一前缀便于运维


#### 递进追问与参考答案


**追问 1：为什么只用文件名当 Key 不够？**

同名文件会被替换、不同知识库可能有同名文件，文件名没有稳定版本与租户作用域。应使用文档 ID、版本和集合作用域，并在元数据中保留映射。


**追问 2：版本键会造成内存翻倍吗？**

切换期间可能短时共存，取决于清理及时性与更新频率。可以异步清理旧版本、限制同时活跃版本并设置 TTL。先确保正确性，再用容量监测调整，不应为省内存取消版本隔离。

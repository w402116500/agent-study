# OS-005: 容器的 CPU/内存限制底层是怎么实现的？OOM 是怎么发生的？

- **归属模块**：`操作系统` | **优先级**：`P0` | **性质**：`通用原理 + 项目实践` | **来源**：本模块新撰（2026-10-06，绑定 DataPilot / Enterprise RAG 场景）

---

#### 简要回答

容器不是虚拟机，而是「普通进程 + 内核隔离手段」：namespace 提供视图隔离（PID、网络、挂载等各看各的），cgroup 提供资源限额（CPU 配额、内存上限）。内存超过上限时内核先做页回收，回收不够就按 OOM score 选进程 SIGKILL，容器表现为被 OOM kill，退出码 137。

#### 详细解析

##### 1. namespace 管「看得见什么」

PID namespace 让容器内进程以为自己是一号进程；NET namespace 给独立网络栈与接口（沙箱「无网络」就是只建 NET namespace 而不接外部网卡）；MNT namespace 配合 mount 提供独立文件系统视图；另有 UTS/IPC/USER。「容器里 ps 只看到自己」就是 namespace 的直接体验。

##### 2. cgroup 管「能用多少」

cgroup v2 用 `cpu.max` 设配额（每周期可用微秒数）、`memory.max` 设硬上限。内存超限的顺序是：先回收页缓存/换页，回收不够 → 触发 OOM → 内核直接 SIGKILL。注意 CPU 超限与内存超限的症状不同：CPU 被限流是**变慢**（throttle），内存超限是**被杀**——排障时这是两类症状两条路。

##### 3. 在项目里怎样回答

DataPilot 沙箱 512MB/15s 的限制就是 cgroup 参数（衔接 DOCK-006），「无网络」就是 namespace 组合（衔接 DOCK-003/DOCK-004）。这题还能反向回答一个架构题：「为什么不用线程池跑模型生成的代码」——线程共享地址空间，恶意或错误代码可以越界伤及宿主进程；容器进程有独立 namespace + 硬限额，最坏情况是容器被杀、Run 标记失败，宿主无恙（衔接 OS-001）。OOM 后的观测特征要能说：容器退出码 137、内核日志有 oom-killer 记录、进程无声消失。

#### 面试总结

- namespace 管视图隔离，cgroup 管资源额度，两者合起来才是「容器」
- CPU 超限变慢（throttle），内存超限被杀（OOM SIGKILL，退出码 137）
- 进程级隔离是沙箱安全模型的地基，线程给不了

# RED-005: Redis RDB 与 AOF 如何选择？缓存场景需要持久化吗？

#### 简要回答

RDB 是时间点快照，AOF 记录写命令并可重放，两者的恢复粒度、文件大小和写入开销不同。纯可重建缓存可选择关闭持久化或按容灾要求配置；会话、评测状态等若是事实数据，不能只因放在 Redis 就随意丢失。当前 Compose 为 Redis 启用 AOF，不能据此推导完整容灾目标。


#### 详细解析


##### 1. 1. 两种持久化的侧重点

RDB 适合周期快照和快速加载，最近写入可能在崩溃时丢失；AOF 更接近逐写记录，重放恢复可能更细但增加写放大。Redis 官方通常建议重要数据组合使用，能接受分钟级损失可使用 RDB，纯缓存也可无持久化。最终取舍取决于数据是不是唯一事实与恢复目标。


##### 2. 2. 缓存与状态的边界

父块缓存丢失可以回源 PostgreSQL，重建代价和峰值需评估；若把用户会话或评测状态仅存 Redis，重启可能改变产品语义。应定义丢失后是重建、重新排队还是向用户报告，而不是只看 Redis 起来了。备份与恢复演练也比配置字符串更能证明可靠性。


##### 3. 3. 当前项目的可核对事实

RagTrail docker-compose 配置 redis:7-alpine，command 使用 --appendonly yes 并挂载 volumes/redis；代码 cache.py 将 Redis 当缓存且异常回源。可以准确说部署启用了 AOF 与数据卷，不能说做过灾备演练、RPO/RTO 或集群高可用。


#### 面试总结

- RDB 是快照
- AOF 是写入日志
- 纯缓存可无持久化
- Compose 启用 AOF 不等于演练高可用


#### 递进追问与参考答案


**追问 1：AOF 文件损坏怎么办？**

先保留故障现场与备份，按 Redis 文档和版本工具检查修复，恢复后校验业务数据。对可重建缓存可清空并回源，避免盲目把不完整缓存当事实。具体恢复步骤要配合部署与备份策略，不能只说重启。


**追问 2：只开 AOF 就不会丢数据吗？**

仍可能丢失最近未刷盘内容、磁盘故障或配置错误，且 AOF 不能保护应用在部分更新时的业务一致性。需要明确 fsync、备份、恢复和跨存储版本策略。

# DB-010: PostgreSQL、Milvus 与 Redis 如何保持文档更新一致？数据库事务能否一起回滚？

- **归属模块**：`数据库与 SQL` | **优先级**：`P0` | **性质**：`方案讨论` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

---

原题关联：新增：数据库基础与项目 SQL 能力展开

对应简历：资料入库；同名文档替换保护；PostgreSQL、Milvus、Redis


#### 简要回答

普通 PostgreSQL 事务不自动覆盖 Milvus 和 Redis。文档更新应围绕版本、状态与幂等步骤设计：准备新数据，验证后切换可见版本，失败可重试或补偿，缓存按版本失效。RAG 当前有同名文档暂存保护，但不能把它说成三种存储原子回滚。


#### 详细解析


##### 1. 1. 为什么会出现混合版本

文档正文、父块与向量分别写入不同存储。若先删旧向量再写新父块失败，可能短期不可检索；父块更新而缓存未删，可能补回旧上下文。每个单独服务成功不代表整体更新成功。失败重试还可能重复向量，必须定义稳定文档/块 ID 和版本作用域。


##### 2. 2. 可讨论的改进设计

新版本先写入暂存空间，校验块数量、引用和必要索引状态，再切换活跃版本；读链路携带版本过滤，旧版本异步清理。需要持久任务状态、可重复执行与补偿机制，避免进程退出后不知道完成到哪一步。这是方案，不声称当前已用 outbox、分布式事务或完整版本切换协议。


##### 3. 3. 对现有简历的准确解释

简历资料入库与同名替换可对应暂存准备和旧数据保护，父块数据库与缓存代码可看到单库 commit 与缓存更新。但准备通过后的删除、文件提升、父块和向量写入仍可能部分成功。面试应说明已覆盖的失败阶段与残余风险，而不是把“有 try/except”解释为跨库全部回滚。


#### 面试总结

- 单库事务不覆盖多存储
- 读写都要携带一致版本
- 幂等与补偿处理部分成功
- 暂存保护不等于原子回滚


#### 递进追问与参考答案


**追问 1：Redis 删缓存失败如何处理？**

TTL 只能限时容忍旧数据，不能提供即时一致。可按版本 Key 让新读不再访问旧缓存，并记录失败清理；若查询仍使用无版本 Key，需要分析允许的陈旧窗口。删除失败应可观察，不只吞掉错误。


**追问 2：能用一个分布式锁彻底解决吗？**

锁可减少同时更新，但不把三种存储变成一个原子事务，持锁进程也可能在部分写入后崩溃。仍需版本、状态记录与补偿；租约到期和旧持有者晚写还需要额外防护。当前不能声称已使用这套锁机制。

# DOCK-007: 沙箱超时或用户取消后，为什么既要停进程又要删命名容器？

---

原题关联：新增：Docker 部署与代码沙箱

对应简历：超时取消；无网络 Docker 沙箱


#### 简要回答

Docker CLI 进程与实际容器是两个生命周期。只杀宿主 CLI 不能保证容器中脚本已停止；应按命名容器执行清理，正常退出也可配合 --rm。DataPilot 有有限等待、停止子进程和 remove_container 收尾；清理失败还需记录并提供后续回收机制，不能直接假定没有残留。


#### 详细解析


##### 1. 1. 两个对象可能脱离

API 启动 docker run 后，CLI 等待容器输出，容器由 Docker daemon 管理。取消等待或 CLI 被杀可能让容器继续占资源。给每次执行独立安全名称，可在错误路径找到并移除对应容器，但名称要避免注入和冲突；不要模糊匹配删其他任务。


##### 2. 2. 清理需要幂等与预算

正常、超时、取消、启动失败都可能进入清理，应允许目标已经不存在。停止先给有限时间，再必要时强制；清理不能无限等待，否则取消也不能收敛。进程崩溃可能跳过 finally，因此可以有启动/周期残留扫描，但需明确所有权与保留策略。


##### 3. 3. 当前实现与不足

DataPilot runner 用异步 subprocess、communicate 与 deadline，remove_container 尽力删除命名容器，正常路径有 --rm。此处可以讲已有清理机制，但不宣称已有定时巡检或跨实例恢复。排查残留时记录 RunID、容器名、时间和状态，而不是暴露完整 stderr 给用户。


#### 面试总结

- CLI 与容器分别管理
- 命名资源支持精确清理
- 清理幂等且有限时
- finally 不覆盖进程崩溃


#### 递进追问与参考答案


**追问 1：为什么不能用 docker ps 全删？**

会误删正常运行的应用或其他任务，且无法区分所有权。应只清理当前任务明确命名和登记的资源，必要时通过标签/状态筛选，并核对是否仍在执行。


**追问 2：清理失败如何向用户展示？**

主任务仍应给明确超时/取消终态，内部记录清理失败与资源标识，触发后续回收。不能把清理失败吞掉并当完全成功，也不应把宿主路径和原始命令秘密直接返回用户。

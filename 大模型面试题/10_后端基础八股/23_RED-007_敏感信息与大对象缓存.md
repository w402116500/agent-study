# RED-007: Redis 里如何避免把敏感信息和大对象缓存成风险？

- **归属模块**：`Redis 缓存` | **优先级**：`P0` | **性质**：`方案讨论` | **来源**：《Agent应用开发个人面经》（20261002 新版简历配套整理，本模块复制收录、内容未改写）

#### 简要回答

缓存也属于数据副本，需按数据分类、Key 权限、序列化大小和 TTL 管控。敏感字段应最小化或脱敏，避免把完整 Prompt、凭证和用户私密内容长期写入；大父块应评估压缩、批量和容量。当前项目代码缓存会话/父块 JSON，面试时要明确这是实现事实，不推导已经完成隐私审计。


#### 详细解析


##### 1. 1. 缓存复制风险

数据库权限收紧后，Redis 副本可能仍保留旧内容；备份、AOF 和日志也扩展泄漏面。应只缓存需要重复读取的字段，设置合理过期，隔离 Redis 网络与认证，必要时加密或脱敏。Key 本身也可能暴露用户或文件名，不要把用户输入直接当路径或管理命令。


##### 2. 2. 大对象对延迟的影响

JSON 序列化和网络传输会随对象变大，单个父块缓存过大可能阻塞 Redis 单线程处理其他请求并增加内存碎片。可以拆分可独立读取的字段、限制最大正文、按 ID 批量回源，但拆分也增加请求数。选择要用命中率、P95、内存与回源成本验证。


##### 3. 3. 项目边界

RAG cache.py 使用 json.dumps 并 setex，没有材料证明加密、字段级脱敏或容量审计。DataPilot 的敏感字段遮蔽是结果输出链路约束，不能自动覆盖 RAG 缓存副本。回答可以指出这一差异，并将生产级密钥、访问控制和审计列为部署要求而非已完成事实。


#### 面试总结

- 缓存是敏感数据副本
- 大 JSON 会拖慢与占内存
- TTL 不等于隐私删除
- DataPilot 输出遮蔽不覆盖 RAG 缓存


#### 递进追问与参考答案


**追问 1：缓存加密后就安全了吗？**

加密只解决部分存储或传输风险，访问控制、密钥保管、备份与应用日志仍可能泄漏。还要减少不必要字段和缩短保留期，不能以一个配置声称完整合规。


**追问 2：要不要缓存完整父块？**

看回源成本和上下文需求。可缓存规范化后的必要正文与元数据，限制长度并按版本隔离；若父块很大，分块或数据库读取可能更合适。应通过命中率、延迟与内存实测选择。

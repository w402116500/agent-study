### 面试问题

你简历里写 SQL 安全有 17 条负向测试用例，全部按预期拦截。你当时为什么要专门做这 17 条测试？这些测试大概是怎么设计的，能说明什么、又不能说明什么？

### 我的原回答

这个的话是因为我要去测试 SQL Guard 的拦截效果。平时我们 Agent 系统模型基本上遇到的都是正向测试语句的错误，比如解析失败、join 错表了，或者字段不存在的问题。

负向测试的话主要是去测试拦截危险语句，比如写操作、分号、跨库引用、注释注入那些危险操作，比如用 `INTO OUTFILE` 写文件，`LOAD_FILE` 去读文件，`SELECT` 里面带有注释。

当然我不能说这些我们是能完美拦截所有攻击的。我们的系统依赖 SQLGlot，万一解析器没覆盖到，也有可能会越过拦截。目前只是拦截已知手法，改进的话必须再进行更多的测试。

### 关键修正

1. 普通 Agent 测试更多是在验证“SQL 能不能正确执行”，负向测试才是在验证“安全边界能不能挡住危险能力”。
2. 普通注释并不一定危险，更准确地说是**可执行注释 / 注释注入绕过**。
3. 这 17 条测试不是 17 个字符串黑名单，而是在验证默认拒绝 AST 策略对代表性风险类别的覆盖。
4. 不能说“解析器没覆盖就一定会放过去”，因为当前策略很多无法确认安全的结构会直接默认拒绝。
5. 更准确的边界是：系统依赖 SQLGlot 的解析正确性和自己的规则覆盖，因此这些测试不能证明安全完备性。

### 修正版口述答案

我专门做这 17 条负向用例，是因为普通 Agent 测试大多验证的是 SQL 能不能正常跑，比如字段错了、Join 错了或者语法解析失败，但这些不能说明安全边界是不是有效。

所以我另外设计了一组危险 SQL，主动去撞 Guard，覆盖写操作、多语句、`INTO OUTFILE`、`LOAD_FILE`、锁、变量、跨库引用、危险函数以及 MySQL 的可执行注释等绕过方式。

这些测试不是看 SQL 最后有没有执行成功，而是看它有没有在真正进入数据库执行之前被 Guard 拒绝，而且拒绝原因是不是符合预期。

17 条当前都按预期被拦截，说明这套默认拒绝策略在这些已覆盖场景下没有明显回归。但我不会说它能证明系统绝对安全，因为整个方案仍然依赖 SQLGlot 的解析正确性和规则覆盖范围。以后发现新的绕过方式，我会继续补进负向回归集。

### 一句话记忆

**17 条全拦截只能证明已覆盖场景没回归，不能证明不存在未知绕过。**

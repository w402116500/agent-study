### 面试官问题

**[题目原意已恢复，逐字问法未完整取回]**

Agent 多轮调用后消息、Tool result 会越来越多。你是怎么做上下文压缩的？如果把旧消息删掉，会不会把关键事实一起删掉？

### 我的原回答

**◐ 核心意思已取回。**

你当时能够区分“系统真实状态”和“每次喂给模型的消息视图”，并说明工具原始输出可以被裁剪，但已经结构化保存的当前目标、验证值、证据关系不能仅依赖聊天 transcript 存在。逐字回答未完整取回。

### 关键修正

这题最重要的不是背 message 数或字符预算，而是讲清架构：**事实状态不靠聊天历史保存，聊天历史只是每一轮给模型看的一个视图。**

压缩优先处理旧 ToolMessage 和冗余 transcript；当前 requirement、已验证值、证据绑定、已提交 claim 等关键状态从结构化 state 重新投影进 Working Set。这样即使原始工具输出被裁剪，系统仍然知道哪些事实已经验证、哪些目标还没完成。

简历里的 211 个分析回合、279 次压缩动作、输入 token 中位约 6.2k、峰值约 14.4k，只能当作固定历史评测的运行记录，不要说成系统通用性能保证。

### 修正版口述答案

我没有把完整聊天记录当成 Agent 的唯一状态存储。

系统会把当前分析目标、查询尝试、已经验证的值、证据绑定和已提交结论这些关键事实单独放在结构化状态里；每一轮真正发给模型的上下文只是从这些状态和最近消息重新装配出来的 Working Set。

当上下文接近预算时，我会优先压缩旧的 ToolMessage、冗余历史和大块结果，而不是把关键事实直接丢掉。下一轮即使原始 transcript 被裁掉，已经验证的事实仍然可以从结构化 state 投影回来。

所以我理解的上下文压缩不是“删聊天记录然后祈祷模型还记得”，而是把模型可见消息和系统真实状态分开管理。

### 一句话记忆

**事实状态不靠聊天历史保存，聊天历史只是每轮给模型看的一个视图。**

### 面试官问题

从用户提交一个数据分析问题到拿到 Markdown 答案，DataPilot 经过哪些组件和状态？

### 我的原回答

你当时是按完整 Run 生命周期回答的，主线是：请求接入 → 快照冻结 → Opening → LangGraph 工具循环 → 证据收敛 → Final Answer → 校验与 SSE 交付。

你原回答里可明确恢复的几句话包括：

> “最终节点的模型上下文只能收到证据清单。”

> “格式、引用编号、数字……任何一道不过则重试一次，不过就降级回答。”

同时你还覆盖了幂等请求、活跃 Run 检查、总超时与取消、Run 启动冻结 schema / graph / model / 遮蔽配置与文件快照、自定义串行工具执行、预算和失败断路等实现。

### 关键修正

第一，不是每调用一次 SQL/Python 就必须立刻提交一次结论。更准确的是：工具结果先形成候选证据；某个 requirement 的材料足够以后，Agent 再把“结论 + 证据引用”结构化提交。最终可进入回答的结论必须显式绑定证据。

第二，Final Answer 不只是看到一份“证据编号清单”。它看到的是重新投影后的最终回答上下文，包含用户问题、已提交结论、准入证据、Artifact 摘要、不完整项等，而不是整段原始 Tool transcript。

第三，后续源码核对后的当前实现是：Final Answer 的事实不一致或引用问题可以**修一次**；第二次仍失败才进入 partial。不要沿用早期“事实错误直接 partial”的旧口径。

### 修正版口述答案

用户提交问题后，后端先做请求幂等和活跃 Run 检查，然后为这次 Run 固定执行上下文，包括数据源、Schema revision、DataLink graph version、模型和遮蔽配置；文件型数据源还会固定输入快照，保证本次执行使用一致的基准。

接着进入 Opening 阶段，模型先判断是普通回复、需要澄清，还是需要真正的数据分析。只有提交合法的分析计划以后，才进入 LangGraph 的 Agent 循环。

分析阶段是 `Agent → 串行 Tool → Agent`。模型按需调用只读 SQL、Python 或 DataLink，服务端按顺序执行和审计，并把受控的 Tool observation 和 Working Set 再交给模型。同时有回合数、工具调用数、超时和同类失败等预算，避免无限循环。

工具结果先成为候选证据。某个分析目标已经具备足够材料时，模型需要把结论和证据引用结构化提交，只有通过材料准入的内容才能进入最终回答。

最后进入独立的 Final Answer 阶段。这里不再把完整原始工具 transcript 全量塞回模型，而是使用经过准入的最终回答上下文生成 Markdown；服务端再做引用和事实复核。如果可修复校验失败，当前实现只允许修一次，第二次仍失败就 partial。整个过程中的事件持久化后再通过 SSE 按序推给前端。

### 一句话记忆

**先冻结基准，再让 Agent 串行取证；结论先绑定证据，最后才生成正文。**

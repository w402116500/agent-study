## 3. 你的自动评分器怎么判“通过”？它会不会把语义上错误的答案判成正确？

### 面试官问题

**[题目原意已恢复，逐字问法未完整取回]**

你这个 57/60 是怎么判通过的？自动评分器能不能真正证明答案语义正确？

### 我的原回答

**◐ 核心意思已取回。**

你当时能够说出评分器是确定性的，并且承认它不是完整的语义裁判；对关键值、预期结果做程序化匹配，但评分器本身也有边界。逐字回答未完整取回。

### 关键修正

不要把自动评分器描述成“能理解所有答案语义”。当前更准确的定位是：它用固定规则检查预期单元格/关键值，并带数值容差，因此适合做稳定的回归判定；但如果一行里出现了相同数字、或者答案在业务语义上回答了别的问题，仅靠全文数值匹配存在误判空间。

因此评测的价值是“可重复地发现回归”，不是替代完整人工语义审计。

### 修正版口述答案

我的评分器是确定性的，主要目的是让同一批题能够稳定回归，而不是让另一个大模型来主观打分。

对于需要数据答案的题，它会按照预设的关键结果去检查最终输出，数值类会允许一定容差。这样同一版本重复跑时，评分口径不会因为 Judge 模型波动而变化。

但我不会说这个评分器能完整判断业务语义。比如文本里碰巧出现了目标数字，或者模型查的是另一个业务口径但数字接近，纯规则匹配就可能存在误判。所以它更适合作为回归测试和失败筛查；真正要证明泛化能力，还需要更大的独立测试集和人工语义审计。

### 一句话记忆

**评分器负责稳定回归，不等于完整的语义裁判。**

## 4. 从用户提交一个数据分析问题到拿到 Markdown 答案，DataPilot 经过哪些组件和状态？

### 面试官问题

从用户提交一个数据分析问题到拿到 Markdown 答案，DataPilot 经过哪些组件和状态？

### 我的原回答

**◐ 核心意思已取回，部分原句可恢复。**

你当时是按完整 Run 生命周期回答的，主线是：请求接入 → 快照冻结 → Opening → LangGraph 工具循环 → 证据收敛 → Final Answer → 校验与 SSE 交付。

你原回答里可明确恢复的几句话包括：

> “模型每一步都要去把证据提交，如果系统发现未提交会提示模型提交，两次上限……”

> “最终节点的模型上下文只能收到证据清单。”

> “格式、引用编号、数字……任何一道不过则重试一次，不过就降级回答。”

同时你还覆盖了幂等请求、活跃 Run 检查、总超时与取消、Run 启动冻结 schema / graph / model / 遮蔽配置与文件快照、自定义串行工具执行、预算和失败断路等实现。

### 关键修正

第一，不是每调用一次 SQL/Python 就必须立刻提交一次结论。更准确的是：工具结果先形成候选证据；某个 requirement 的材料足够以后，Agent 再把“结论 + 证据引用”结构化提交。最终可进入回答的结论必须显式绑定证据。

第二，Final Answer 不只是看到一份“证据编号清单”。它看到的是重新投影后的最终回答上下文，包含用户问题、已提交结论、准入证据、Artifact 摘要、不完整项等，而不是整段原始 Tool transcript。

第三，后续源码核对后的当前实现是：Final Answer 的事实不一致或引用问题可以**修一次**；第二次仍失败才进入 partial。不要沿用早期“事实错误直接 partial”的旧口径。

### 修正版口述答案

用户提交问题后，后端先做请求幂等和活跃 Run 检查，然后为这次 Run 固定执行上下文，包括数据源、Schema revision、DataLink graph version、模型和遮蔽配置；文件型数据源还会固定输入快照，保证本次执行使用一致的基准。

接着进入 Opening 阶段，模型先判断是普通回复、需要澄清，还是需要真正的数据分析。只有提交合法的分析计划以后，才进入 LangGraph 的 Agent 循环。

分析阶段是 `Agent → 串行 Tool → Agent`。模型按需调用只读 SQL、Python 或 DataLink，服务端按顺序执行和审计，并把受控的 Tool observation 和 Working Set 再交给模型。同时有回合数、工具调用数、超时和同类失败等预算，避免无限循环。

工具结果先成为候选证据。某个分析目标已经具备足够材料时，模型需要把结论和证据引用结构化提交，只有通过材料准入的内容才能进入最终回答。

最后进入独立的 Final Answer 阶段。这里不再把完整原始工具 transcript 全量塞回模型，而是使用经过准入的最终回答上下文生成 Markdown；服务端再做引用和事实复核。如果可修复校验失败，当前实现只允许修一次，第二次仍失败就 partial。整个过程中的事件持久化后再通过 SSE 按序推给前端。

### 一句话记忆

**先冻结基准，再让 Agent 串行取证；结论先绑定证据，最后才生成正文。**

## 5. 为什么 Run 开始时要冻结 Schema revision、DataLink graph version 和输入文件快照？

### 面试官问题

你刚才反复提到“Run 启动时要冻结快照”。那我想问，为什么一定要在 Run 开始时冻结 Schema revision、DataLink graph version 和输入文件快照？为什么不能每一轮 Agent 调工具的时候都直接读取当前最新的数据源状态？

### 我的原回答

**⚠️ 原话未完整取回。**

当前记录可以确认你的回答方向是“避免同一次 Run 中途发生版本漂移，让前后步骤基于不同事实基准”，但逐字口述没有完整保存。

### 关键修正

冻结的核心不是“追求旧数据”，而是保证一次 Run 内的**因果一致性、可复现性和可审计性**。

要注意边界：CSV / SQLite 这类文件型数据源可以固定输入快照；MySQL 的远程业务数据值并不是被做成完整数据库快照，因此不要说成“整个数据库在 Run 内绝对静止”。当前固定的是连接/Schema/DataLink/配置等运行基准，文件型源另有真实文件快照。

### 修正版口述答案

因为一次复杂分析会经历多轮模型和工具调用。如果每一轮都重新读取当前最新的 Schema、DataLink 图或者文件内容，那么分析进行到一半时，只要有人改了字段、发布了新的语义图，或者替换了文件，前面规划时看到的世界和后面执行时看到的世界就会不一致。

这样不仅容易出现“第一轮计划引用的字段，第三轮已经不存在”这种问题，也会让事后很难复现：同一个 Run 到底是基于哪个版本做出的结论说不清楚。

所以我在 Run 开始时固定 Schema revision、DataLink graph version、模型和遮蔽配置；对 CSV、SQLite 这类文件型数据源还固定输入快照。整个 Run 使用同一套运行基准，新的版本变化只影响后续新的 Run。

这里我也不会说 MySQL 的业务数据被完全快照冻结，它仍然是远程数据源；我固定的是这次 Run 的结构和配置基准，避免系统自己在执行中途换版本。

### 一句话记忆

**Run 内先保证同一个事实和配置基准，新变化留给下一次 Run。**

## 6. 上一轮已经查过的数字，为什么多轮追问时不能直接从历史摘要里拿来复用？

### 面试官问题

**[题目原意已恢复，逐字问法未完整取回]**

会话记忆里既然保存了历史摘要，用户下一轮追问同一个指标时，为什么还要重新查询？直接复用上一轮数字不是更省 token 和数据库开销吗？

### 我的原回答

**◐ 核心意思已取回。**

你当时的核心观点是：历史摘要可以帮助模型理解“上一轮在聊什么、用户口径是什么”，但不能把历史计算结果永久当作本轮事实；只靠“时间没过多久”也不足以证明旧数字仍然有效。

### 关键修正

这里要明确区分两件事：**历史语义**和**历史数据事实**。

历史主题、用户偏好、待澄清项可以复用；涉及金额、数量、占比等数据事实时，如果本轮仍然要把它作为证据使用，就应该重新证明。时间间隔短不代表数据没变。真正要做跨 Run 数值缓存，需要额外绑定数据版本、指标口径、时间有效性等条件，当前实现没有把它当作默认能力。

### 修正版口述答案

我的会话记忆主要复用的是历史语义，不是把上一轮数字当成永久事实。

比如用户上一轮问的是华东区域销售额，这一轮说“那占全国的比例呢”，我可以复用“华东区域”和用户之前的口径这些上下文，帮助理解追问。但分子、分母这些数据值如果本轮还要作为证据，就应该重新查询或重新证明，因为底层数据可能已经变化。

即使只过了几分钟，也不能单凭时间短就认为旧数字仍然有效。真正想跨 Run 复用数值，需要把数据版本、指标口径和有效时间一起做成明确的缓存契约。

### 一句话记忆

**历史语义可以复用，历史数据必须重新证明。**

## 7. 上下文越来越长时怎么压缩？压缩后为什么不会把关键事实丢掉？

### 面试官问题

**[题目原意已恢复，逐字问法未完整取回]**

Agent 多轮调用后消息、Tool result 会越来越多。你是怎么做上下文压缩的？如果把旧消息删掉，会不会把关键事实一起删掉？

### 我的原回答

**◐ 核心意思已取回。**

你当时能够区分“系统真实状态”和“每次喂给模型的消息视图”，并说明工具原始输出可以被裁剪，但已经结构化保存的当前目标、验证值、证据关系不能仅依赖聊天 transcript 存在。逐字回答未完整取回。

### 关键修正

这题最重要的不是背 message 数或字符预算，而是讲清架构：**事实状态不靠聊天历史保存，聊天历史只是每一轮给模型看的一个视图。**

压缩优先处理旧 ToolMessage 和冗余 transcript；当前 requirement、已验证值、证据绑定、已提交 claim 等关键状态从结构化 state 重新投影进 Working Set。这样即使原始工具输出被裁剪，系统仍然知道哪些事实已经验证、哪些目标还没完成。

简历里的 211 个分析回合、279 次压缩动作、输入 token 中位约 6.2k、峰值约 14.4k，只能当作固定历史评测的运行记录，不要说成系统通用性能保证。

### 修正版口述答案

我没有把完整聊天记录当成 Agent 的唯一状态存储。

系统会把当前分析目标、查询尝试、已经验证的值、证据绑定和已提交结论这些关键事实单独放在结构化状态里；每一轮真正发给模型的上下文只是从这些状态和最近消息重新装配出来的 Working Set。

当上下文接近预算时，我会优先压缩旧的 ToolMessage、冗余历史和大块结果，而不是把关键事实直接丢掉。下一轮即使原始 transcript 被裁掉，已经验证的事实仍然可以从结构化 state 投影回来。

所以我理解的上下文压缩不是“删聊天记录然后祈祷模型还记得”，而是把模型可见消息和系统真实状态分开管理。

### 一句话记忆

**事实状态不靠聊天历史保存，聊天历史只是每轮给模型看的一个视图。**

## 8. 你说有“结论提交 → 材料准入 → 正文数字复核”三阶段校验，这三层分别解决什么？

### 面试官问题

**[题目原意已恢复，逐字问法未完整取回]**

你简历里写了三阶段答案校验。为什么要分成三层？第一层和最后一层看起来不都是在检查数字吗？

### 我的原回答

**◐ 核心意思已取回。**

你当时已经能区分：先检查模型提交的结论是否真的有查询证据，再限制哪些材料可以进入最终回答，最后检查 Markdown 正文有没有把这些已确认事实写错。逐字回答未完整取回。

### 关键修正

三层不是重复检查：

1. **结论提交**：模型声明“我的结论是什么、依据哪些证据、值是多少”，系统核对提交值是否来自已验证查询结果。
2. **材料准入**：不是所有工具结果都能自动成为最终回答材料；只有被有效 claim 接纳的验证事实才进入 Final Answer 材料集。
3. **正文复核**：即便前两步都正确，模型在自然语言生成 Markdown 时仍可能抄错数字或引用，因此正文还要再次与准入事实核对。

DataLink 的语义关系可以帮助理解结构，但不能凭自己变成金额、数量等数值事实。

### 修正版口述答案

我把它拆成三层，是因为三个阶段防的是不同错误。

第一层是结论提交。模型不能只说“我分析完了”，而是要把结论、证据引用和关键值结构化提交，系统先确认这些值确实来自当前 Run 已经验证过的查询结果。

第二层是材料准入。前面可能执行了很多探索 SQL 或工具调用，但不是所有结果都应该被 Final Answer 使用。只有真正支持已提交结论的验证材料才能进入最终回答上下文。

第三层是正文复核。即使前两层已经确认了“正确事实是什么”，最终模型在把它写成 Markdown 时仍然可能抄错数字或者引用错来源，所以服务端还会对可明确绑定的正文事实再核一次。

所以第一层是“结论有没有证据”，第二层是“哪些材料有资格进答案”，第三层是“最终正文有没有忠实写出这些事实”。

### 一句话记忆

**结论有证据、材料要干净、落到正文还要再核一遍。**

## 10. 为什么不能只靠数据库只读账号，或者简单判断 SQL 是否以 SELECT 开头？

### 面试问题

你简历里写了 SQL 安全是 SQLGlot + default-deny 的只读 AST 校验。你具体讲一下：为什么不能只靠数据库只读账号或者简单判断 SQL 是不是以 SELECT 开头？你这套 SQL 安全到底拦了哪些风险？

### 我的原回答

首先，如果是走文件型的数据源的话，只读账号是防不住的，因为那两个没有账号体系。简单判断 SQL 开头的话，有可能危险语句藏在语法结构里，比如加了分号，分号右边加了一条危险语句，或者子查询里藏了 `sleep`，还有用前导注释伪装的，用前缀判断应付不了这些情况。

另外还有就是结果查询如果太大的话，没有加 `limit` 限制很可能返回的时候挤爆内存。

我的 SQL 拦截具体包括结构类、写入类、函数类、范围类、资源类、拒绝信息类。结构类拦截空语句、解析失败、多语句、非查询节点；写入类拦截非查询节点和 `into` 子句；函数类拦截黑名单和 MySQL 未知函数白名单，只放行确认安全的函数；范围类拦截 SQL 里出现的表、列没有对应当前 Run 的 schema 快照的语句；资源类就是没有加 `limit` 的，防止一下返回几十万行挤爆内存。

### 关键修正

1. **核心思路是对的**：只读账号只是最后一道保险，而且 CSV、SQLite 这类数据源并不存在统一的数据库账号体系。
2. 不能只判断 `SELECT` 前缀，因为危险能力可能藏在多语句、子查询、函数、可执行注释等结构里。
3. 当前实现里，**没有 LIMIT 不是直接拦截**，而是自动注入默认 LIMIT；LIMIT 太大时会被收紧到最大值。
4. MySQL 的“未知函数”更准确的说法是：SQLGlot 解析成匿名函数、又不在明确 allowlist 中的，默认拒绝。
5. 资源保护不只靠 LIMIT，执行层还有结果行数、列数、单元格大小、总字节数、超时等限制。
6. 最稳的表达不是“看 SQL 像不像 SELECT”，而是“看 AST 里到底允许它做什么”。

### 修正版口述答案

只靠数据库只读账号不够，因为我的系统除了 MySQL，还有 CSV、SQLite 这类文件型数据源，它们没有统一的账号权限体系，所以只读账号最多只能作为某些数据库上的最后一道保险。

另外，简单判断 SQL 是否以 `SELECT` 开头太浅了。危险能力可能藏在多语句、子查询、函数、`INTO OUTFILE`、跨库引用或者 MySQL 的可执行注释里，所以我会先用 SQLGlot 把 SQL 解析成 AST，再按默认拒绝的方式判断它实际包含什么能力。

我的 Guard 会拦截多语句、非查询结构、写操作、危险函数、文件访问、锁、跨库引用、未知表列以及可执行注释这类风险。对资源问题，我不是简单拒绝没写 LIMIT 的 SQL，而是自动补默认 LIMIT，过大的 LIMIT 也会被收紧，执行层还会继续限制结果规模和执行时间。

所以我的核心不是判断 SQL “长得像不像 SELECT”，而是判断 **AST 里到底允许它做什么**。

### 一句话记忆

**不是看 SQL 像不像 SELECT，而是看 AST 里到底允许它做什么。**

## 14. 为什么要专门做 17 条 SQL 负向安全测试？它能说明什么，不能说明什么？

### 面试问题

你简历里写 SQL 安全有 17 条负向测试用例，全部按预期拦截。你当时为什么要专门做这 17 条测试？这些测试大概是怎么设计的，能说明什么、又不能说明什么？

### 我的原回答

这个的话是因为我要去测试 SQL Guard 的拦截效果。平时我们 Agent 系统模型基本上遇到的都是正向测试语句的错误，比如解析失败、join 错表了，或者字段不存在的问题。

负向测试的话主要是去测试拦截危险语句，比如写操作、分号、跨库引用、注释注入那些危险操作，比如用 `INTO OUTFILE` 写文件，`LOAD_FILE` 去读文件，`SELECT` 里面带有注释。

5. 更准确的边界是：系统依赖 SQLGlot 的解析正确性和自己的规则覆盖，因此这些测试不能证明安全完备性。

所以我另外设计了一组危险 SQL，主动去撞 Guard，覆盖写操作、多语句、`INTO OUTFILE`、`LOAD_FILE`、锁、变量、跨库引用、危险函数以及 MySQL 的可执行注释等绕过方式。

这些测试不是看 SQL 最后有没有执行成功，而是看它有没有在真正进入数据库执行之前被 Guard 拒绝，而且拒绝原因是不是符合预期。

17 条当前都按预期被拦截，说明这套默认拒绝策略在这些已覆盖场景下没有明显回归。但我不会说它能证明系统绝对安全，因为整个方案仍然依赖 SQLGlot 的解析正确性和规则覆盖范围。以后发现新的绕过方式，我会继续补进负向回归集。

### 一句话记忆

**17 条全拦截只能证明已覆盖场景没回归，不能证明不存在未知绕过。**

## 15. Guard 越做越严格，会不会误杀正常 SQL？怎么平衡安全和可用性？

### 面试问题

如果 Guard 越做越严格，会不会把很多正常 SQL 也误杀？你怎么在“安全”和“可用性”之间做平衡？

### 我的原回答

当然会有这个问题。首先安全肯定是最重要的，可用性方面我会把拒绝边界设置在可覆盖范围。

比如 MySQL 下我不认识的函数默认拒绝，SQLGlot 不认识的匿名函数拒绝；正常的常用函数方向，通过 SQLGlot 的 AST 语法树可以精确去识别结构，防止过度误杀。

还有一点就是将这些拒绝信息和提示反馈给模型去自行修复，并且带上为什么拒绝的原因返回给模型，告诉模型应该如何重试。

### 关键修正

1. “MySQL 下我不认识的函数都拒绝”不够准确。
2. 更准确的是：**SQLGlot 解析成匿名函数、又不在明确 allowlist 中的函数，默认拒绝。**
3. AST 比字符串规则更可靠地识别结构，但不要说成“绝对精确”。
4. 要区分可修复错误和安全边界错误：前者可以反馈原因让模型改写，后者不应该为了成功率自动放宽。

### 修正版口述答案

这个确实有安全和可用性的权衡，但我的原则还是安全边界优先。

我尽量不用简单的关键字黑名单，而是让 SQLGlot 先把 SQL 解析成 AST，再根据真实结构判断。这样正常的子查询、CTE、聚合等结构不会因为字符串碰撞就被误杀。

对于一些不能确认安全的能力，我会采用默认拒绝。比如 MySQL 里 SQLGlot 解析成匿名函数、又不在明确放行列表里的函数，我宁愿先拒绝，而不是直接交给数据库执行。

另一方面，拒绝以后也不是让 Agent 卡死。像解析失败、字段不存在这类可以修复的问题，我会把拒绝原因、出问题的位置或者提示返回给模型，让它改写 SQL 再试。

但如果是写操作、跨库、危险函数这类安全边界问题，就不会为了提高成功率自动放宽规则。

### 一句话记忆

**安全边界不自动放宽，可修复错误给模型重试路径。**

## 16. 线上合法业务确实需要一个当前不在 allowlist 里的 MySQL 函数，怎么办？

### 面试问题

如果线上真的遇到一个合法业务查询，必须使用某个现在不在 allowlist 里的 MySQL 函数，你会怎么处理？会不会让模型自己把它加进白名单？

### 我的原回答

这个的话，必须得专门针对这个函数去做定向测试。我们当然不是让模型去把它加进白名单。

目前我们的所有安全都是由系统去确定性判断的，不能让模型自行判断是否安全。只有经过校验过后的函数，才能自己对代码层去加入函数。

### 关键修正

1. 安全策略的修改权不能交给模型，这一点非常关键。
2. 新函数需要做定向安全测试，确认它是否存在文件访问、锁、外部资源等危险能力。
3. 通过后，应由开发者通过代码变更显式加入 allowlist。
4. 同时应补对应的正向和负向回归测试。

### 修正版口述答案

如果线上确实有合法业务需要一个当前没放行的 MySQL 函数，我不会让模型自己决定放行。

我会先针对这个函数做定向测试，确认它的能力边界，包括正常调用以及有没有文件访问、锁、外部资源这类风险。确认安全以后，再由开发者通过代码变更显式加入 allowlist，同时补对应的正向和负向回归测试。

因为我这套安全设计的原则一直是确定性判断：模型可以生成 SQL，但不能修改安全策略本身。

### 一句话记忆

**模型只能使用安全策略，不能修改安全策略。**

## 17. DataLink 到底解决什么问题？为什么只有 Schema 还不够？

### 面试问题

你简历里写 DataLink 语义映射把一个历史评测子集从 66.7% 提到了 83.3%。DataLink 在你的系统里到底解决什么问题？为什么只有 Schema 还不够？

### 我的原回答

这个的话是为了解决模型读不到数据库的业务逻辑，比如字段与业务概念的对应、近似语义的字段、跨表的相邻连接关系。

比如说用户问各会员等级的平均评分，模型会去判断字段名是不是会员等级，但是其实它不是，模型只能靠猜。相似语义的歧义，比如说店铺评分，有个是店铺自身的评分，有个是顾客对订单的评价，模型可能会选错字段。外键的话只能表示直接联系，但是不能描述间接关系。

DataLink 的实现主要是通过抽取数据源表结构，然后对数据源去采每个字段的前五个值，这个会进行脱敏处理，然后去推断关系，通过 join 关系、同义词表匹配、分布相似度，把表和表、字段与字段的联系度打分。之后会让 LLM 去把列映射为业务概念、实体、语义关系。

当然我不能说 DataLink 返回的关系一定是对的。我实际测试是用了三轮同样的测试，两组同样的问题，但区别是让模型去调用 DataLink 的语义地图，明显结果 DataLink 对有语义的难题提升比较大。

关于 DataLink 不准的办法，我的解决方案是让人工去进行审核。系统生成 DataLink 图谱后，我们可以去编辑相应的语义关系、概念，去精准 DataLink 的语义地图。

### 关键修正

1. 核心定位非常对：**Schema 解决结构，DataLink 补业务语义。**
2. “每个字段采前五个值”不准确。
3. 当前给 Agent 的安全语义投影中，只有低基数分类字段才会携带受限 `typical_values`，数量最多 20；敏感字段的典型值会被剥掉。
4. 当前可以明确确认 Agent 会看到字段语义、aliases、concept / entity 映射、relationship、join path、confidence、provenance。
5. “同义词表 + 分布相似度”这类构建打分细节，第一层不要讲死，除非已经核对构建器源码。
6. 66.7% → 83.3% 应表述为**固定语义题子集上的历史对照结果**，不能说成整体系统准确率。
7. DataLink 不是绝对真相，需要人工审核和修订。

### 修正版口述答案

DataLink 主要解决的是物理 Schema 和业务语义之间的缺口。

只有 Schema 的时候，模型知道有哪些表、字段、类型和外键，但它不一定知道某个字段在业务上到底代表什么。比如用户问“会员等级”，数据库里未必就有一个叫 `member_level` 的字段；或者“店铺评分”可能既有店铺自身评级，也有用户对订单的评价，光看字段名模型很容易猜错。

另外，外键能告诉模型直接关系，但复杂问题可能需要多跳 Join。DataLink 会把字段和业务概念、实体以及候选关系、Join Path 组织成一层语义地图，并带上置信度和来源信息。

Agent 真正拿到的不是完整原始图，而是一个受限语义投影，包括字段别名、业务概念映射、关系和 Join Path；敏感典型值会被剥掉。

我也没有把 DataLink 当绝对真相。历史上我在固定语义题子集做过三轮对照，结果从 66.7% 到 83.3%，说明它对这组语义歧义题有帮助，但这不是整体准确率证明。

如果自动生成的语义关系不准，我还提供了人工审核和编辑能力，可以修正概念、映射和关系，再发布新的图版本。

### 一句话记忆

**Schema 告诉模型数据长什么样，DataLink 补的是这些字段在业务里是什么意思、应该怎么连。**

## 18. DataLink 自己也可能推错，怎么避免它变成新的错误事实源？

### 面试问题

既然 DataLink 自己也可能推错，那 Agent 拿到一个错误的语义关系以后，会不会直接生成错误 SQL？你怎么保证 DataLink 不会从“辅助信息”变成新的错误事实源？

### 我的原回答

我不能保证 DataLink 绝对不出错。DataLink 只是给模型的参考建议，并没有要求模型一定要遵循 DataLink 的建议。

并且 DataLink 带回来的边会带上源，比如说外键还是推断、置信度、证据 JSON。关系边只是一点，正确的外键边、典型值还会存在召回结果里，模型是看到的多份材料。

当然最终拦截还是得经由我们的系统判断，不会让模型胡乱生成，这是最终底线。

### 关键修正

1. 前半段是对的：DataLink 是**推断型语义建议**，不是权威事实源。
2. 当前语义上下文明确带有 `trust="inferred"`。
3. relationship / join path 会保留 `provenance`、`confidence`，部分关系还会带 evidence。
4. 模型看到的不只是单一关系，还可能同时看到物理 Schema、字段语义、典型值和 Join Path。
5. 但最后一句“系统能兜底”说得过头了。
6. 系统能校验表列是否存在、SQL 是否安全、查询结果是否真实、Claim 数值是否来自真实结果；但**不能保证识别业务语义选错**。

### 修正版口述答案

我不能保证 DataLink 一定正确，所以我没有把它当事实源，而是当语义建议。

DataLink 返回的关系会保留来源、置信度以及部分证据信息，模型还能同时看到物理 Schema、字段语义和候选 Join Path，不是要求它机械地按照某一条推断关系生成 SQL。

系统层还能保证一部分确定性边界，比如最后使用的表和字段必须真实存在于当前 Schema，SQL 必须通过安全校验，查询结果和后续提交的数值也要能对应上真实执行结果。

但是我要明确一个边界：如果 DataLink 在业务语义上把两个都真实存在的字段映射错了，而模型又采纳了这个错误映射，那么 SQL 可能依然合法、结果也可能自洽，这种错误系统未必能自动发现。

所以我对 DataLink 的定位一直是辅助语义层，不是权威事实层。对系统性的语义错误，我主要通过置信度、来源信息、历史评测以及人工审核和修正图谱来降低风险。

### 一句话记忆

**系统能验证这个数字是不是查出来的，但不一定能验证你是不是查对了业务指标。**

## 19. 如果 DataLink 映射错了，但 SQL、结果、三阶段事实校验都通过，系统能发现吗？

### 面试问题

如果 DataLink 恰好把业务字段映射错了，但 SQL 合法、查询结果也真实，甚至三阶段事实校验都通过了，你这套系统能发现吗？如果发现不了，你会怎么改进？

### 我的原回答

这个的话确实判断不了。我最理想的办法就是去审计和人工修订。

我们每轮的 DataLink 调用结果都会去带上标注和源，去方便我们审核错误点。

### 关键修正

1. 这个边界判断是对的：现有系统不能自动判断所有业务语义错误。
2. 更准确的说法不是“每个结果都有完整证据 JSON”，而是：语义关系尽量保留来源、置信度和可用证据；系统记录当次消费的图版本和安全语义投影。
3. 审计的价值是定位“模型当时到底看到了哪条语义映射或关系”。
4. 人工修订不应该只修一次回答，而应该修正**语义资产本身**，让后续 Run 都受益。

### 修正版口述答案

这种情况我确实没法靠现有的 SQL 或事实校验自动发现，因为它查到的数据可能完全真实，只是业务语义选错了。

我的处理思路主要是审计加人工修订。DataLink 返回的关系会保留来源、置信度以及可用的证据信息，系统也会记录当次使用的图版本和语义投影，所以如果线上发现答案语义错了，我能追到当时模型到底参考了哪条映射或者哪条关系。

确认是 DataLink 本身的问题以后，我不会只改单次回答，而是直接修订对应的概念、字段映射或者关系，再发布新的语义图版本，让后续 Run 使用修正后的结果。

所以这里我的目标不是声称系统能自动识别所有语义错误，而是让这种错误 **可追踪、可修正、修一次以后能沉淀下来**。

### 一句话记忆

**语义错误未必能自动判，但要做到可追踪、可修订、可沉淀。**

### 面试问题

如果 Guard 越做越严格，会不会把很多正常 SQL 也误杀？你怎么在“安全”和“可用性”之间做平衡？

### 我的原回答

当然会有这个问题。首先安全肯定是最重要的，可用性方面我会把拒绝边界设置在可覆盖范围。

比如 MySQL 下我不认识的函数默认拒绝，SQLGlot 不认识的匿名函数拒绝；正常的常用函数方向，通过 SQLGlot 的 AST 语法树可以精确去识别结构，防止过度误杀。

还有一点就是将这些拒绝信息和提示反馈给模型去自行修复，并且带上为什么拒绝的原因返回给模型，告诉模型应该如何重试。

### 关键修正

1. “MySQL 下我不认识的函数都拒绝”不够准确。
2. 更准确的是：**SQLGlot 解析成匿名函数、又不在明确 allowlist 中的函数，默认拒绝。**
3. AST 比字符串规则更可靠地识别结构，但不要说成“绝对精确”。
4. 要区分可修复错误和安全边界错误：前者可以反馈原因让模型改写，后者不应该为了成功率自动放宽。

### 修正版口述答案

这个确实有安全和可用性的权衡，但我的原则还是安全边界优先。

我尽量不用简单的关键字黑名单，而是让 SQLGlot 先把 SQL 解析成 AST，再根据真实结构判断。这样正常的子查询、CTE、聚合等结构不会因为字符串碰撞就被误杀。

对于一些不能确认安全的能力，我会采用默认拒绝。比如 MySQL 里 SQLGlot 解析成匿名函数、又不在明确放行列表里的函数，我宁愿先拒绝，而不是直接交给数据库执行。

另一方面，拒绝以后也不是让 Agent 卡死。像解析失败、字段不存在这类可以修复的问题，我会把拒绝原因、出问题的位置或者提示返回给模型，让它改写 SQL 再试。

但如果是写操作、跨库、危险函数这类安全边界问题，就不会为了提高成功率自动放宽规则。

### 一句话记忆

**安全边界不自动放宽，可修复错误给模型重试路径。**

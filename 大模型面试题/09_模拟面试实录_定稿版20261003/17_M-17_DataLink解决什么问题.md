### 面试问题

你简历里写 DataLink 语义映射把一个历史评测子集从 66.7% 提到了 83.3%。DataLink 在你的系统里到底解决什么问题？为什么只有 Schema 还不够？

### 我的原回答

这个的话是为了解决模型读不到数据库的业务逻辑，比如字段与业务概念的对应、近似语义的字段、跨表的相邻连接关系。

比如说用户问各会员等级的平均评分，模型会去判断字段名是不是会员等级，但是其实它不是，模型只能靠猜。相似语义的歧义，比如说店铺评分，有个是店铺自身的评分，有个是顾客对订单的评价，模型可能会选错字段。外键的话只能表示直接联系，但是不能描述间接关系。

DataLink 的实现主要是通过抽取数据源表结构，然后对数据源去采每个字段的前五个值，这个会进行脱敏处理，然后去推断关系，通过 join 关系、同义词表匹配、分布相似度，把表和表、字段与字段的联系度打分。之后会让 LLM 去把列映射为业务概念、实体、语义关系。

当然我不能说 DataLink 返回的关系一定是对的。我实际测试是用了三轮同样的测试，两组同样的问题，但区别是让模型去调用 DataLink 的语义地图，明显结果 DataLink 对有语义的难题提升比较大。

关于 DataLink 不准的办法，我的解决方案是让人工去进行审核。系统生成 DataLink 图谱后，我们可以去编辑相应的语义关系、概念，去精准 DataLink 的语义地图。

### 关键修正

1. 核心定位非常对：**Schema 解决结构，DataLink 补业务语义。**
2. “每个字段采前五个值”不准确。
3. 当前给 Agent 的安全语义投影中，只有低基数分类字段才会携带受限 `typical_values`，数量最多 20；敏感字段的典型值会被剥掉。
4. 当前可以明确确认 Agent 会看到字段语义、aliases、concept / entity 映射、relationship、join path、confidence、provenance。
5. “同义词表 + 分布相似度”这类构建打分细节，第一层不要讲死，除非已经核对构建器源码。
6. 66.7% → 83.3% 应表述为**固定语义题子集上的历史对照结果**，不能说成整体系统准确率。
7. DataLink 不是绝对真相，需要人工审核和修订。

### 修正版口述答案

DataLink 主要解决的是物理 Schema 和业务语义之间的缺口。

只有 Schema 的时候，模型知道有哪些表、字段、类型和外键，但它不一定知道某个字段在业务上到底代表什么。比如用户问“会员等级”，数据库里未必就有一个叫 `member_level` 的字段；或者“店铺评分”可能既有店铺自身评级，也有用户对订单的评价，光看字段名模型很容易猜错。

另外，外键能告诉模型直接关系，但复杂问题可能需要多跳 Join。DataLink 会把字段和业务概念、实体以及候选关系、Join Path 组织成一层语义地图，并带上置信度和来源信息。

Agent 真正拿到的不是完整原始图，而是一个受限语义投影，包括字段别名、业务概念映射、关系和 Join Path；敏感典型值会被剥掉。

我也没有把 DataLink 当绝对真相。历史上我在固定语义题子集做过三轮对照，结果从 66.7% 到 83.3%，说明它对这组语义歧义题有帮助，但这不是整体准确率证明。

如果自动生成的语义关系不准，我还提供了人工审核和编辑能力，可以修正概念、映射和关系，再发布新的图版本。

### 一句话记忆

**Schema 告诉模型数据长什么样，DataLink 补的是这些字段在业务里是什么意思、应该怎么连。**

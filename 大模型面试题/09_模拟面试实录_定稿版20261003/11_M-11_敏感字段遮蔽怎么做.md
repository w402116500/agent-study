### 面试问题

你刚才提到除了 SQL 安全校验以外，查询结果还会对敏感字段做遮蔽。这个脱敏具体是怎么做的？你为什么选择在这一层做，而不是让模型自己判断哪些字段敏感？

### 我的原回答

这里我做的是主要在配置层里先可以设置遮蔽字段，在数据源配置中可以配置需要遮蔽的具体字段。设置后该字段的查询信息会替换成星号。

匹配方式是通过生成的 SQL 语句用 SQLGlot 去解析查询结果列名是否与遮蔽字段匹配，匹配就遮蔽。

让模型自己判断字段敏感的话，如果你是用的本地部署的大模型，那当然没问题。我主要是考虑到隐私性的问题，所以不让大模型去自我判断。

### 关键修正

1. 数据源所有者显式配置 `mask_fields` 这一点是对的。
2. **脱敏本身不靠 SQLGlot。** SQLGlot 主要负责 SQL 安全校验。
3. SQL 执行后，Data Gateway 根据**返回结果列名**和配置的敏感字段做大小写不敏感匹配；命中的值替换为 `***`。
4. 脱敏发生在结果进入 Agent 和 Artifact 之前。
5. “本地模型就没问题”不够准确。即使是本地模型，也不应该让概率模型自己决定安全策略，因为它可能漏判。
6. 安全策略应该由确定性代码执行，而不是模型自我约束。

### 修正版口述答案

我这里没有让模型自己识别敏感字段，而是采用显式配置。

数据源所有者先确认哪些字段需要遮蔽，这份配置会跟数据源一起保存，并在 Run 开始时固定下来。SQL 执行完成以后，Data Gateway 在结果返回之前做统一序列化，根据结果列名和配置的敏感字段做匹配，命中的值统一替换成 `***`。

所以进入 Agent、查询结果 Artifact 和后续回答链路的已经是脱敏数据，而不是先让模型看到原值，再让模型决定要不要隐藏。

我没有把这个判断交给模型，是因为安全策略不能依赖概率判断。即使是本地模型，也可能漏判；而且原始敏感值一旦已经进入模型上下文，再在答案阶段遮住就已经晚了。

### 一句话记忆

**敏感字段由用户显式配置，Data Gateway 在数据进入模型之前统一遮蔽。**
